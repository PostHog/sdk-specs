# Writing SDK acceptance tests

## Establish the contract

1. Read the relevant canonical `openspec/specs/<capability>/spec.md` before writing a test. Audit existing acceptance scenarios against it: scenarios may be out of date, over-specific, or missing important assertions. Treat OpenSpec as the source of truth, not the current Gherkin wording or one SDK's behavior.
2. Read the relevant public SDK implementation and tests to find untested branches, inputs, outcomes, and interactions. Source code supplies candidates and evidence of divergences; it does **not** silently redefine the canonical contract. Record gaps between source and OpenSpec rather than changing the test to match a defect.
3. Compare the public method's signature with the compliance adapter's negotiated RPC route and argument mapping. Account for required and optional parameters, omission versus explicit `null`, `false`, zero, nested values, reserved-looking property names, native return kinds, and invalid inputs where relevant. Do not invent parameters, defaults, results, or capabilities in the adapter.
4. If OpenSpec, existing acceptance scenarios, and the intended SDK contract conflict, stop and ask for a product decision. For an approved correction, use this repository's OpenSpec CLI workflow: create or continue a change, follow `openspec status` and `openspec instructions` to prepare its delta, apply it, validate strictly, and archive/sync it into the canonical spec on the same branch and in the same PR. Do not directly edit the canonical spec before preparing the delta or resolve a conflict by weakening an assertion.
5. Once the intended canonical behavior is explicitly confirmed, **state that it is a canonical specification correction**. List each audited SDK that currently differs, with source evidence, the observable correction needed, and whether a separate SDK change is required. Existing SDK behavior is not a vote that overrides the confirmed contract. Do not quietly claim a divergent SDK conforms or change its production code as part of an acceptance-test PR.

## Observe public behavior

- Acceptance tests are **black-box** tests. Exercise public SDK methods through supported adapter routes, then inspect outputs available to an SDK caller or traffic received by the isolated mock service. To test event delivery, perform the public flush and assert the received event count, name, identities, and relevant JSON properties. A test of non-delivery must include a bounded delivery/flush observation; merely observing an empty queue or a moment without traffic does not prove a drop.
- Do not inspect private queues, cached evaluator state, internal scheduling, mutable counters invented by an adapter, or implementation-specific object layouts. Do not infer an event was queued from the fact that it was delivered; describe the observable outcome instead. Require fixed clocks or scheduling controls only when the contract actually asserts externally observable time or ordering behavior.
- Allocate a fresh, isolated SDK instance and mock receiver per scenario. Isolation is normal test setup, not an assertion that SDK storage needed explicit clearing. Populate storage explicitly only when the scenario needs pre-existing data.
- Public SDK methods must not throw or reject to their callers. Do not make a native throw an accepted success outcome in an acceptance test. Distinguish SDK method throws from adapter protocol/transport errors; expose both faithfully in reports. If existing OpenSpec permits an SDK throw, flag the conflict for an explicit spec decision rather than enshrining that allowance in a new test.
- Preserve JSON semantics in received-event assertions: property absence differs from `null`, `true` differs from `1`, `false` differs from `0`, and nested collections must compare recursively. Assert only properties the canonical contract actually requires, not incidental enrichment or implementation-specific duplicates.

## Select and validate the intended scope

- Prefer adding or correcting scenarios in the relevant existing `acceptance/` feature. Do not create a parallel feature solely to work around a feature-wide `Background`; make setup apply only where its steps are relevant. Preserve unrelated client, server, and negative coverage when reorganizing a feature.
- Opt in migrated acceptance scenarios with `@sdk:server` or `@sdk:client`, matched against the adapter's negotiated `sdk_type`. The adapter declares its SDK type, supported routes, and capabilities; the harness owns scenario selection and assertions. Do not interpret legacy `@server`, `@client`, or `@both` as v2 selectors. Remove redundant legacy scope tags from migrated scenarios, including inherited feature-level tags; retain their meaning on unmigrated scenarios without opting those scenarios in. If a scenario should run for both SDK types, define and validate that selection rule before migrating it rather than assuming a combination of tags already works.
- Keep applicability distinct from selection. The v2 `--acceptance-suite` discovers acceptance features and selects scenarios opted in with `@sdk:` for the adapter's declared SDK type. The YAML-parity suite uses the same Gherkin runner with capability-based selection; its legacy descriptive tags do not opt unrelated acceptance scenarios in. An explicit `--feature` or `--case-id` is a debugging scope, not evidence that an SDK profile selected the entire intended suite. Verify the actual runner behavior before claiming coverage. A selected case with a missing route or step binding is a visible gap, not a silent skip. Report what ran and what remained unselected.
- A Scenario Outline's Examples rows are distinct executions, not duplicates to suppress. Use feature path, scenario name, and the concrete Examples row/input to describe failures. An ordinary single-case acceptance scenario does not need an authored `@case:` tag. If a matrix needs stable per-row labels, use `@case:<case_id>` on the outline with unique values in a `case_id` Examples column. The YAML-parity suite uses the same Gherkin parser and harness; its distinct, readable feature-path/scenario-name pairs identify ordinary scenarios. The v2 report uses an internal `case_id` to correlate inventory, results, and fixtures; a scenario without an authored label uses its feature path and name. Unmigrated outlines without per-row labels still use source-row locations until their acceptance coverage is migrated. That protocol field is not a reason to author tags on every acceptance scenario. Check the actual failure output before claiming that it prints the row's input values; improving presentation can be separate from test coverage.
- Run controlled healthy and defective adapters to verify that an assertion fails for missing, duplicated, misdirected, or mistyped outputs and for unexpected native throws. Then run the selected cases against a freshly built real SDK adapter in each relevant profile. Controlled hosts prove the harness, not SDK conformance. Keep raw exit codes, diagnostics, selected/not-selected counts, and genuine SDK failures visible.
- Do not expand CI defaults, advance a pinned specs revision or image digest, publish an image, or claim wider conformance as a side effect of adding cases. Coordinate rollout separately after the specs, harness and SDK changes are reviewed and released. Stack follow-on PRs within each repository rather than across repositories, using `gh stack` when a PR stack is requested.
