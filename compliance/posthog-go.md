## Notes

### n1 — Alias (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side flow: "Validate inputs. Both the existing id and the alias target id must be present." The `@both`-tagged acceptance scenario "Alias is dropped when required identities are missing" expects: no event enqueued, and "the SDK should record a validation warning." The spec's own error-handling section does note "some [server SDKs] raise validation errors (for example Ruby and Go validators)" as an acknowledged variation.
- **SDK currently:** `Alias.Validate()` (`alias.go:39-41`) returns a `FieldError` when `Alias`/`DistinctId` is empty; dispatched from `EnqueueWithContext`'s `case Alias:` branch (`posthog.go:593-596`), which returns the error to the caller with no event enqueued and no panic — this satisfies "no event enqueued" and matches the spec's documented Go-as-validator variation for the *first* half. However, no logger warning is ever emitted on this path: `posthog.go:593-596` returns immediately on `Validate()` failure with no call to `c.Warnf`/`c.Errorf` anywhere in that branch (confirmed by reading the full case block). The acceptance scenario's "the SDK should record a validation warning" describes an SDK-internal recorded signal (log line), independent of whatever the caller does with the returned `error` — a caller who ignores the returned error (common in Go when a call is treated as fire-and-forget, as most other `Enqueue` call sites in this SDK's own examples do) would see no diagnostic trace of the drop at all.
- **Backwards compatibility:** Backward-compatible — adding a `c.Warnf("[alias] %s", err)` call alongside the existing `return` on validation failure is purely additive; it doesn't change the returned error or control flow.
- **Remediation:** Add a `c.Warnf(...)` log call in the `Alias` validation-failure path in `EnqueueWithContext` (`posthog.go:593-596`), mirroring the existing `c.Warnf`/`c.Errorf` patterns used elsewhere in the same function (e.g. `posthog.go:521,531`).

### n2 — Before Send Hook (🟡 Partial)
- **Spec requires:** `both` applicability. A `beforeSend(event) -> event | null` hook run before enqueue; mutate or drop (`nil` return); on hook exception, must not crash the caller; spec documents hook chaining via an array of hooks (run in order, stopping the chain on a drop) as a supported pattern, and documents "fall back to the original message" as the majority error-handling pattern for a hook exception.
- **SDK currently:** `Config.BeforeSend` (`config.go:153`) is typed as a single `BeforeSendFunc` (`message.go:40`) — confirmed via full-repo grep that no array/slice-of-hooks variant exists anywhere. `processBeforeSend`/`runBeforeSendHook` (`posthog.go:510-550`) correctly mutate/drop on a `nil` return and wrap the hook invocation in `defer/recover()` so a panicking hook cannot crash the caller (`posthog.go:541-550`, tested by `before_send_test.go:86-93`). Deviation: on a panic, invalid-type return, or an invalidated event, Go **drops the message entirely** (`posthog.go:521,527,531,536`) rather than falling back to the original pre-hook message, which is the pattern the spec documents as the majority behavior (and which posthog-ruby/posthog-node both implement). This is a deliberate, documented design choice (`message.go:30-31` doc comment), not an oversight, but is a real behavioral deviation from the spec's stated common pattern. Hook chaining (array-of-hooks) is entirely unimplemented.
- **Backwards compatibility:** Backward-compatible for chaining — adding an optional `Config.BeforeSendHooks []BeforeSendFunc` (or accepting `BeforeSend` as either a single func or a slice) alongside the existing single-hook field is additive. Needs deprecation path for the panic/invalid-return fallback behavior — changing "drop" to "fall back to original" is an observable behavior change for any integration relying on the current drop semantics (e.g. via monitoring drop counts).
- **Remediation:** Add hook-chaining support via a new `Config` field/type; consider (behind a changelog-flagged behavior change, not silently) falling back to the original message instead of dropping on hook panic/invalid-return, to align with the spec's majority pattern.

### n3 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Enrich events with `distinct_id`/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; run `before_send`; **"Drop silently** on: disabled SDK, opted-out user, empty/invalid event name, invalid distinct id (server)... **Never throw** to the caller under normal operation." Also implies a dynamic, runtime-toggleable opt-out mechanism the `@both`-tagged capture acceptance scenarios can exercise (e.g. "Capture honors opt-out state").
- **SDK currently:** Enrichment is complete and correct: `$lib`/`$lib_version`/`$is_server` (`message.go:66-80`), timestamp/UUID defaulting, `$groups` merge, `before_send` hook invocation (`posthog.go:734-746`), and `DefaultEventProperties` super-property merge (`posthog.go:727`) — all match spec. Validation (`validateCaptureEvent`/`Capture.Validate()`, `capture.go:134-140`) returns a typed `FieldError`/`ConfigError` to the caller rather than throwing/panicking, confirmed by `negative_test.go:22-34` — this is an acceptable Go-specific variation the spec explicitly acknowledges ("Go...raise validation errors"). **Gap:** there is no dynamic, runtime-toggleable opt-out mechanism anywhere — confirmed via grep across `config.go`/`posthog.go` for `OptOut`/`Disabled`/`optout` (case-insensitive): zero matches for any mutable field. The only capture-suppressing state is the permanent, constructor-time `ErrSDKDisabled` path taken when the API key is empty (`posthog.go:245-248`, `noop_posthog.go`) — a static kill-switch set once at construction, not a dynamic per-call opt-out a caller can toggle at runtime. The acceptance scenario "Capture honors opt-out state" (`@both`) has no corresponding API surface to exercise.
- **Backwards compatibility:** Backward-compatible — adding new `OptOutCapturing()`/`OptInCapturing()`/`IsOptedOut()` methods (or an atomic bool field) checked at the top of `EnqueueWithContext`, defaulting to opted-in, is purely additive.
- **Remediation:** Add a dynamic, runtime-mutable opt-out flag and corresponding `OptOutCapturing()`/`OptInCapturing()`/`IsOptedOut()` methods on the `Client` interface, checked early in `EnqueueWithContext` to silently no-op (return nil, no network call) while opted out.

### n4 — Capture Exception (🟡 Partial)
- **Spec requires:** Acceptance feature `capture-exception.feature` is `@both`-tagged. A `$exception` event with flat top-level `$exception_type`/`$exception_message` properties in addition to `$exception_list`; outermost-first/root-cause-last exception-list ordering for chained exceptions; entry-point-first stack frame ordering; `Mechanism.Handled` correctly marked for manual capture; non-standard/malformed inputs must not throw.
- **SDK currently:** Stack-frame ordering is correctly outermost-first: `runtime.Callers` yields innermost-first, explicitly reversed at `error_tracking_stack_trace.go:163-169`, with a dedicated regression test `TestDefaultStackTraceExtractor_CanonicalWireOrder` (`error_tracking_stack_trace_test.go:211-226`) asserting the exact ordering. Validation (`error_tracking.go:190-212`) returns a `FieldError` rather than panicking. Go additionally implements native, platform-specific debug-image extraction for symbolication (Mach-O/`LC_UUID` on Darwin, ELF/`NT_GNU_BUILD_ID`+`/proc/self/maps` on Linux) wired automatically into `NewDefaultException` and the `slog.Handler` adapter — a capability beyond the spec's baseline. **Confirmed gaps:** (1) Go never emits flat `$exception_type`/`$exception_message` properties — grep across `error_tracking.go` confirms only `$exception_list` is populated (`error_tracking.go:144-145`); this directly contradicts the acceptance scenario requiring `$exception_type=TypeError`/`$exception_message=boom` as flat top-level properties. (2) `Mechanism.Handled` is never set to `true` by default on any convenience path (`NewDefaultException`, `SlogCaptureHandler.Handle`) — it stays `nil` unless the caller manually constructs the `ExceptionItem`, contrary to spec's expectation that a manual-capture API marks `handled=true`. (3) Go has no chain-unwrapping helper (no `errors.Unwrap` walk building a multi-item `$exception_list`) — `ExceptionList` ordering for chained causes is entirely caller-controlled with zero SDK enforcement, so the spec's "root-cause-last" ordering requirement is neither enforced nor violated, simply unimplemented as a convenience path.
- **Backwards compatibility:** Backward-compatible — adding `$exception_type`/`$exception_message` (sourced from `ExceptionList[0].Type`/`.Value`) as flat properties, defaulting `Mechanism.Handled = true` in `NewDefaultException`/the slog handler, and adding an opt-in `errors.Unwrap`-chain-building helper are all purely additive.
- **Remediation:** Add flat `$exception_type`/`$exception_message` properties in the `Exception` message's `APIfy()`/enqueue path, sourced from the first entry of `ExceptionList`; default `Mechanism.Handled = true` on the convenience-constructor paths; consider adding an opt-in helper that walks `errors.Unwrap()` to build a correctly-ordered multi-item `$exception_list` for chained errors.

### n5 — Feature Flag Called Tracker (🟡 Partial)
- **Spec requires:** Dedup `$feature_flag_called` by `(flag, value, distinct_id, normalized groups)`; bounded, incremental eviction (capacity pressure "SHOULD NOT clear the entire tracker"); clear fully on shutdown/identity reset. Minimal-event mode: when gated on by the server (`minimalFlagCalledEvents`) and the flag's `has_experiment` is exactly `false`, reduce properties to an allowlist that — per the most recent sdk-specs fix (commit `b59e8b4`, "add session-attribution properties to minimal-event allowlist") — must include 10 session-attribution properties (`$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid`) in addition to the pre-existing core properties, while still excluding `$referrer`.
- **SDK currently:** `minimalFlagCalledEventAllowlist` (`capture.go:187-208`) contains 17 entries (`$feature_flag`, `$feature_flag_response`, `$feature_flag_has_experiment`, `$feature_flag_id`, `$feature_flag_version`, `$feature_flag_reason`, `$feature_flag_request_id`, `$feature_flag_evaluated_at`, `$feature_flag_error`, `locally_evaluated`, `$groups`, `$process_person_profile`, `$geoip_disable`, `$is_server`, `$session_id`, `$window_id`, `$device_id`) but is **missing all 10 of the session-attribution properties** added by sdk-specs commit `b59e8b4` — confirmed by exhaustive case-insensitive grep for `referring_domain|utm_source|utm_medium|utm_campaign|utm_content|utm_term|gad_source|mc_cid|gclid|fbclid` across all non-test `.go` files: zero matches. It does correctly exclude `$referrer`, but that's moot without the offsetting allowlist entries. This gap is locked in by the SDK's own test, `TestMinimalFlagCalledEventProperties_KeepsExactlyAllowlist` (`minimal_flag_called_events_test.go:405-431`), which hardcodes the same pre-fix 17-entry list as the expected/correct allowlist. Separately, `Close()`/`CloseWithContext()` (`posthog.go:1387-1432`) never clear the `distinctIdsFeatureFlagsReported` LRU cache (`posthog.go:199,249`) — grep for `.Purge(` across the entire repo returns zero matches — contradicting the acceptance scenario "Tracker clears on SDK shutdown" (tagged `@both` in `acceptance/private/feature-flag-called-tracker.feature`). Core mechanics are otherwise correct and well-tested: eviction is genuinely incremental (the LRU from `hashicorp/golang-lru/v2` evicts one oldest entry per insert when full — matching "SHOULD NOT clear the entire tracker"), and the dedup key (`flagUser` struct, `posthog.go:209-220`) correctly normalizes group context via `canonicalGroupsRepr` (`posthog.go:1049-1077`, sorted-key JSON encoding) so insertion-order differences don't produce separate dedupe entries; minimization gating correctly fails safe to the full event whenever `has_experiment` is unknown (`nil`) rather than confirmed `false` (`capture.go:226-228`).
- **Backwards compatibility:** Backward-compatible for both fixes — adding entries to an allowlist only retains more data in minimized events (strictly additive); calling `.Purge()` in `CloseWithContext` is a low-risk internal cleanup with no public API impact (a closed client shouldn't be tracking further calls anyway).
- **Remediation:** Add the 10 session-attribution property names from sdk-specs commit `b59e8b4` to `minimalFlagCalledEventAllowlist` in `capture.go`, and update `minimal_flag_called_events_test.go`'s hardcoded expectation accordingly. Separately, call `c.distinctIdsFeatureFlagsReported.Purge()` in `CloseWithContext` (`posthog.go:1401-1432`).

### n6 — Flag Definition Loader (🟡 Partial)
- **Spec requires:** `both`, acceptance file `acceptance/private/flag-definition-loader.feature` tagged `@server` on all scenarios. Fetch/cache local-evaluation flag definitions from a privileged endpoint; ETag-based conditional fetches; a background poll loop; stale-on-failure preservation; quota/auth error handling; external/shared cache-provider integration (sync and async, with fail-safe behavior on provider failure).
- **SDK currently:** Everything except the external cache-provider extension point is implemented and well-tested: privileged auth (`Config.SecretKey`, `config.go:73-127`, gated poller construction `posthog.go:286-303`); dedicated `/flags/definitions` endpoint (`featureflags.go:460-461`); ETag round-trip on both 200 and 304 (`featureflags.go:533-549,588,605`, sent via `If-None-Match` at `featureflags.go:2196-2198`); genuine background poll loop (`go poller.run()`, `featureflags.go:486`, `time.NewTimer`, default `DefaultFeatureFlagsPollingInterval = 5 * time.Minute`, overridable via the public `Config.NextFeatureFlagsPollingTick` hook); stale-on-failure preservation on network errors, non-200/non-304/non-402 statuses, and JSON unmarshal errors (all `return` before mutating `poller.state`, `featureflags.go:524-529,564-567,574-578`); explicit 402/quota handling that clears definitions and ETag (`featureflags.go:551-562`). **Gaps:** (1) no distinct 401/403 handling — these fall into the generic non-200 branch, which is functionally reasonable (spec permits "may clear...or back off") but not the dedicated code path the spec's "Handle quota or auth errors specially" behavior calls out; (2) **no external/shared flag-definition cache-provider extension point exists at all** — exhaustive case-insensitive grep for `cacheprovider`, `flagdefinitioncache`, `externalcache`, `distributedcache` across all `.go` files (source and test) and docs returns zero matches; none of the spec's cache-provider scenarios (sync provider, async provider, store-after-fetch, provider-read-failure fail-safe, provider-shutdown-isolation) have any corresponding implementation, unlike posthog-ruby/php/node/python which all ship a `FlagDefinitionCacheProvider`-style interface for this exact purpose.
- **Backwards compatibility:** Backward-compatible — adding a cache-provider extension point (new optional `Config` field / interface consulted before/after the direct fetch) and distinct 401/403 handling are both purely additive with zero risk to existing callers.
- **Remediation:** Add a `FlagDefinitionCacheProvider`-style interface (fetch-decision, cache-read, store-after-fetch, shutdown-cleanup) to `Config`, consulted by the poller with fail-safe fallback to a direct fetch on provider error, mirroring the sibling SDKs' implementations. Add explicit 401/403 handling distinct from the generic error branch.

### n7 — Flush (🟡 Partial)
- **Spec requires:** `@both`. No-op on empty queue with no network call; bypass batching intervals and drain immediately; acceptance scenario "Flush keeps events retryable when delivery fails": on a 503 (or other retryable failure), the call must not throw, and the failed event "should remain queued for retry."
- **SDK currently:** Go has no single explicit `Flush()` method distinct from `Close()`/the background worker loop, but the worker (`posthog.go:1692-1799`) correctly batches and uploads on count/byte/interval triggers with FIFO order. Both wire pipelines' send loops (`send`, `posthog.go:1513-1577`; `sendV1`, `capture_v1_send.go:54-152`) correctly retry retryable failures in-loop with backoff before giving up, and never propagate a panic/throw to the caller for a normal terminal failure — satisfying "must not throw." However, once a batch's own bounded retry budget is exhausted, **both pipelines permanently drop the batch** with no re-enqueue to any queue/channel: the legacy path logs "%d messages dropped after %d attempts" and calls `c.notifyFailure(pb.msgs, err)` with no requeue (`posthog.go:1575-1576`); the v1 path's `dropMessages` helper does the same (`capture_v1_send.go:99-102,116-125,137-140,222-227`), confirmed by `TestV1SendMaxAttemptsExhaustion` (`capture_v1_send_test.go:461-482`) recording exactly one failure and zero successes after exhaustion. This directly contradicts "the event...should remain queued for retry" once a batch's local retry budget (not just a single attempt) is exhausted.
- **Backwards compatibility:** Breaking — re-enqueueing failed batches after retry-budget exhaustion changes delivery/ordering semantics (potential duplicate-send risk, unbounded-queue-growth risk during a sustained outage) not currently guarded against; should ship as an explicit opt-in mode rather than a silent default-behavior change.
- **Remediation:** On terminal (post-retry-budget) failure in `send`/`sendV1`, re-enqueue the batch's messages back onto the internal queue (respecting `MaxQueueSize`) instead of unconditionally dropping them, ideally gated behind an opt-in flag given the current drop-on-exhaustion behavior is the long-standing default.

### n12 — Is Feature Enabled (❌ Fail)
- **Spec requires:** Hard `SHALL`, `@both`, no server-SDK carve-out: "The SDK SHALL accept a caller-supplied boolean default (`defaultValue`...) and SHALL return it whenever the flag has no value: flags not loaded yet, a failed flags request, or no flag with that key in the loaded flags. A flag that has a value — including `false` and variant strings — always wins over the caller-supplied default."
- **SDK currently:** `IsFeatureEnabled(flagConfig FeatureFlagPayload) (interface{}, error)` (`posthog.go:79`, impl `posthog.go:792-803`) delegates to `GetFeatureFlag`, which delegates to `GetFeatureFlagResult`. The `FeatureFlagPayload` struct (`feature_flag_config.go:6-24`) has fields `Key, DistinctId, DeviceId, Groups, PersonProperties, GroupProperties, OnlyEvaluateLocally, SendFeatureFlagEvents` — **no `DefaultValue`/`Default` field anywhere.** On a missing/unknown flag, `GetFeatureFlag` unconditionally returns `(false, nil)` via the `ErrFlagNotFound` branch (`posthog.go:836-838`), with no way for a caller to make a miss resolve to a caller-chosen `true`. The newer canonical path, `FeatureFlagEvaluations.IsEnabled(key string) bool` (`feature_flag_evaluations.go:72-82`), takes only a `key` argument and hardcodes `return false` for an unknown flag (lines 79-80) — also no default-value parameter. Neither the legacy nor the canonical API satisfies the spec's default-value contract; both collapse "known false" and "unknown/missing" to the identical `false` result with no caller-supplied override. This mirrors the identical, independently-confirmed gap in posthog-ruby, posthog-php, and posthog-node.
- **Backwards compatibility:** Backward-compatible — adding an optional `DefaultValue *bool` field to `FeatureFlagPayload` (consulted only on the missing-flag path, preserving today's `false` fallback when the field is nil) and an optional second parameter to `FeatureFlagEvaluations.IsEnabled` are both purely additive; existing callers who don't set/pass them see identical behavior.
- **Remediation:** Add `DefaultValue *bool` to `FeatureFlagPayload`, returned (when non-nil) instead of the current unconditional `false` on a miss in `GetFeatureFlag`/`GetFeatureFlagResult`. Add an equivalent optional default parameter to `FeatureFlagEvaluations.IsEnabled`.

### n15 — Retry Queue (🟡 Partial)
- **Spec requires:** `both`. In-memory queue with backpressure/drop-when-full and a capacity warning; classify retryable (network errors, 5xx, 408, 429) vs. non-retryable (other 4xx) failures; retryable failures keep the same events queued for a later, separate flush attempt; success removal by stable identity, not index, so events captured concurrently while a batch is in flight are not mistaken for the just-sent batch and dropped.
- **SDK currently:** Legacy pipeline's `isRetryableStatus` (`posthog.go:1656-1666`) classifies all `>=500`, `408`, and `429` as retryable — an exact spec match. The v1 pipeline's `isRetryableStatusV1` (`capture_v1_send.go:41-48`) retries only `408/500/502/503/504` — **429 is treated as non-retryable/terminal in v1**, both a direct spec deviation and an inconsistency between Go's own two pipelines (confirmed by `capture_v1_send_test.go:403-433`). Backpressure: the pre-batch `msgs` channel drops the *new* incoming message non-blocking when full (`posthog.go:585-589`, confirmed by `queue_overflow_test.go:37-79`) — spec-permitted; the post-batch `batches` channel blocks up to `BatchSubmitTimeout` (default 100ms) then drops (`posthog.go:1460-1489`). **Gap:** on overflow, no capacity warning is logged/emitted anywhere — `queue_overflow_test.go:74-78` explicitly asserts **no** warning/log/callback fires on drop, only a returned `ErrQueueFull` to the immediate caller, contradicting the spec's capacity-warning expectation for a sustained-overload scenario nobody is actively checking return values for. Success removal by stable identity (not index) is correctly implemented in the v1 pipeline via a UUID-keyed map (`capture_v1.go:157-165`, `capture_v1_send.go:157-181`, confirmed by `TestV1SendPartialRetryResendsOnlyRetrySubset`); the legacy pipeline has no partial-batch concept (whole-batch retry only), so index-vs-identity confusion cannot arise there either. The same retry-budget-exhaustion batch-drop issue documented under Flush (n7) applies here too — contradicting "retryable failures keep the same events queued for a later attempt" once a batch's local retry budget is spent.
- **Backwards compatibility:** Backward-compatible to add a capacity-warning log call on drop (additive, no behavior change to the drop itself) and to align v1's retryable-status set with the legacy pipeline's (429 retryable) — though the latter changes v1's current terminal-failure timing for 429 responses specifically, worth a changelog callout. The exhausted-retry batch-loss issue needs the same careful opt-in fix described under n7.
- **Remediation:** Add a `c.Warnf`/similar log call on queue-full drop in `EnqueueWithContext`/`sendBatch`. Add `429` to `isRetryableStatusV1`'s retryable set in `capture_v1_send.go`. Apply n7's re-enqueue-on-exhaustion fix to both pipelines.
