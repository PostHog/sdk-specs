## Notes

### n1 — Alias (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side flow: "Validate inputs. Both the existing id and the alias target id must be present." The `@both`-tagged acceptance scenario "Alias is dropped when required identities are missing" expects: no event enqueued, and "the SDK should record a validation warning." The spec's own error-handling section does note "some [server SDKs] raise validation errors (for example Ruby and Go validators)" as an acknowledged variation.
- **SDK currently:** `Alias.Validate()` (`alias.go:39-41`) returns a `FieldError` when `Alias`/`DistinctId` is empty; dispatched from `EnqueueWithContext`'s `case Alias:` branch (`posthog.go:593-596`), which returns the error to the caller with no event enqueued and no panic — this satisfies "no event enqueued" and matches the spec's documented Go-as-validator variation for the *first* half. However, no logger warning is ever emitted on this path: `posthog.go:593-596` returns immediately on `Validate()` failure with no call to `c.Warnf`/`c.Errorf` anywhere in that branch (confirmed by reading the full case block). The acceptance scenario's "the SDK should record a validation warning" describes an SDK-internal recorded signal (log line), independent of whatever the caller does with the returned `error` — a caller who ignores the returned error (common in Go when a call is treated as fire-and-forget, as most other `Enqueue` call sites in this SDK's own examples do) would see no diagnostic trace of the drop at all.
- **Backwards compatibility:** Backward-compatible — adding a `c.Warnf("[alias] %s", err)` call alongside the existing `return` on validation failure is purely additive; it doesn't change the returned error or control flow.
- **Remediation:** Add a `c.Warnf(...)` log call in the `Alias` validation-failure path in `EnqueueWithContext` (`posthog.go:593-596`), mirroring the existing `c.Warnf`/`c.Errorf` patterns used elsewhere in the same function (e.g. `posthog.go:521,531`).

### n2 — Before Send Hook (🟡 Partial)
- **Spec requires:** `both` applicability. A `beforeSend(event) -> event | null` hook run before enqueue; mutate or drop (`nil` return); on hook exception, must not crash the caller; spec documents hook chaining via an array of hooks (run in order, stopping the chain on a drop) as a supported pattern, and documents "fall back to the original message" as the majority error-handling pattern for a hook exception.
- **SDK currently:** `Config.BeforeSend` (`config.go:153`) is typed as a single `BeforeSendFunc` (`message.go:40`) — confirmed via full-repo grep that no array/slice-of-hooks variant exists anywhere. `processBeforeSend`/`runBeforeSendHook` (`posthog.go:510-550`) correctly mutate/drop on a `nil` return and wrap the hook invocation in `defer/recover()` so a panicking hook cannot crash the caller (`posthog.go:541-550`, tested by `before_send_test.go:86-93`). Deviation: on a panic, invalid-type return, or an invalidated event, Go **drops the message entirely** (`posthog.go:521,527,531,536`) rather than falling back to the original pre-hook message, which is the pattern the spec documents as the majority behavior (and which posthog-ruby/posthog-node both implement). This is a deliberate, documented design choice (`message.go:30-31` doc comment), not an oversight, but is a real behavioral deviation from the spec's stated common pattern. Hook chaining (array-of-hooks) is entirely unimplemented.
- **Backwards compatibility:** Backward-compatible for chaining — adding an optional `Config.BeforeSendHooks []BeforeSendFunc` (or accepting `BeforeSend` as either a single func or a slice) alongside the existing single-hook field is additive. Needs deprecation path for the panic/invalid-return fallback behavior — changing "drop" to "fall back to original" is an observable behavior change for any integration relying on the current drop semantics (e.g. via monitoring drop counts).
- **Remediation:** Add hook-chaining support via a new `Config` field/type; consider (behind a changelog-flagged behavior change, not silently) falling back to the original message instead of dropping on hook panic/invalid-return, to align with the spec's majority pattern.

### n3 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Enrich events with `distinct_id`/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; run `before_send`; **"Drop silently** on: disabled SDK, opted-out user, empty/invalid event name, invalid distinct id (server)... **Never throw** to the caller under normal operation." Also implies a dynamic, runtime-toggleable opt-out mechanism the `@both`-tagged capture acceptance scenarios can exercise (e.g. "Capture honors opt-out state").
- **SDK currently:** Enrichment is complete and correct: `$lib`/`$lib_version`/`$is_server` (`message.go:66-80`), timestamp/UUID defaulting, `$groups` merge, `before_send` hook invocation (`posthog.go:734-746`), and `DefaultEventProperties` super-property merge (`posthog.go:727`) — all match spec. Validation (`validateCaptureEvent`/`Capture.Validate()`, `capture.go:134-140`) returns a typed `FieldError`/`ConfigError` to the caller rather than throwing/panicking, confirmed by `negative_test.go:22-34` — this is an acceptable Go-specific variation the spec explicitly acknowledges ("Go...raise validation errors"). **Gap:** there is no dynamic, runtime-toggleable opt-out mechanism anywhere — confirmed via grep across `config.go`/`posthog.go` for `OptOut`/`Disabled`/`optout` (case-insensitive): zero matches for any mutable field. The only capture-suppressing state is the permanent, constructor-time `ErrSDKDisabled` path taken when the API key is empty (`posthog.go:245-248`, `noop_posthog.go`) — a static kill-switch set once at construction, not a dynamic per-call opt-out a caller can toggle at runtime. The acceptance scenario "Capture honors opt-out state" (`@both`) has no corresponding API surface to exercise.
- **Backwards compatibility:** Backward-compatible — adding new `OptOutCapturing()`/`OptInCapturing()`/`IsOptedOut()` methods (or an atomic bool field) checked at the top of `EnqueueWithContext`, defaulting to opted-in, is purely additive.
- **Remediation:** Add a dynamic, runtime-mutable opt-out flag and corresponding `OptOutCapturing()`/`OptInCapturing()`/`IsOptedOut()` methods on the `Client` interface, checked early in `EnqueueWithContext` to silently no-op (return nil, no network call) while opted out.

### n4 — Capture Exception (🟡 Partial)
- **Spec requires:** Acceptance feature `capture-exception.feature` is `@both`-tagged. A `$exception` event whose canonical type and message are `$exception_list[0].type`/`.value` (#103 made `$exception_list[0]` canonical, so flat top-level `$exception_type`/`$exception_message` are not required); outermost-first/root-cause-last exception-list ordering for chained exceptions; entry-point-first stack frame ordering; `Mechanism.Handled` correctly marked for manual capture; non-standard/malformed inputs must not throw.
- **SDK currently:** Stack-frame ordering is correctly outermost-first: `runtime.Callers` yields innermost-first, explicitly reversed at `error_tracking_stack_trace.go:163-169`, with a dedicated regression test `TestDefaultStackTraceExtractor_CanonicalWireOrder` (`error_tracking_stack_trace_test.go:211-226`) asserting the exact ordering. Validation (`error_tracking.go:190-212`) returns a `FieldError` rather than panicking. Go additionally implements native, platform-specific debug-image extraction for symbolication (Mach-O/`LC_UUID` on Darwin, ELF/`NT_GNU_BUILD_ID`+`/proc/self/maps` on Linux) wired automatically into `NewDefaultException` and the `slog.Handler` adapter — a capability beyond the spec's baseline. **Confirmed gaps:** (1) `Mechanism.Handled` is never set to `true` by default on any convenience path (`NewDefaultException`, `SlogCaptureHandler.Handle`) — it stays `nil` unless the caller manually constructs the `ExceptionItem`, contrary to spec's expectation that a manual-capture API marks `handled=true`. (2) Go has no chain-unwrapping helper (no `errors.Unwrap` walk building a multi-item `$exception_list`) — `ExceptionList` ordering for chained causes is entirely caller-controlled with zero SDK enforcement, so the spec's "root-cause-last" ordering requirement is neither enforced nor violated, simply unimplemented as a convenience path.
- **Backwards compatibility:** Backward-compatible — defaulting `Mechanism.Handled = true` in `NewDefaultException`/the slog handler, and adding an opt-in `errors.Unwrap`-chain-building helper are all purely additive.
- **Remediation:** Default `Mechanism.Handled = true` on the convenience-constructor paths; consider adding an opt-in helper that walks `errors.Unwrap()` to build a correctly-ordered multi-item `$exception_list` for chained errors.

### n5 — Evaluate Flags (🟡 Partial)
- **Spec requires:** `server`. A snapshot API that resolves identity from the call or request context; distinguishes an omitted key list from an explicitly empty one (empty = return an empty snapshot with no cache read, no local evaluation, no remote request); scopes local and remote work to a non-empty key list; makes **at most one** direct `/flags` request per call; never lets a remote fallback overwrite a locally resolved value; returns a safe empty snapshot for a missing identity or disabled SDK and a *partial* snapshot when remote evaluation fails after some records resolved. Payload access must be silent and must **validate serialized payloads as JSON**, logging and returning the absent-payload sentinel for malformed/empty/whitespace-only JSON rather than the raw string. It also requires **retained negative knowledge**: after a clean remote fallback omits a requested key with no local definition, the SDK must remember that omission in a finite-capacity in-memory store, skip re-probing while the knowledge is valid, clear it after every successful definitions refresh, and coordinate concurrent evaluations that overlap on the same unknown key. The runtime criterion on the snapshot filter (reshaped by PR [#77](https://github.com/PostHog/sdk-specs/pull/77) into the only runtime surface) is a `MAY`.
- **SDK currently:** The core snapshot API is well built and matches the spec on most points. `evaluateFlagsWithContext` (`posthog.go:1196-1305`) resolves the distinct id from `RequestContextFromContext` when the payload omits it (`posthog.go:1200-1205`), returns `noopFeatureFlagEvaluations` + `ErrNoDistinctID` when neither supplies one (`posthog.go:1207-1210`), and distinguishes nil from empty correctly — `payload.FlagKeys != nil && len(payload.FlagKeys) == 0` short-circuits to an empty snapshot before any cache read, local evaluation, or request (`posthog.go:1217-1226`), exactly the "empty key list is a no-op" scenario. There is structurally **one** `makeFlagsRequest` call site per evaluation (`posthog.go:1260-1268`), locally evaluated keys are skipped when merging the remote response (`if _, alreadyLocal := locallyEvaluated[key]; alreadyLocal { continue }`, `posthog.go:1285-1287`), out-of-scope remote keys are dropped against `requestedFlagKeys` (`posthog.go:1276-1284`), quota-limited responses contribute no records (`posthog.go:1273`), and a remote failure returns the locally resolved records alongside `remoteErr` rather than discarding them (`posthog.go:1258-1271,1296-1305`) — the partial-snapshot requirement. `Only(keys)` warns on unknown requested keys (`feature_flag_evaluations.go:160-176`) and `OnlyAccessed()` intersects with present flags, so both in-memory filters are conformant and side-effect-free. **Two confirmed gaps.** (1) **No negative-knowledge retention or probe coordination of any kind.** Exhaustive grep for `missingKey`, `negativeKnowledge`, `probe`, `generation`, `notFound`, `absent` across `posthog.go`, `featureflags.go`, `flags.go`, and `feature_flag_evaluations.go` returns zero matches for any such store; there is no definitions-generation counter and no in-flight-probe map. A requested key that exists in neither the local definitions nor a clean `/flags` response therefore triggers a fresh fallback request on **every** subsequent `EvaluateFlags` call for that scope, forever, and two concurrent evaluations missing the same key both issue their own request. This is the identical gap confirmed in posthog-php and posthog-ruby on 2026-09-28 — Go is the third server SDK in a row with it. (2) **Snapshot payload access performs no JSON validation.** `GetFlagPayload` (`feature_flag_evaluations.go:109-118`) returns `*flag.Payload` verbatim and returns `""` only when the pointer is nil; grep confirms no `json.Valid`/`json.Unmarshal` on any snapshot read path. A malformed, empty, or whitespace-only serialized payload is handed to the caller as the raw string, which the spec's `Scenario Outline: Snapshot payload reads reject malformed JSON` forbids for both the local- and remote-evaluation sources, and nothing is logged. The optional runtime criterion is absent (no `evaluation_runtime` symbol anywhere) — permitted, since PR [#77](https://github.com/PostHog/sdk-specs/pull/77) left the whole runtime surface a `MAY`.
- **Backwards compatibility:** Backward-compatible for both. A negative-knowledge store is new internal state behind the existing call signature, and it strictly *removes* requests rather than changing any returned value. ### n9 — Flush (🟡 Partial, materially improved since 2026-08-06)
- **Spec requires:** `@both`. No-op on empty queue with no network call; bypass batching intervals and drain immediately; acceptance scenario "Flush keeps events retryable when delivery fails": on a 503 (or other retryable failure), the call must not throw, and the failed event "should remain queued for retry."
- **SDK currently:** **The missing-public-API half of the last audit's finding is fixed.** PR [#324](https://github.com/PostHog/posthog-go/pull/324) added a real, caller-invokable `Flush()`/`FlushWithContext(ctx)` (`flush.go:5-42`): it returns `ErrClosed` on a closed client, honors context cancellation at every step, hands the worker a reply channel and then **blocks on the `done` channels of exactly the uploads that were pending when the request was made** — so it drains immediately rather than waiting for the batch interval, and it is a genuine no-op (no network call) when nothing is queued. - **Spec requires:** `server`, brand new (PR [#87](https://github.com/PostHog/sdk-specs/pull/87), merged this cycle), and it names Go's packages explicitly in its applicability table: `posthogmcp` (manual API) and `posthogmcpsdk` (go-sdk adapter). Observer-only one-call instrumentation whose failures never reach the handler or the client; exactly one `$mcp_tool_call` per final outcome with required `$mcp_tool_name`/`$mcp_is_error`/`$mcp_duration_ms`/`$mcp_source`/`$session_id`/`timestamp`; failure capture with a low-cardinality `$mcp_error_type` and a sanitized `$mcp_error_message`; a cross-SDK-deterministic `$session_id` derivation; `$process_person_profile: false` for anonymous calls; client/server identity; injected `context`/`llm_model`/`conversation_id` arguments kept out of `$mcp_parameters`; bounded per-session state; a 102,400-byte event bound with a normative shrink order; and `$lib`/`$lib_version` naming the MCP instrumentation. When it emits `$exception` alongside a failed call, that event must follow `exception-event-metadata` with `$exception_source: "mcp.tool_call"`, `mechanism.handled: true`, `mechanism.synthetic: true` **only for an `isError` result that carried no thrown error**, the thrown error's own type (never the explicit label), `$exception_level: "error"`, and the call's `$session_id` and `$mcp_tool_name`. `$mcp_input_required` and `$mcp_unknown_tool` are `SHOULD`s; `$mcp_tools_list`, the `send_feedback` virtual tool, `$mcp_server_build`, `$mcp_error_status`, `$mcp_input_keys`, and `$mcp_input_aliases_used` are `MAY`s.
- **SDK currently:** A genuinely strong first implementation — Go is one of the three SDKs the spec names, and the great majority of the contract is implemented and tested. The cross-SDK `$session_id` derivation is **exact**: `deriveSessionID` is `"ses_" + H(x) + H(x + "::salt")` with two 32-bit FNV-1a lanes over runes, seeds `0x84222325`/`0xcbf29ce4` and primes `0x1b3`/`0x193` (`posthogmcp/session.go:21-38`), duplicated identically in the adapter (`posthogmcpsdk/sessions.go:105-120`) with a comment explaining the rune-vs-UTF-16-unit equivalence. Conversation handles are accepted only in UUIDv7 shape and lowercased (`posthogmcp/session.go:11-19`); unanchored calls mint `ses_<UUIDv7>` (`session.go:40-44`). Per-session state is bounded exactly as the spec asks — `maxGeneratedSessions = 1024` with LRU-style `evictOldest`, plus a 30-minute inactivity rotation and a periodic `sweep` (`posthogmcpsdk/sessions.go:11-103`) — and a request-scoped (stateless HTTP) session is deliberately never remembered. The required properties are all present (`posthogmcp/constants.go:5-37`, `event.go:272`), `$mcp_source` is the literal `posthog_mcp_analytics`, `$mcp_session_id` is correctly **not** emitted, the size bound is the spec's 102,400 bytes with staged shrinking of `$mcp_response`/`$mcp_parameters` before other properties (`constants.go:43-58`, `event.go:69-83`, `exception.go:110-130`), `$process_person_profile` is suppressed for an unresolved identity (`event.go:76-78`), `$lib` is `posthog-go-mcp` (`constants.go:39`), injected argument names are stripped before the handler and excluded from `$mcp_parameters` (`posthogmcpsdk/arguments.go:14-59`), and tools whose root schema uses `$ref`/`allOf`/`anyOf`/`oneOf` are skipped (`posthogmcpsdk/tools.go:318-337`). `$mcp_error_type` falls back to the error's real Go type looking past `errors.errorString`/`fmt.wrapError`-style wrappers (`posthogmcp/error_type.go:11-46`), and both `SHOULD` optional events (`$mcp_unknown_tool`, `$mcp_input_required`) ship. **Three confirmed gaps, all on the `$exception` side-car and the intent source.** (1) **`$exception_source: "mcp.tool_call"` is never set.** `buildException` (`posthogmcp/exception.go:84-110`) sets `$exception_level`, `$session_id`, `$mcp_conversation_id`, tool/server/client identity — but there is no `$exception_source` constant in the package at all (`grep -n exception_source posthogmcp/*.go`: zero matches), so the required provenance value is absent. (2) **`mechanism.synthetic` is inverted.** `buildException` hardcodes `synthetic := true` (`exception.go:85-96`), yet it is only ever reached for a **thrown** error — `buildToolCallMessages` gates it on `call.Error != nil` (`event.go:44-51`) — which is precisely the case the spec says is *not* synthetic. The SDK has the information needed to get this right: `ToolCall` distinguishes `IsError bool` (an `isError` result with no Go error) from `Error error` (`tool_call.go:101-106`). The net effect is that every MCP `$exception` Go emits is mislabelled as instrumentation-synthesized, and no `$exception` is emitted for an `isError` result, which the spec permits. (3) **No `client_metadata` intent source.** The `IntentSource` type declares only `context_parameter` and `inferred` (`tool_call.go:13-18`), and `prepareToolCall` returns `errors.New("posthogmcp: invalid IntentSource")` for anything else (`event.go:68-72`) — so the spec's `SHOULD` to prefer a standardized `_meta` intent (`io.modelcontextprotocol/aiInvocation` `userIntent`) with `$mcp_intent_source: "client_metadata"` is not merely unimplemented, the manual API actively rejects the value a caller would pass for it. Separately, `prepareToolCall` rejects a negative `Duration` with an error (`event.go:65-67`) where the spec says a caller-supplied duration "is clamped to 0"; this only affects the lower-level manual entry point, which the spec exempts from matching automatic instrumentation, so it is noted rather than scored. Every `MAY` is absent (`$mcp_tools_list`, `send_feedback`, `$mcp_server_build`, `$mcp_error_status`, `$mcp_input_keys`, `$mcp_input_aliases_used`) — permitted, and not counted against this row.
- **Backwards compatibility:** Backward-compatible for all three. Adding `$exception_source` is a new property on an event the SDK already builds. Conditioning `synthetic` on `call.Error == nil` corrects a value that is wrong on every event today, so no consumer can be relying on it being right. Adding an `IntentSourceClientMetadata` constant widens an accepted enum — today's two values keep working, and the adapter can start preferring `_meta` without any caller change.
- **Remediation:** Add a `propertyExceptionSource = "$exception_source"` constant and set it to `"mcp.tool_call"` in `buildException` (`posthogmcp/exception.go:84-110`). Change `synthetic := true` to `synthetic := p.call.Error == nil`, and consider emitting `$exception` for `isError` results so the synthetic branch is actually reachable. Add `IntentSourceClientMetadata IntentSource = "client_metadata"` to `posthogmcp/tool_call.go`, accept it in `prepareToolCall`'s validation, and read `io.modelcontextprotocol/aiInvocation.userIntent` from request `_meta` in `posthogmcpsdk/middleware.go` ahead of the `context` argument. Clamp a negative `Duration` to zero instead of erroring.

### n18 — Set/Reset Person/Group Properties For Flags (❌ Fail, all four contracts)
- **Spec requires:** Each of these four specs' own `## Applicability` line says `client` ("Server SDKs usually take person/group properties directly on each flag-evaluation call instead of maintaining a persistent local override store"). However, all four acceptance feature files (`set-person-properties-for-flags.feature`, `set-group-properties-for-flags.feature`, `reset-person-properties-for-flags.feature`, `reset-group-properties-for-flags.feature`) are tagged `@both` at the feature level and on every individual scenario, with concrete, generically-written scenarios that make no client-only assumption and are mechanically satisfiable server-side. Per this matrix's established precedent (weighting acceptance-tag precision over stale spec prose — the same treatment already applied to posthog-python, posthog-php, posthog-ruby, posthog-node, posthog-java, and posthog-dotnet for these exact four contracts), these are scored as in-scope-but-unimplemented, not N/A.
- **SDK currently:** `grep -rni "PropertiesForFlags"` across the entire repository returns zero matches for all four. Every flag-evaluation call (`GetFeatureFlag`, `GetAllFlags`, `EvaluateFlags`, etc.) takes `PersonProperties`/`GroupProperties` directly as per-call struct fields (`feature_flag_config.go`, `feature_flag_evaluations.go`) — the spec's own documented server-side *alternative*, but architecturally distinct from a *persistent* override store that automatically applies to all subsequent evaluation calls without the caller re-passing it every time, which is what the acceptance scenarios test. There is no persistent override cache and no `SetPersonPropertiesForFlags`/`SetGroupPropertiesForFlags`/`ResetPersonPropertiesForFlags`/`ResetGroupPropertiesForFlags` method anywhere in the SDK.
- **Backwards compatibility:** Backward-compatible — a new opt-in stateful override store (e.g. scoped to the existing `request_context.go` per-request context mechanism) would be purely additive; no existing call signature needs to change.
- **Remediation:** Add `SetPersonPropertiesForFlags()`/`SetGroupPropertiesForFlags()`/`ResetPersonPropertiesForFlags()`/`ResetGroupPropertiesForFlags()`, backed by a context-scoped override store consulted as a default by flag-evaluation call sites, mergeable with (and overridable by) explicit per-call properties. Also worth flagging upstream to sdk-specs maintainers: the spec-prose `Applicability: client` and the acceptance files' `@both` tags are inconsistent and should be reconciled SDK-wide.

### n19 — Retry Queue (🟡 Partial)
- **Spec requires:** `both`. In-memory queue with backpressure/drop-when-full and a capacity warning; classify retryable (network errors, 5xx, 408, 429) vs. non-retryable (other 4xx) failures; retryable failures keep the same events queued for a later, separate flush attempt; success removal by stable identity, not index, so events captured concurrently while a batch is in flight are not mistaken for the just-sent batch and dropped.
- **SDK currently:** Legacy pipeline's `isRetryableStatus` (`posthog.go:1656-1666`) classifies all `>=500`, `408`, and `429` as retryable — an exact spec match. The v1 pipeline's `isRetryableStatusV1` (`capture_v1_send.go:41-48`) retries only `408/500/502/503/504` — **429 is treated as non-retryable/terminal in v1**, both a direct spec deviation and an inconsistency between Go's own two pipelines (confirmed by `capture_v1_send_test.go:403-433`). Backpressure: the pre-batch `msgs` channel drops the *new* incoming message non-blocking when full (`posthog.go:585-589`, confirmed by `queue_overflow_test.go:37-79`) — spec-permitted; the post-batch `batches` channel blocks up to `BatchSubmitTimeout` (default 100ms) then drops (`posthog.go:1460-1489`). **Gap:** on overflow, no capacity warning is logged/emitted anywhere — `queue_overflow_test.go:74-78` explicitly asserts **no** warning/log/callback fires on drop, only a returned `ErrQueueFull` to the immediate caller, contradicting the spec's capacity-warning expectation for a sustained-overload scenario nobody is actively checking return values for. Success removal by stable identity (not index) is correctly implemented in the v1 pipeline via a UUID-keyed map (`capture_v1.go:157-165`, `capture_v1_send.go:157-181`, confirmed by `TestV1SendPartialRetryResendsOnlyRetrySubset`); the legacy pipeline has no partial-batch concept (whole-batch retry only), so index-vs-identity confusion cannot arise there either. The same retry-budget-exhaustion batch-drop issue documented under Flush (n7) applies here too — contradicting "retryable failures keep the same events queued for a later attempt" once a batch's local retry budget is spent.
- **Backwards compatibility:** Backward-compatible to add a capacity-warning log call on drop (additive, no behavior change to the drop itself) and to align v1's retryable-status set with the legacy pipeline's (429 retryable) — though the latter changes v1's current terminal-failure timing for 429 responses specifically, worth a changelog callout. The exhausted-retry batch-loss issue needs the same careful opt-in fix described under n7.
- **Remediation:** Add a `c.Warnf`/similar log call on queue-full drop in `EnqueueWithContext`/`sendBatch`. Add `429` to `isRetryableStatusV1`'s retryable set in `capture_v1_send.go`. Apply n7's re-enqueue-on-exhaustion fix to both pipelines.

### n20 — Traces (❌ Fail)
- **Spec requires:** A `startSpan`/`withSpan` API producing OTLP spans shipped to `POST {host}/i/v1/traces`, independent of LLM-analytics-as-events, requiring no OpenTelemetry runtime dependency.
- **SDK currently:** No implementation exists. Exhaustive grep for `startSpan`, `withSpan`, `/i/v1/traces`, `resourceSpans`, `scopeSpans`, `span_id`, `trace_id` across the entire repository returns zero matches anywhere.
- **Backwards compatibility:** Backward-compatible — a net-new, additive subsystem.
- **Remediation:** Implement a dependency-free span-handle API (`SetAttribute`/`AddEvent`/`SetStatus`/`RecordException`/`End`) plus `StartSpan`/`WithSpan`, an in-memory buffered span batch, and a `/i/v1/traces` transport, reusing the existing batching/HTTP-client machinery.

### n21 — Tracing Headers (✅ Pass)
- **Spec requires:** `both` applicability. Request-scoped middleware/context extracting `X-PostHog-Distinct-Id`/`X-PostHog-Session-Id` case-insensitively; sanitize (trim/strip control chars/cap length); explicit call-site values take precedence over context; personless-capture fallback (random `distinct_id` + `$process_person_profile=false`) when no identity is resolvable anywhere, unless the caller already set that property explicitly; feature-flag evaluation must no-op (no network call, no `$feature_flag_called`) when no identity is resolvable anywhere; per-request isolation; headers never used for auth; panic-safe request middleware.
- **SDK currently:** This is a comprehensive, best-in-class implementation, fully covered by `request_context.go` (781 lines) and `request_context_test.go` (625 lines). Case-insensitive header extraction: `ExtractRequestContext` (`request_context.go:209-232`) uses `http.Header.Get`, which Go's `net/http` canonicalizes case-insensitively. Sanitization: `sanitizeRequestContextValue` (`request_context.go:329-352`) trims, strips control characters, and caps at `maxRequestContextValueLength = 1000` runes (`request_context.go:33`), tested at `request_context_test.go:269-291`. Explicit-value precedence: `resolveCaptureContext`/`mergeContextProperties` (`request_context.go:241-300`) only fall back to context when the explicit value is empty, and apply explicit properties last so they win on conflict, tested at `request_context_test.go:51-78`. Personless fallback: generates a random UUID and sets `$process_person_profile=false` only when neither an explicit nor a context distinct id is resolvable, and only when request context exists at all — a plain `Enqueue()` (no context) with no `DistinctId` still returns the pre-existing "distinct ID required" `FieldError` rather than silently going personless, matching the spec's requirement that this fallback is context-gated, not universal (`request_context.go:241-276`, tested `request_context_test.go:80-125,206-213,331-351`). Feature-flag no-op: `EvaluateFlags`/`EvaluateFlagsWithContext` (`posthog.go:1155-1254`) consult `RequestContextFromContext` when `DistinctId` is empty and return a no-op `noopFeatureFlagEvaluations` snapshot plus `ErrNoDistinctID` with **no** network call when neither payload nor context supplies an id (`posthog.go:1167-1178`) — matching the private acceptance scenario "Server feature flag evaluation without explicit or context distinct id is empty." (Note: the older, `Deprecated`-labeled single-flag getters `IsFeatureEnabled`/`GetFeatureFlag`/`GetFeatureFlagResult`/`GetAllFlags` do not take a `context.Context` and so cannot consult request context at all — this is documented, intentional API evolution toward `EvaluateFlags`, not an unaddressed gap in the currently-recommended API.) Per-request isolation is real: `WithFreshRequestContext`/`NewRequestContextMiddleware` create a fresh `context.WithValue` scope per request, verified under concurrency by `request_context_test.go:293-329`. Headers are never used for authentication anywhere in the codebase. `WithCapturePanics` additionally implements spec-adjacent panic autocapture that correctly re-panics with the original value after capturing (`request_context.go:188-200,445-450`, tested `request_context_test.go:381-503`), going beyond the spec's baseline. No gaps found against this spec's requirements for the currently-recommended API surface.
