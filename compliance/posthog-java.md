**Repo:** [PostHog/posthog-android](https://github.com/PostHog/posthog-android) — `posthog-server/` subdirectory (the standalone `PostHog/posthog-java` repo is archived; its Java/Kotlin server SDK now lives here, package `com.posthog.server`)

**A note on repo layout:** The standalone `PostHog/posthog-java` GitHub repository is archived; its README redirects to `posthog-android`, at `posthog-android/tree/main/posthog-server`. This audit clones the `posthog-android` monorepo (commit above) and inspects `posthog-server/src/main/java/com/posthog/server/` (public surface: `PostHog.kt`/`PostHogInterface.kt`, `PostHogConfig.kt`, `PostHogRequestContext.kt`, `PostHogFeatureFlagEvaluations.kt`, plus `internal/` for the local-evaluation engine, flag-definition poller, evaluated-flag-value cache, and in-memory event queue) alongside its declared Gradle dependency `api(project(":posthog"))` — a shared core module at `posthog/src/main/java/com/posthog/` also used by `posthog-android` (the mobile client SDK, audited separately in this matrix at the same commit). `posthog-server`'s `PostHog` class extends the core's `PostHogStateless` base class rather than the richer client-only `PostHog` base class used by `posthog-android` — so most client-only ambient-identity/session/replay/consent primitives (`reset()`, `register()`/`unregister()`, `getAnonymousId()`, `getSessionId()`, session replay, surveys, bootstrap, autocapture, screen views, opt-in/opt-out) simply aren't exposed on the server class at all, mirroring the same architectural split found in posthog-node's `PostHogCoreStateless` vs. `PostHogCore`. This is a genuinely server-side SDK: stateless per call except for an explicit, opt-in `PostHogRequestContext` (a `ThreadLocal`-based per-request scope for distinct-id/session-id/property propagation), no persistent process/UI, no disk persistence anywhere (`PostHogMemoryQueue` is explicitly documented as memory-only). Notably, `posthog-server` is a newer, more deliberately-designed rewrite relative to the other server SDKs already in this matrix — it ships a canonical `evaluateFlags()`/`PostHogFeatureFlagEvaluations` snapshot API with per-key access-tracking and a real evaluated-flag-value LRU+TTL cache (`internal/PostHogFeatureFlagCache.kt`), features some sibling SDKs (e.g. posthog-node, posthog-ruby) only have as looser, less-typed constructs.

## Notes

### n1 — Alias (❌ Fail)
- **Spec requires:** `both` applicability. Server-side flow: validate that both the existing distinct id and the alias target id are present; the `@both`-tagged acceptance scenario "Alias is dropped when required identities are missing" (`acceptance/public/alias.feature`) requires that no event be enqueued and that the SDK record a validation warning.
- **SDK currently:** `PostHog.kt:214-222` (`alias()`) delegates straight to shared-core `PostHogStateless.aliasStateless()` (`posthog/src/main/java/com/posthog/PostHogStateless.kt:356-368`):
  ```kotlin
  public override fun aliasStateless(distinctId: String, alias: String) {
      if (!isEnabled()) { return }
      val props = mutableMapOf<String, Any>()
      props["alias"] = alias
      captureStateless("$create_alias", distinctId, properties = props)
  }
  ```
  There is no blank/empty check on either `distinctId` or `alias` — directly contrasting with `identify()` seven lines below (`PostHogStateless.kt:370-382`), which has exactly this guard (`if (distinctId.isBlank()) { log(...); return }`). A call with a blank/empty alias or distinct id is sent straight to the API as a malformed `$create_alias` event rather than being dropped with a warning. No test in `PostHogTest.kt` or shared-core `PostHogStatelessTest.kt` exercises the missing-identity case.
- **Backwards compatibility:** Backward-compatible — adding a blank-check that logs a warning and returns early, mirroring `identify()`'s existing pattern, is additive; it only changes behavior for a currently-malformed call that today silently ships bad data instead of failing loudly.
- **Remediation:** Add the same `isBlank()` guard `identify()` already has to `aliasStateless()` for both `distinctId` and `alias`, logging a warning and returning without enqueuing when either is blank.

### n2 — Before Send Hook (🟡 Partial)
- **Spec requires:** `both` applicability, acceptance `@both` throughout (`acceptance/private/before-send-hook.feature`). A `beforeSend(event) -> event | null` hook run before enqueue; supports multiple registered hooks run in order, each receiving the previous hook's output; stops the chain on a drop; hook exceptions must not crash the caller.
- **SDK currently:** Hooks are registered via `PostHogConfig.addBeforeSend()`/`removeBeforeSend()` (server `PostHogConfig.kt:187-198`, forwarded into the shared core config in `asCoreConfig()`), stored as an ordered list and invoked in `PostHogStateless.buildEvent()` (`posthog/src/main/java/com/posthog/PostHogStateless.kt:288-322`). **Confirmed chaining bug:** the loop calls `beforeSend.run(postHogEvent)` on every iteration — the original, pre-chain event — instead of the running `eventChecked` variable it just assigned:
  ```kotlin
  var eventChecked: PostHogEvent? = postHogEvent
  for (beforeSend in beforeSendList) {
      try {
          eventChecked = beforeSend.run(postHogEvent)   // should be eventChecked, not postHogEvent
          if (eventChecked == null) { ... return null }
      } catch (e: Throwable) { ... return null }
  }
  return eventChecked
  ```
  With two or more registered hooks, each one independently transforms the original event; hook #2 never sees hook #1's mutation — violating the spec's "each hook receives the previous hook's output" requirement. No existing test (`PostHogBeforeSendTest.kt`, `PostHogStatelessTest.kt`) registers more than one hook, so this is untested and unnoticed. **Confirmed exception-safety deviation:** a throwing hook causes the entire event to be dropped (`return null`, line ~317) rather than falling back to the original/last-good event as the spec's documented per-SDK policies all do — this is asserted as intentional by an existing test, not an oversight, but it is a real deviation from the spec's stated fallback behavior. Null-stops-chain (the drop-on-`null` half) is correctly implemented.
- **Backwards compatibility:** Backward-compatible — fixing the chaining bug (`beforeSend.run(eventChecked)`) is a pure bug fix with no signature change. Changing the exception-fallback from drop-to-original is also additive/non-breaking (it means fewer events dropped, not more).
- **Remediation:** Fix `buildEvent()` to pass `eventChecked` (not `postHogEvent`) into each successive hook call. Separately, consider falling back to the pre-hook event on a thrown exception instead of dropping, to align with the spec's documented per-SDK fallback policies.

### n3 — Capture (✅ Pass)
- **Spec requires:** `both` applicability. Enrich events with distinct_id/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; honor opt-out with no network call; run `before_send`; never throw to the caller.
- **SDK currently:** `PostHog.kt:57-108` (`capture()`) resolves identity/personless-fallback via `PostHogRequestContext.resolveCaptureContext()`, then delegates to shared-core `captureStateless()` (`PostHogStateless.kt`), which builds properties in order (context → feature flags → `$set`/`$set_once` → `$groups` → `$lib`/`$lib_version`, caller-supplied properties applied last so they win), auto-generates a time-based UUID (`PostHogEvent.kt:21-28`), defaults the timestamp via the configured `dateProvider`, and checks the disabled/opt-out gate before any queueing — the whole body is wrapped in `try/catch(Throwable)` so `capture()` never throws. Well tested at both the server (`PostHogTest.kt`) and shared-core (`PostHogStatelessTest.kt`) layers.
- One minor, non-blocking deviation noted for completeness: a throwing `before_send` hook drops the event rather than falling back to the pre-hook message (see n2) — that defect is scored under Before Send Hook, not here, since Capture's own enrichment/opt-out/never-throw contract is otherwise fully satisfied.

### n4 — Capture Exception (🟡 Partial)
- **Spec requires:** Spec's own `## Applicability` line says `client` ("the audited implementations live in client/mobile SDKs with ambient device/user/session context"), but the acceptance feature `capture-exception.feature` is tagged `@both` at the feature level and on every one of its scenarios — treated as in-scope per this audit's acceptance-precedence convention, and doubly justified here since `posthog-server` genuinely implements `captureException()`. Requires correctly-ordered `$exception_list` (outermost/caught-first, root-cause-last), correctly-ordered stack frames (entry-point-first), flat top-level `$exception_type`/`$exception_message` properties, and preserved (not synthesized) stack traces.
- **SDK currently:** `captureException()` (`PostHog.kt:228-248`) resolves request context then delegates to shared-core exception handling built on `ThrowableCoercer` (`posthog/src/main/java/com/posthog/internal/errortracking/ThrowableCoercer.kt`). `$exception_list` ordering is correct (outermost-first, cause-chain walk with a cycle guard, `ThrowableCoercer.kt:41-57`); stack frames are correctly reversed from the JVM's native crash-site-first order to entry-point-first (`ThrowableCoercer.kt:71-73`, with an explicit comment documenting the reversal); stack preservation is structurally guaranteed since the JVM always provides a real `Throwable.stackTrace` (no synthesis fallback exists or is needed). **Gap:** `$exception_type`/`$exception_message` flat, top-level properties are never emitted anywhere — confirmed by an exhaustive grep across both `posthog-server/` and shared-core `posthog/` main source returning zero matches for either string; `ThrowableCoercer` only ever sets `$exception_list` and `$exception_level`. This directly contradicts the acceptance scenario "Capturing a handled exception emits an exception event," which requires `$exception_type=TypeError`-equivalent/`$exception_message=boom`-equivalent flat properties. Source-context (`pre_context`/`context_line`/`post_context`) is not implemented, which the spec explicitly permits as optional per-frame.
- **Backwards compatibility:** Backward-compatible — adding `$exception_type`/`$exception_message` sourced from `$exception_list[0].type`/`.value` is additive and removes nothing currently emitted.
- **Remediation:** Add `$exception_type`/`$exception_message` as flat top-level properties in the shared-core exception-building path (`ThrowableCoercer` or its caller), sourced from the first (outermost) entry of the constructed `$exception_list`.

### n5 — Debug (🟡 Partial)
- **Spec requires:** Spec's own applicability is `client` ("some SDKs expose only configuration-time logging options instead of a public runtime method"), and the acceptance file is `@client`-only with 3 scenarios: runtime enable/disable toggle; no network/analytics traffic when toggled; defaults to enabled when called with no argument.
- **SDK currently:** `PostHog.kt:53-55` (`debug(enable: Boolean)`) delegates to shared-core `PostHogStateless.debug()` (`posthog/src/main/java/com/posthog/PostHogStateless.kt:603-608`), which live-mutates `config.debug` and gates only local logging (`PostHogPrintLogger`) with no network/analytics side effects — this genuinely satisfies the spec's functional intent despite the client-only carve-out, similar to how other server SDKs' Debug rows have been scored ✅-beyond-scope in this matrix. However, both `PostHogInterface.kt:73` and `PostHogStateless.kt:603` declare `debug(enable: Boolean)` with **no default parameter**, so the "defaults to enabled when omitted" acceptance scenario cannot even be invoked in the SDK's own idiom (a caller must always pass an explicit `true`/`false`). No test asserts the "zero network/analytics traffic" guarantee either. Scored Partial rather than the clean ✅ some sibling SDKs earned, since the signature itself deviates from the spec's default-to-`true` behavior.
- **Backwards compatibility:** Backward-compatible — adding `enable: Boolean = true` as a default parameter value is purely additive.
- **Remediation:** Add a default value of `true` to `debug()`'s `enable` parameter on both `PostHogInterface.kt` and the shared-core base class.

### n6 — Event Batcher (🟡 Partial)
- **Spec requires:** `both` applicability, acceptance `@both`. Accumulate events; flush at count threshold (`flushAt`) or interval timer (`flushInterval`); preserve FIFO order; explicit flush should drain the queue; optionally shrink-and-retry on HTTP 413.
- **SDK currently:** `internal/PostHogMemoryQueue.kt` correctly implements count-threshold flush (`flushIfOverThreshold()`, default `flushAt=100`) and a self-rescheduling interval timer (`startTimer()`, default `flushIntervalSeconds=5`), FIFO ordering via a single `ArrayDeque` with `addLast`/`removeFirst` under one lock (`add()`/`takeEvents()`), and a `maxBatchSize` cap (default 100). **Gap 1:** explicit `flush()` (`PostHogMemoryQueue.kt:73-85`) sends only **one** batch capped at `maxBatchSize` — for a queue larger than `maxBatchSize`, a single `flush()` call does not fully drain it; a caller must call `flush()` repeatedly. Confirmed by `PostHogMemoryQueueTest.kt`'s test requiring a second explicit `flush()` call to finish draining. **Gap 2:** HTTP 413 is not specially handled at all — it falls into the generic "non-retryable, drop the whole batch" branch in `batchEvents()` (only `isNetworkingError() || statusCode >= 500` triggers a requeue-and-retry); equivalent shrink-on-413 logic exists in the shared-core client-only queue implementation but is architecturally unreachable from `posthog-server`, which always uses `PostHogMemoryQueue`. Since the spec frames 413-shrink-retry as optional ("some SDKs"), gap 2 alone would not be disqualifying, but gap 1 is a real deviation from "explicit flush drains immediately."
- **Backwards compatibility:** Backward-compatible — making `flush()` loop until the queue is empty (or a static batch-count guard is hit) is an internal behavior change with no signature impact.
- **Remediation:** Change `flush()` in `PostHogMemoryQueue.kt` to loop `executeBatch()` until the queue is below the 1-event threshold, rather than sending a single capped batch.

### n7 — Feature Flag Cache (✅ Pass, beyond stated scope)
- Spec's own `## Applicability` says `client` ("some server SDKs also cache flag definitions or results" is explicitly acknowledged as an accepted server-side analogue), and the acceptance file is tagged `@both` at the feature level — a thin but real override signal.
- `internal/PostHogFeatureFlagCache.kt` is a genuine evaluated-flag-**value** cache (not merely flag definitions) — a true LRU (`LinkedHashMap` with `accessOrder=true` and `removeEldestEntry`) storing evaluated `Map<String, FeatureFlag>` results keyed by `FeatureFlagCacheKey` (distinctId + groups + properties + flagKeys), with TTL-based lazy eviction on read (`isExpired()`/`expiresAt`). Configurable via `PostHogConfig.kt`'s `featureFlagCacheSize` (default 1000) and `featureFlagCacheMaxAgeMs` (default 5 minutes), both marked `@PostHogExperimental`. Thoroughly tested in `PostHogFeatureFlagCacheTest.kt` (TTL expiry, LRU eviction order, key equality, concurrency). Architecturally distinct from, and complementary to, the flag-**definitions** loader (row 16). Scored ✅ since the contract is genuinely implemented, well beyond the "definitions-only" carve-out the spec grants server SDKs.

### n8 — Feature Flag Called Tracker (🟡 Partial)
- **Spec requires:** Dedup `$feature_flag_called` by `(flag, value, distinct_id, normalized groups)`; bounded/incremental eviction (capacity pressure SHOULD NOT clear the entire tracker); clear fully only on shutdown/identity-reset boundaries; minimal-event mode gated by `has_experiment===false`, with an allowlist that — per the most recent sdk-specs fix (commit `b59e8b4`) — must include 10 session-attribution properties (`$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid`) while still excluding `$referrer`.
- **SDK currently — dedup eviction is fully compliant:** `posthog/src/main/java/com/posthog/internal/PostHogFeatureFlagCalledCache.kt` uses a hand-rolled LRU (linked list + hash map) that, on overflow, evicts a ~20% batch of the oldest entries one at a time (`BATCH_EVICTION_FACTOR`) rather than a full clear; `.clear()` is a separate method called only from `close()`/`reset()`-style lifecycle boundaries in `PostHogStateless.kt`. Confirmed by dedicated tests distinguishing batch eviction from full clear. **Gap — minimal-event allowlist is missing all 10 session-attribution properties:** `MINIMAL_FEATURE_FLAG_CALLED_PROPERTIES` (`posthog/src/main/java/com/posthog/PostHogStateless.kt:693-711`, inherited unmodified by `posthog-server`) contains exactly 16 entries (`$feature_flag`, `$feature_flag_response`, `$feature_flag_has_experiment`, `$feature_flag_id`, `$feature_flag_version`, `$feature_flag_reason`, `$feature_flag_request_id`, `$feature_flag_evaluated_at`, `$feature_flag_error`, `locally_evaluated`, `$groups`, `$process_person_profile`, `$session_id`, `$window_id`, `$lib`, `$lib_version`) — the flag-identity/session/platform categories, but zero session-attribution properties. An exhaustive grep across both `posthog/` and `posthog-server/` (main and test) for any of the 10 required strings (`utm_source`, `$referring_domain`, `gclid`, `fbclid`, etc.) returns no matches anywhere in the codebase. `$referrer` is correctly absent, but only incidentally — there is no session-attribution support at all to offset. This reproduces the exact same gap independently found in posthog-ruby, posthog-node (pre-fix), and posthog-php: a minimized `$feature_flag_called` event that happens to be the first event in a session will silently null out that session's UTM/referrer attribution. `PostHogTest.kt` pins the current (incomplete) property set via an `expectedKeys`-style assertion.
- **Backwards compatibility:** Backward-compatible — adding 10 keys to a strip-allowlist `Set` is strictly additive; it can only cause minimized events to retain more properties than before, never fewer.
- **Remediation:** Add the 10 session-attribution property names from sdk-specs commit `b59e8b4` to `MINIMAL_FEATURE_FLAG_CALLED_PROPERTIES` in `posthog/src/main/java/com/posthog/PostHogStateless.kt:693-711`.

### n9 — Flag Definition Loader (✅ Pass)
- Spec Applicability `both`; acceptance file (`acceptance/private/flag-definition-loader.feature`) tagged `@server`.
- `internal/LocalEvaluationPoller.kt` runs a genuine background `ScheduledExecutorService`-based poll loop (configurable `pollIntervalSeconds`, default 30s) that periodically refreshes flag definitions without an application call being the trigger. ETag/If-None-Match support exists on a dedicated local-evaluation endpoint distinct from any general remote-config endpoint (`posthog/src/main/java/com/posthog/internal/PostHogApi.kt`), with 304 responses correctly preserving prior definitions. External/shared cache-provider integration (`PostHogFlagDefinitionCacheProvider.kt`) supports both an async (`CompletionStage`-based) contract and a synchronous convenience subclass adapting blocking calls, matching the spec's "MAY be sync or async" language exactly, with provider-failure fallback to a direct fetch. Personal-API-key gating for local evaluation is enforced (`internal/PostHogFeatureFlags.kt`). Well tested across `PostHogFeatureFlagsTest.kt` and `FlagEvaluatorTest.kt`.

### n10 — Flush (🟡 Partial)
- **Spec requires:** `both` applicability. No-op on empty queue with no network call; bypass batching intervals and drain immediately; on delivery failure the failed batch must remain queued for a later retry, not silently dropped.
- **SDK currently:** `PostHog.kt:49-51` (`flush()`) delegates to shared-core `PostHogStateless.flush()`, which calls `queue?.flush()` → `PostHogMemoryQueue.flush()` (`internal/PostHogMemoryQueue.kt:73-85`). Correctly a no-op when the queue has no events (`isAboveThreshold(1)` guard) and correctly bypasses the interval timer to send immediately. Retryable failures (`isNetworkingError() || statusCode >= 500`) correctly re-add the taken batch back to the front of the queue (`batchEvents()`, lines 211-220) rather than dropping it — satisfying the core "keep retryable failures queued" requirement. **Gap (shared with Event Batcher, n6):** `flush()` sends only a single capped batch (`maxBatchSize`), not a full drain — a queue larger than `maxBatchSize` is not fully flushed by one `flush()` call, contradicting the acceptance expectation that an explicit flush drains what's pending. **Gap 2:** HTTP 429 is misclassified as non-retryable (falls through to the `else`/drop branch since `429 < 500`), directly contradicting the spec's explicit framing of rate-limit responses as retryable — a 429 during `flush()` permanently drops the batch instead of preserving it for retry.
- **Backwards compatibility:** Backward-compatible — looping `flush()` until drained, and reclassifying 429 as retryable, are both internal behavior changes with no signature/contract impact.
- **Remediation:** Same fix as n6 for the drain behavior; separately, add `statusCode == 429` to the retryable branch in `PostHogMemoryQueue.batchEvents()`.

### n21 — Retry Queue (🟡 Partial)
- **Spec requires:** `both`. In-memory queue with backpressure/drop-when-full; classify retryable (network errors, 5xx, 429) vs. non-retryable (other 4xx) failures; exponential/linear backoff, honoring `Retry-After` where present; retryable failures keep the same events queued for a later, separate flush attempt; success removal by stable identity (not index), so concurrently-captured events aren't confused with the in-flight batch.
- **SDK currently:** `internal/PostHogMemoryQueue.kt` implements drop-oldest backpressure with a logged warning when `maxQueueSize` is exceeded (`add()`, default 10000), tested in `PostHogMemoryQueueTest.kt`. Removal-on-success is identity-safe by construction — the same `ArrayDeque<PostHogEvent>` object references are popped/pushed, never index/slice arithmetic. Backoff is linear (`min(retryDelaySeconds * retryCount, maxRetryDelaySeconds)`, defaults 5s/60s ceiling) — spec-permitted, since it allows linear or exponential. **Gap 1:** HTTP 429 is misclassified as non-retryable — `batchEvents()`'s retry condition is only `isNetworkingError() || statusCode >= 500` (`PostHogMemoryQueue.kt:211-226`), so a 429 falls into the `else` branch and the batch is dropped outright rather than requeued, directly contradicting the spec's explicit listing of rate-limit responses as retryable. **Gap 2:** `Retry-After` is parsed by the shared HTTP layer (`PostHogApi.kt`, attached to `PostHogApiError`) but never consumed by the queue's own retry/backoff calculation — `calculateDelay(retry: Boolean)` takes no `retryAfterSeconds` parameter at all, confirmed by grep returning zero references to it anywhere in `posthog-server`. **Gap 3:** no maximum-retry-count cap exists — a persistently failing batch retries indefinitely at the 60-second backoff ceiling, rather than eventually being dropped as terminal (the shared-core client-only queue has a `maxRetries` concept that `PostHogMemoryQueue` doesn't use).
- **Backwards compatibility:** Backward-compatible — reclassifying 429 as retryable, honoring `Retry-After` when present, and adding an optional terminal-retry-count cap are all internal behavior refinements with no public signature impact.
- **Remediation:** Add `statusCode == 429` to the retryable branch in `batchEvents()`; thread the parsed `Retry-After` value from `PostHogApiError` into `calculateDelay()`; consider adding an optional max-retry-count ceiling to avoid unbounded retry-forever behavior during a sustained outage.

### n24 — Shutdown (🟡 Partial)
- **Spec requires:** `both`. Flush pending events, stop workers permanently, reject/no-op future captures, be idempotent, not crash on delivery failure.
- **SDK currently:** `close()` (`PostHog.kt:33-35` → shared-core `PostHogStateless.close()`, `posthog/src/main/java/com/posthog/PostHogStateless.kt:106-135`) is idempotent by construction (an `isEnabled()` guard returns immediately on a second call), correctly stops the flag poller and clears the feature-flag-called dedup cache in a lifecycle-boundary full-clear (matching n8's expectations), uninstalls integrations defensively (each wrapped in its own try/catch), and — since `enabled` flips to `false` before any of this — correctly causes subsequent `capture()`/`identify()`/etc. calls to no-op rather than throw (confirmed by tests in both `PostHogTest.kt` and `PostHogStatelessTest.kt`). **The most significant gap: `close()` never flushes the queue.** The call chain goes `enabled = false` → `queue?.stop()` → `featureFlags?.shutDown()` → `featureFlagsCalled?.clear()`; `queue?.stop()` (`internal/PostHogMemoryQueue.kt:99-109`) only cancels the interval timer — it does not call `flush()`. Any events accumulated below the `flushAt` threshold at the moment `close()` is called are silently lost unless the caller manually calls `flush()` before `close()`. No test in either `PostHogTest.kt` or `PostHogStatelessTest.kt` demonstrates a queued sub-threshold event being delivered purely as a result of calling `close()`/`shutdown()`. This directly contradicts the spec's "flush pending events" requirement for a graceful shutdown.
- **Backwards compatibility:** Backward-compatible — adding a `queue?.flush()` call before `queue?.stop()` inside `close()` is additive; it only changes behavior for the currently-lossy case (pending sub-threshold events at shutdown time), which is unlikely to be a behavior any caller depends on today.
- **Remediation:** Add a `queue?.flush()` call in `PostHogStateless.close()` before `queue?.stop()`, so pending events are drained before the SDK becomes permanently disabled.
