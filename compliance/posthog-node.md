**A note on repo layout:** The `PostHog/posthog-node` repository itself has been archived/redirected — its code was moved into the `posthog-js` monorepo and now lives at `packages/node` (Node-specific integration: the `PostHog` client class, Express/NestJS middleware, error-tracking stack-trace enrichment, feature-flag polling, the new `captureAi`/`ai-capture` route) and `packages/core` (the shared `@posthog/core` library also used by `packages/browser` and `packages/react-native`: the capture/batch/flush/retry engine in `posthog-core-stateless.ts`, the richer ambient-identity `posthog-core.ts` base class used only by client SDKs, logs, error-tracking primitives). This audit clones `posthog-js` (commit above) and inspects `packages/node/src` + `packages/core/src` only — `packages/browser`, `packages/react-native`, and `packages/ai` are out of scope except where they are the *only* place a Node-facing option (e.g. `enableFullAiCapture`) is actually consumed. `packages/node`'s `PostHogBackendClient` still extends the stateless `PostHogCoreStateless`, **not** the richer client-only `PostHogCore`, so most client-only ambient-identity/session/replay primitives (`group()`, `reset()`, `getAnonymousId()`, `onFeatureFlags()`, session replay, bootstrap, etc.) simply don't exist on the Node class at all, making most N/A calls unusually clean-cut. The repo still supports both a legacy "v0" batch-capture pipeline (`POST /batch/`, default) and a newer "v1" pipeline (`POST /i/v1/analytics/events`, opt-in only via `POSTHOG_CAPTURE_MODE=v1` env var, `packages/node/src/capture-v1/config.ts`) — both share one queue/flush/retry engine in `posthog-core-stateless.ts` but differ in transport (`packages/node/src/capture-v1/*`), which matters for several findings below. Since the last audit (2026-08-06, `e1efa572`), the monorepo has added a dedicated AI-event capture route (`packages/node/src/ai-capture/`), a richer flag-evaluation snapshot API (`packages/node/src/feature-flag-evaluations.ts`), and no Traces/OTel-native-spans support in `packages/node` (still only in the separate `packages/ai` package's OTel bridge to `/i/v0/ai/otel`, not `/i/v1/traces`).

## Notes

### n1 — Logs (🟡 Partial)
- **Spec requires:** A `captureLog`/logger API producing OTLP-shaped log records shipped via `POST {host}/i/v1/logs`, with severity-number mapping, batching/rate-capping, gzip, and retry/413 handling.
- **SDK currently:** A complete, spec-conformant logs pipeline exists in shared `@posthog/core` — `packages/core/src/logs/index.ts` (`PostHogLogs.captureLog()`, tumbling-window rate cap, FIFO oldest-eviction overflow, persisted queue, exponential-backoff retry, 413 batch-halving) and `packages/core/src/logs/logs-utils.ts` (OTLP severity/value mapping). The transport, `PostHogCoreStateless._sendLogsBatch()`, correctly POSTs to `${host}/i/v1/logs?token=...` and gzips. **None of this is wired into `packages/node`.** A fresh grep confirms `grep -rn "captureLog\|PostHogLogs\|LogsConfig\|logsHost" packages/node/src` returns zero matches, and `packages/node/src/exports.ts:15` re-exports only `Metrics`/`MetricsConfig` from `@posthog/core`, nothing from `logs`. There is still no `public get logger()` getter on `PostHogBackendClient` analogous to the existing `public get metrics()` getter (`client.ts:598`) that wires up the sibling `PostHogMetrics` class. A Node application cannot call `captureLog` today even though the transport layer is present on every Node client instance.
- **Backwards compatibility:** Backward-compatible — instantiating `PostHogLogs` and exposing it via a new lazy getter/method on `PostHogBackendClient`, mirroring the existing `metrics` getter pattern, is purely additive.
- **Remediation:** Add a `captureLog()` method or `logger`/`logs` getter to `packages/node/src/client.ts` that constructs `PostHogLogs` against the already-present `_sendLogsBatch` transport, the same way `metrics` is wired up today.

### n2 — Traces (❌ Fail)
- **Spec requires:** A `startSpan`/`withSpan` API producing OTLP spans shipped to `POST {host}/i/v1/traces`, explicitly distinct from LLM-analytics-as-events, requiring no OpenTelemetry runtime dependency.
- **SDK currently:** Exhaustive grep for `startSpan`/`withSpan`/`i/v1/traces`/`traceparent`/`getActiveSpan` across `packages/core/src`, `packages/browser/src`, `packages/react-native/src`, and `packages/node/src` returns zero matches anywhere in the monorepo. What exists instead is exactly the substitute the spec explicitly excludes: LLM analytics captured as `$ai_generation`/`$ai_trace_id` ordinary analytics events, plus `packages/ai/src/otel/{exporter,processor}.ts`, which posts OTel spans to `${host}/i/v0/ai/otel` (not `/i/v1/traces`), only for `gen_ai.*` AI-semantic-convention spans, and depends on real `@opentelemetry/sdk-trace-base`/`@opentelemetry/exporter-trace-otlp-http` packages — the exact OTel runtime dependency the spec says the canonical implementation must avoid. This bridge lives in the separate `packages/ai` package, which `packages/node`'s `package.json` does not depend on. No SDK in this monorepo implements the canonical contract yet — this is a monorepo-wide gap, not a node-specific regression, and is unchanged since the last audit.
- **Backwards compatibility:** Backward-compatible — a net-new subsystem; no removal needed.
- **Remediation:** Implement a dependency-free `startSpan`/`withSpan` API shipping OTLP spans to `/i/v1/traces` in `@posthog/core`, wired into `packages/node` (and browser/react-native), independent of the `packages/ai` OTel bridge.

### n3 — Tracing Headers (🟡 Partial)
- **Spec requires:** `both` applicability. Request-scoped middleware extracting `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` case-insensitively; sanitize (trim/strip control chars/cap length); explicit call-site values take precedence over context; personless-capture fallback unless the caller explicitly supplied `$process_person_profile`; flag-evaluation APIs no-op/return-empty when no identity is resolvable; per-request isolation; headers never used for auth.
- **SDK currently:** Server-side consumption is real and well-tested. `packages/node/src/extensions/context/context.ts` implements genuine `AsyncLocalStorage`-based per-request isolation. `packages/node/src/extensions/tracing-headers.ts` reads headers case-insensitively (Node's `IncomingHttpHeaders` is always lowercased); `sanitizeTracingHeaderValue` strips control chars, trims, caps at 1000 chars. Two framework integrations wire this in: `express.ts` and `nestjs.ts`, both never swallowing errors. Capture precedence is correct in `_prepareEventMessage` (`client.ts:~2920-2940`): explicit `distinctId` wins over context, explicit properties win over context properties. Personless fallback (`client.ts:2934-2937`, synthesize `uuidv7()` + `$process_person_profile=false`) remains **unconditional**, executed after the property spread, so it overwrites any caller-supplied `$process_person_profile` value rather than only applying "unless the caller explicitly supplied that property" — a real, narrow, unchanged deviation. Flag-evaluation no-op-when-no-identity is correctly implemented on the modern API surface (`getAllFlags`, `getAllFlagsAndPayloads`, `evaluateFlags`, `getFeatureFlagResult` all resolve via a shared distinct-id-resolution helper and return early with no network call and no `$feature_flag_called` when unresolvable). Gap: the deprecated-but-still-shipped legacy API surface (`getFeatureFlag`, `isFeatureEnabled`) still requires `distinctId` as a mandatory positional argument with no context-fallback and no no-op path.
- **Backwards compatibility:** Backward-compatible — adding an options-overload with context-fallback to the legacy `getFeatureFlag`/`isFeatureEnabled` methods, and fixing the personless-fallback to respect a caller-supplied `$process_person_profile`, are both additive/narrowing fixes.
- **Remediation:** Add optional-`distinctId`-with-context-fallback support to `getFeatureFlag`/`isFeatureEnabled`; guard the personless-fallback assignment in `_prepareEventMessage` with a check for an already-present `$process_person_profile` property.

### n4 — Alias (🟡 Partial)
- **Spec requires:** `both` applicability. Validate inputs — both the existing distinct id and the alias target id must be present; if either is missing, drop the call with zero enqueued events and a validation warning (acceptance scenario "Alias is dropped when required identities are missing," tagged `@both`).
- **SDK currently:** `alias()`/`aliasImmediate()` (`packages/node/src/client.ts:~1050-1090`) build the correct `$create_alias` event shape for the happy path. There is still no validation of `data.distinctId`/`data.alias` for emptiness anywhere in the method (confirmed by fresh code read — no guard clause exists before `_sendPreparedEvent`). Both flow through the shared `_prepareEventMessage`, where a falsy `distinctId` is silently replaced with a synthesized `uuidv7()` and the event is enqueued anyway with `$process_person_profile: false` — rather than being dropped with a validation warning as the acceptance scenario requires. Unchanged from the previous audit.
- **Backwards compatibility:** Backward-compatible — adding an emptiness check that logs a warning and returns early is additive; it only changes behavior for a currently-malformed call that today silently mutates the distinct id instead of failing loudly.
- **Remediation:** In `alias()`/`aliasImmediate()`, validate that `data.distinctId` and `data.alias` are both present and non-empty before building the event; log a warning and return without enqueuing otherwise.

### n5 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Enrich events with `distinct_id`/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; honor an opt-out state so capture is silently dropped with no network call; validate that `event` and `distinct_id` are non-empty; support a `before_send` hook that can mutate/drop events, with hook exceptions logged and the original message used as a fallback (not the event being dropped).
- **SDK currently:** `capture()` is fire-and-forget and never throws. Enrichment is complete and correct: `$lib`/`$lib_version`/`$is_server`, timestamp/uuid defaulting, `$groups`, `$process_person_profile=false` fallback for missing distinct id. A genuine dynamic opt-out exists (`optIn()`/`optOut()`, exposed as `enable()`/`disable()`), checked in `enqueue()`/`sendImmediate()` with silent no-op. Gaps, both reconfirmed unchanged against current code: (1) no runtime validation of `event`/`distinct_id` non-emptiness anywhere — `_warnIfInvalidCapture` (`client.ts:710-721`) only checks for string-typed `properties` or `$exception` misuse, not empty event/distinctId; a falsy `distinctId` is silently replaced with a synthesized UUID instead of triggering a validation warning; (2) `before_send` hook exceptions are not caught at the Node-specific hook-invocation site `_runBeforeSend` (`client.ts:3050-3072`, distinct from the try/catch-wrapped version in `PostHogCore` used only by browser/react-native) — an uncaught exception propagates as a rejected promise and is only caught one layer above by a generic `.catch` in `_sendPreparedEvent` (`client.ts:750-754`), which drops the entire event via `console.error` rather than falling back to the original, unmutated message as the spec requires.
- **Backwards compatibility:** Backward-compatible — adding event/distinct_id validation and fixing the before_send exception path to preserve the original message (rather than dropping) are both additive/bug-fix-shaped changes with no public signature impact.
- **Remediation:** Add non-empty validation for `event` and `distinct_id` with a logged warning on failure; wrap the Node-specific `_runBeforeSend`'s hook invocation in its own try/catch that falls back to the pre-hook message on exception, matching `PostHogCore`'s existing browser/RN behavior.
- **New this run — environment-sourced release identifier (capture spec, PR [#80](https://github.com/PostHog/sdk-specs/pull/80)):** the capture spec now requires a server SDK that can read its environment to resolve `POSTHOG_RELEASE_ID` once at construction and stamp `$release_id` **on the shared event path**, so ordinary captures, `alias`, `group_identify` and person-property events all carry it. posthog-node reads the variable correctly — `CoreErrorTracking.getInjectedReleaseId()` (`packages/core/src/error-tracking/release.ts`) trims it, treats blank as unset, and prefers it over the injected `globalThis._posthogReleaseId` bundle global — but it is only applied on the **exception** paths: `packages/node/src/extensions/error-tracking/index.ts:57-61` and `packages/node/src/extensions/sentry-integration.ts:158`. `grep -rn '\$release_id' packages/core/src/posthog-core-stateless.ts packages/node/src/client.ts` returns nothing, so an ordinary `capture()`, `alias()`, `groupIdentify()` or `identify()` event carries no `$release_id` at all. It is also read per-event rather than once at construction, and (unlike posthog-python) there is no minimized-`$feature_flag_called` allowlist question to answer because the property never reaches that event either.
- **Remediation (release id):** resolve the release id once in the client constructor and stamp it with a `setdefault`-equivalent in the shared event-preparation path in `packages/core/src/posthog-core-stateless.ts`, before `beforeSend`, instead of only in the two error-tracking call sites; keep it out of `$set`/`$set_once`/`$group_set`.

### n6 — Capture AI (🟡 Partial)
- **Spec requires:** `server` applicability. `captureAi`/`captureAiImmediate` mirroring `capture`'s shape on a fully isolated AI-event queue/route/endpoint, never sharing a send cycle with `capture()` even for `$ai_*`-named events; UUID generation/validation identical to `capture`; the route never throws; oversized events are dropped while logging only event name + byte size, never content; `enableFullAiCapture` gates wrapper-level behavior (media passthrough, skip truncation) without altering `capture_ai` payloads directly; **privacy mode always wins over `enableFullAiCapture`**, regardless of client-level or per-call configuration.
- **SDK currently:** This is a mature, well-tested, near-complete implementation. `captureAi`/`captureAiImmediate` (`packages/node/src/client.ts:853-887`) mirror `capture`'s `EventMessage` shape exactly (`types.ts:447,459`). The route is genuinely isolated: dedicated `AI_CAPTURE_ROUTE` (`ai-capture/routing.ts:1`), its own persisted queue key, its own endpoint `/i/v0/ai/batch/`, and independent flush handling — verified never to mix with the ordinary analytics route even when `capture()` is called with an `$ai_*`-named event (`__tests__/ai-capture/wiring.spec.ts:58-79`). UUID generation/validation reuses the shared `getEventUuid`/`isValidUUID` helpers. The route never throws (`_sendPreparedAiEvent` funnels through the same `.catch((err) => console.error(err))` guard as ordinary capture). Oversized-event dropping is correctly implemented: `partitionAiBatch` (`ai-capture/batching.ts:16-47`) computes byte size and for events over the 8MiB cap (`ai-capture/routing.ts:5`) logs/emits only `` `Event ${event} (${bytes} bytes) exceeds the 8MiB limit...` `` — name and size only, confirmed never containing payload content, and directly tested (`wiring.spec.ts:87-109`). `enableFullAiCapture` (`types.ts:346`, `client.ts:151,219`) is correctly scoped to the separate `packages/ai` wrapper package (media redaction, truncation skip) rather than altering `captureAi` payloads directly, matching the spec's "capture_ai is a pipe" requirement. **Gap: the "privacy mode always wins" guarantee is broken at the client-config level.** `packages/ai/src/utils.ts:384-386`'s `withPrivacyMode` correctly ORs a client-level `privacy_mode` with a per-call `privacyMode` argument and redacts if either is true — but `PostHogOptions.privacyMode` (`packages/node/src/types.ts:194`, documented again at `types.ts:341-343` as "Privacy mode always wins") is **never read, stored, or assigned anywhere** in `packages/node/src/client.ts` or `packages/core/src` — no constructor assignment, no getter. `packages/ai`'s own tests only exercise this path by manually monkey-patching a mock client (`(mockPostHogClient as any).privacy_mode = true`, e.g. `packages/ai/tests/anthropic.test.ts:753`), which a real `new PostHog(key, { privacyMode: true })` client can never reproduce. The per-call `privacyMode` argument passed directly to an AI-wrapper call does work correctly and unconditionally redacts — only the persistent client-level override is dead.
- **Backwards compatibility:** Backward-compatible — this is a strengthening fix (the spec explicitly permits guarantees to strengthen, never weaken, pre-GA); no existing caller currently gets any redaction benefit from setting `privacyMode` at the client level today since it does nothing, so wiring it up can only add behavior for callers who already believed they'd set it.
- **Remediation:** In `packages/node/src/client.ts`, store the normalized `privacyMode` option as a real property/getter (e.g. `public readonly privacyMode: boolean`, or a `privacy_mode` getter matching the snake_case name `packages/ai`'s `withPrivacyMode` already reads) so a real client instance carries the value the type declares; add a regression test asserting that constructing a client with `{ privacyMode: true, enableFullAiCapture: true }` and calling a `packages/ai` wrapper redacts input/output.

- **Spec requires:** Native HTTP client injectable/replaceable; ingestion requests include token; gzip; non-2xx/3xx failures reported without throwing to capture callers; a feature-flag-evaluation retry policy: retry only on transport failures or HTTP 502/504, default budget of exactly 1 retry (2 total attempts), exponential backoff starting at 300ms and doubling to 600ms for the second retry.
- **SDK currently:** Native `fetch` (injectable `FetchLike`) used throughout, no axios/undici dependency. Ingestion requests correctly include the token and gzip via native `zlib.gzip`. Non-2xx/3xx failures are reported without throwing to `capture()` callers. The `/flags` retry classification remains correct (`isRetryableFlagsFetchError`: network errors except `ECONNREFUSED`, or 502/504 only) and the default retry budget is correct (`featureFlagsRequestMaxRetries` defaults to `1`, giving 2 total attempts). **The backoff timing is still wrong**: fresh read of `retriable()` (`packages/core/src/utils/index.ts:51-78`) confirms it still uses one fixed `props.retryDelay` (default 3000ms) for every retry iteration — no exponential logic exists anywhere in `packages/core`. The `/flags` call site passes no `retryDelay` override, so it inherits the fixed 3000ms default rather than the spec-mandated 300ms→600ms exponential sequence, failing the timing-sensitive acceptance scenarios in `http-client.feature`.
- **Backwards compatibility:** Backward-compatible — changing the fixed 3000ms delay to the spec's exponential 300ms/600ms schedule for the flags-retry path specifically is an internal timing change with no public API impact (aside from tests asserting the old timing).
- **Remediation:** Introduce a dedicated exponential-backoff schedule (300ms base, doubling, capped at the 1-retry default) for the `/flags` retry path in `retriable()`/`isRetryableFlagsFetchError`'s call site, distinct from the general-purpose fixed-delay retry used elsewhere.

### n24 — Local Feature Flag Evaluator (🟡 Partial)
- **Spec requires:** Everything the previous note covered (operator dispatch, rollout hashing, multivariate bucketing, cohort matching, property-override merging, unrecognized operators degrading to inconclusive per-flag), plus two requirements added since the last audit. **Experiment holdouts** (PR [#76](https://github.com/PostHog/sdk-specs/pull/76)): a flag with a holdout evaluates the holdout before its release conditions. **Group keys are rendered for bucketing like the flags service** (PR [#89](https://github.com/PostHog/sdk-specs/pull/89)): a string key contributes its unquoted contents and a number its canonical JSON encoding, while a key of **any other type** is unresolved context — the condition is inconclusive, remote evaluation stays eligible, the key is not rendered with a host-specific spelling, and nothing crashes.
- **SDK currently:** **Holdouts are implemented** — `packages/core/src/featureFlagLocalEvaluation.ts:546-580` hashes `holdout-<value>` with the service's `-` separator (the comment makes the separator's significance explicit) and `packages/node/src/types.ts:406-408` carries `filters.holdout` through the definition type. posthog-node is the second SDK in this matrix to have them, after posthog-python. The operator-degradation behavior re-verified as correct and the batch isolation in `getAllFlagsAndPayloads` is unchanged. **The group-key rule is the new gap:** `packages/node/src/extensions/feature-flags/feature-flags.ts:400` passes `groups[groupName]` straight into `matchFeatureFlagProperties` as the bucketing value, and `getFeatureFlagHash` (`featureFlagLocalEvaluation.ts:537-541`) interpolates it into a template literal. A string or number key renders correctly (`42` → `"42"`, matching the service), but the declared `bucketingValue: string` type is not enforced at the runtime boundary — `groups` arrives from an untyped caller map — so a boolean key buckets on the literal `"true"` and an object key on `"[object Object]"`, host-specific spellings the service would never produce, instead of making the condition inconclusive and falling back to `/flags`. Nothing crashes, which is the other half of the requirement. This is the identical gap recorded for posthog-python ([posthog-python.md#n19](posthog-python.md)).
- **Backwards compatibility:** Backward-compatible — today's behavior for a non-scalar group key is a silent disagreement with the backend, so changing it to inconclusive-plus-remote-fallback corrects a wrong answer rather than removing a relied-on one. The acceptance-asset sync gap noted previously is unchanged and needs no code change.
- **Remediation:** At the group branch in `feature-flags.ts`, narrow the key: accept `string` as-is and `number` via its canonical JSON encoding, and throw `InconclusiveMatchError` for anything else so the flag defers to `/flags`. Separately, mirror the operator-degradation and group-key scenarios from `spec.md` into `acceptance/private/local-feature-flag-evaluator.feature`.

### n25 — Retry Queue (🟡 Partial)
- **Spec requires:** `both`. In-memory queue with backpressure/drop-when-full; classify retryable (network errors, 5xx, 429, timeouts) vs. non-retryable (most 4xx) failures; exponential/linear backoff honoring `Retry-After`; retryable failures keep the same events queued for a later, separate flush attempt; success removal by identity/stable-id (not index); terminal/exhausted failures drop the batch.
- **SDK currently:** Retryable classification (v0): network errors, 408/429, or 5xx; non-retryable 4xx correctly drops with an emitted/rethrown error. Overflow handling is oldest-dropped FIFO eviction with a warning log. Post-flush removal is identity-based (matched by UUID first, falling back to object-reference identity), correctly satisfying the anti-regression requirement about concurrently-captured events not being mistaken for the just-sent batch. `Retry-After` is honored, but **only in v1** (`capture-v1/sender.ts:130,165,300-326`) — v0 (still the default pipeline) never reads `Retry-After` anywhere, confirmed unchanged by fresh grep. v0 uses fixed-delay (not exponential) retry — spec-permitted ("exponential *or linear*"), so not a violation, just the weaker of the two policies; v1 does true exponential backoff. The same v1-events-can-be-lost-on-exhausted-retry issue documented under Flush (n9) applies here too — directly contradicting "retryable failures keep the same events queued for a later attempt" for the v1 pipeline specifically, though currently latent since v1 is opt-in-only.
- **Backwards compatibility:** Backward-compatible to add `Retry-After` support to v0 (additive). The v1 queue-loss issue needs the same careful, non-silent fix described under n9.
- **Remediation:** Add `Retry-After` honoring to the v0 retry path in `packages/core/src/utils/index.ts`'s `retriable()`; fix the v1 event-loss issue per n9's remediation.

### n26 — MCP Analytics (🟡 Partial, new row)
- **Spec requires:** The MCP analytics spec's applicability table lists `@posthog/mcp` under **posthog-js**. In practice `packages/mcp/package.json` declares `posthog-node` as both a workspace dependency and a `^5.0.0` peer dependency — the add-on's host SDK, whose `capture` carries the `$mcp_*` events, is posthog-node, not the browser package. This row is scored here on that basis and cross-referenced from [posthog-js.md](posthog-js.md#n37); **the applicability table and the package's actual host client disagree, and which SDK owns this row is a spec question for a human maintainer**, not something this audit resolves. The requirements themselves: one `$mcp_tool_call` per call reaching a final outcome, always carrying `$mcp_tool_name`, `$mcp_is_error`, `$mcp_duration_ms`, `$mcp_source`, `$session_id` and a request-start `timestamp`; no `$mcp_tool_call` for an `input_required` round, a task handle, or a call naming an unregistered tool (a rule that "applies to every SDK" regardless of capability tags); `$mcp_input_required` and `$mcp_unknown_tool` SHOULD be emitted; events bounded at 102,400 bytes with a normative shrink order; `$lib` of the form `posthog-<runtime>-mcp`.
- **SDK currently:** `packages/mcp` is the richest MCP implementation in this matrix and the one posthog-js's audit already examined in detail at `6538babc`; re-reading it at this run's commit confirmed both gaps are unchanged — `grep -rn 'mcp_unknown_tool\|mcp_input_required' packages/mcp/src` returns **zero** matches, and the suite still asserts the misreporting behavior directly in `packages/mcp/src/__tests__/error-capture.test.ts:162` ("captures errors for unknown tool names") — so rather than restate the rest of the evidence this note defers to [posthog-js.md](posthog-js.md#n37) for it. In summary: the required `$mcp_tool_call` properties, session derivation, injected arguments, server build, feedback tool and size bound are all present; **neither `$mcp_unknown_tool` nor `$mcp_input_required` is emitted**, and an unknown tool is not merely unreported but *misreported* as a failed `$mcp_tool_call` on both instrumentation paths, inflating the server's own tool error rate with names it never registered.
- **Backwards compatibility:** Backward-compatible — adding the two event names and suppressing the misreported `$mcp_tool_call` are additive and corrective; no existing property changes meaning.
- **Remediation:** Emit `$mcp_unknown_tool` with the requested name instead of a failed `$mcp_tool_call` when the server has no such tool, emit `$mcp_input_required` per round, and declare the matching `@mcp_unknown_tool_capable`/`@mcp_input_required_capable` acceptance tags. Separately, raise the ownership question above with the spec owners so this row is tracked against exactly one SDK.
