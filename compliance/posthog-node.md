# posthog-node — SDK Compliance

**Repo:** [PostHog/posthog-node](https://github.com/PostHog/posthog-node)
**Audited commit:** `e1efa5725754aed1e2709e255e5abd607a276664` ([commit](https://github.com/PostHog/posthog-js/commit/e1efa5725754aed1e2709e255e5abd607a276664)) — audited on 2026-08-06

**Summary:** 11 ✅ · 15 🟡 · 6 ❌ · 27 ➖ · 0 ❓

**A note on repo layout:** The `PostHog/posthog-node` repository itself has been archived/redirected — its code was moved into the `posthog-js` monorepo and now lives at `packages/node` (Node-specific integration: the `PostHog` client class, Express/NestJS middleware, error-tracking stack-trace enrichment, feature-flag polling) and `packages/core` (the shared `@posthog/core` library also used by `packages/browser` and `packages/react-native`: the capture/batch/flush/retry engine in `posthog-core-stateless.ts`, the richer ambient-identity `posthog-core.ts` base class used only by client SDKs, logs, tracing-headers, and error-tracking primitives). This audit therefore clones `posthog-js` (commit above) and inspects `packages/node/src` + `packages/core/src`. A consequence of this architecture: `packages/node`'s `PostHogBackendClient` extends the stateless `PostHogCoreStateless`, **not** the richer client-only `PostHogCore` — so most client-only ambient-identity/session/replay primitives (`group()`, `reset()`, `getAnonymousId()`, `onFeatureFlags()`, session replay, bootstrap, etc.) simply don't exist on the Node class at all, making most N/A calls unusually clean-cut. The repo also ships its own compliance test harness adapter at `compliance/node/` (used against the `posthog-sdk-test-harness`), which supports both a legacy "v0" batch-capture contract (`POST /batch/`) and a newer "v1" contract (`POST /i/v1/analytics/events`, env `POSTHOG_CAPTURE_MODE=v1`) — both pipelines share one queue/batch/flush/retry engine in `posthog-core-stateless.ts` but differ in transport implementation (`packages/node/src/capture-v1/*`), which matters for several findings below.

## Notes

### n1 — Logs (🟡 Partial)
- **Spec requires:** A `captureLog`/logger API producing OTLP-shaped log records shipped via `POST {host}/i/v1/logs`, with severity-number mapping, batching/rate-capping, gzip, and retry/413 handling. (No acceptance `.feature` file exists for this contract in either `acceptance/public` or `acceptance/private`.)
- **SDK currently:** A complete, spec-conformant, well-tested logs pipeline exists in shared `@posthog/core` — `packages/core/src/logs/index.ts` (`PostHogLogs.captureLog()`, capture-time gating in spec order, tumbling-window rate cap, FIFO oldest-eviction overflow, persisted queue, exponential-backoff retry, genuine 413 batch-halving retry) and `packages/core/src/logs/logs-utils.ts` (`getOtlpSeverityNumber`/`getOtlpSeverityText`, `toOtlpAnyValue`, `buildOtlpLogRecord`). The transport, `PostHogCoreStateless._sendLogsBatch()` (`packages/core/src/posthog-core-stateless.ts:1613-1656`), correctly POSTs to `${host}/i/v1/logs?token=...`, gzips the payload, and classifies 413 as non-retryable/`too-large`. One minor wire-format deviation: integers are encoded as JSON numbers (`{ intValue: 42 }`) rather than the spec's canonical stringified int64 (`{ "intValue": "4999" }`) — the spec does note the server also accepts a JSON number, so this isn't an interop break. **The critical gap: none of this is wired into `packages/node`.** `grep -rn "captureLog\|PostHogLogs\|LogsHost\|LogsConfig" packages/node/src` returns zero matches; `packages/node/src/exports.ts` re-exports `Metrics`/`MetricsConfig` from `@posthog/core` but nothing from `logs`; there is no `public get logger()` getter on `PostHogBackendClient` analogous to the existing `public get metrics()` getter (`client.ts:528-534`) that *does* wire up the sibling `PostHogMetrics` class. By contrast, `packages/browser/src/posthog-logs.ts` and `packages/react-native/src/posthog-rn.ts` do instantiate `PostHogLogs`. A Node application cannot call `captureLog` today even though the transport layer is present on every Node client instance (`PostHogBackendClient extends PostHogCoreStateless`).
- **Backwards compatibility:** Backward-compatible — instantiating `PostHogLogs` and exposing it via a new lazy getter/method on `PostHogBackendClient`, mirroring the existing `metrics` getter pattern, is purely additive.
- **Remediation:** Add a `captureLog()` method or `logger`/`logs` getter to `packages/node/src/client.ts` that constructs `PostHogLogs` against the already-present `_sendLogsBatch` transport, the same way `metrics` is wired up today.

### n2 — Traces (❌ Fail)
- **Spec requires:** A `startSpan`/`withSpan` API producing OTLP spans shipped to `POST {host}/i/v1/traces`, explicitly distinct from LLM-analytics-as-events, requiring no OpenTelemetry runtime dependency. (No acceptance `.feature` file exists for this contract.)
- **SDK currently:** Exhaustive grep for `startSpan`/`withSpan`/`/i/v1/traces`/`traceparent`/`getActiveSpan` across `packages/core/src`, `packages/browser/src`, `packages/react-native/src`, and `packages/node/src` returns zero matches anywhere in the monorepo. What exists instead is exactly the substitute the spec explicitly excludes: (a) LLM analytics captured as `$ai_generation`/`$ai_trace_id` ordinary analytics events; and (b) `packages/ai/src/otel/{exporter,processor}.ts`, which posts OTel spans to `${host}/i/v0/ai/otel` (not `/i/v1/traces`), only for `gen_ai.*` AI-semantic-convention spans, and depends on real `@opentelemetry/sdk-trace-base`/`@opentelemetry/exporter-trace-otlp-http` packages — the exact OTel runtime dependency the spec says the canonical implementation must avoid. This AI/OTel bridge lives in the separate `packages/ai` package, which `packages/node`'s `package.json` does not even depend on. The spec itself notes this capability "precedes the first SDK implementation" — no SDK in this monorepo (node, browser, react-native) implements it yet, so this is a monorepo-wide gap, not a node-specific regression.
- **Backwards compatibility:** Backward-compatible — a net-new subsystem; no removal needed.
- **Remediation:** Implement a dependency-free `startSpan`/`withSpan` API shipping OTLP spans to `/i/v1/traces` in `@posthog/core`, wired into `packages/node` (and browser/react-native), independent of the `packages/ai` OTel bridge.

### n3 — Tracing Headers (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side responsibilities: request-scoped middleware extracting `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` case-insensitively; sanitize (trim/strip control chars/cap length); explicit call-site values take precedence over context; personless-capture fallback (random `distinct_id` + `$process_person_profile=false`) unless the caller explicitly supplied that property; flag-evaluation APIs no-op/return-empty when no identity is resolvable; per-request isolation; headers never used for auth.
- **SDK currently:** Server-side consumption is real and well-tested. `packages/node/src/extensions/context/context.ts` implements genuine `AsyncLocalStorage`-based per-request isolation. `packages/node/src/extensions/tracing-headers.ts` (`getPostHogTracingHeaderValues`, lines 11-13) reads `x-posthog-session-id`/`x-posthog-distinct-id` (Node's `IncomingHttpHeaders` is always lowercased, so case-insensitivity is structurally guaranteed); `sanitizeTracingHeaderValue` strips control chars, trims, caps at exactly 1000 chars (`TRACING_HEADER_MAX_LENGTH`, line 3), treats post-sanitize-empty as missing. Two real framework integrations wire this into request context: `packages/node/src/extensions/express.ts` (`setupExpressRequestContext`/`posthogErrorHandler`, always calls `next(error)`, never swallows) and `packages/node/src/extensions/nestjs.ts` (`PostHogInterceptor`, fresh context per request, always rethrows on exception capture) — broader framework coverage than posthog-python's Django/Celery-only pair. Capture precedence is correct: `client.ts:_prepareEventMessage` (~lines 2785-2826) has explicit `distinctId` win over context, and explicit properties win over context properties. Personless fallback matches spec shape (`client.ts:2819-2822`: synthesize `uuidv7()` + `$process_person_profile=false`) — but this assignment is **unconditional**, executed after the property spread, so it overwrites any caller-supplied `$process_person_profile` value rather than only applying "unless the caller explicitly supplied that property" as the spec specifies — a real, narrow deviation. Flag-evaluation no-op-when-no-identity is correctly implemented on the modern API surface (`getAllFlags`, `getAllFlagsAndPayloads`, `evaluateFlags`, `getFeatureFlagResult` all resolve via `_resolveDistinctId`, `client.ts:1057-1065`, and return early with no network call and no `$feature_flag_called` when unresolvable — confirmed by tests `evaluate-flags.spec.ts:261,267`). Gap: the deprecated-but-still-shipped legacy API surface (`getFeatureFlag`, `isFeatureEnabled`) requires `distinctId` as a mandatory positional argument with no context-fallback and no no-op path — mirrors posthog-python's identical n3 finding.
- **Backwards compatibility:** Backward-compatible — adding an options-overload with context-fallback to the legacy `getFeatureFlag`/`isFeatureEnabled` methods, and fixing the personless-fallback to respect a caller-supplied `$process_person_profile`, are both additive/narrowing fixes.
- **Remediation:** Add optional-`distinctId`-with-context-fallback support to `getFeatureFlag`/`isFeatureEnabled`; guard the personless-fallback assignment in `_prepareEventMessage` with a check for an already-present `$process_person_profile` property.

### n4 — Alias (🟡 Partial)
- **Spec requires:** `both` applicability. Validate inputs — both the existing distinct id and the alias target id must be present; if either is missing, drop the call with zero enqueued events and a validation warning (acceptance scenario "Alias is dropped when required identities are missing," tagged `@both`).
- **SDK currently:** `alias()`/`aliasImmediate()` (`packages/node/src/client.ts:941-984`) build the correct `$create_alias` event shape (`properties: { distinct_id, alias }`) for the happy path, matching the `@both`-tagged happy-path scenario exactly. But there is no validation of `data.distinctId`/`data.alias` for emptiness anywhere in the method. Both flow through the shared `_prepareEventMessage` (`client.ts:~2785-2822`), where a falsy `distinctId` is silently replaced with a synthesized `uuidv7()` and the event is enqueued anyway with `$process_person_profile: false` — rather than being dropped with a validation warning as the acceptance scenario requires.
- **Backwards compatibility:** Backward-compatible — adding an emptiness check that logs a warning and returns early is additive; it only changes behavior for a currently-malformed call that today silently mutates the distinct id instead of failing loudly.
- **Remediation:** In `alias()`/`aliasImmediate()`, validate that `data.distinctId` and `data.alias` are both present and non-empty before building the event; log a warning and return without enqueuing otherwise.

### n5 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Enrich events with `distinct_id`/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; honor an opt-out state so capture is silently dropped with no network call; validate that `event` and `distinct_id` are non-empty; support a `before_send` hook that can mutate/drop events, with hook exceptions logged and the original message used as a fallback (not the event being dropped).
- **SDK currently:** `capture()` (`client.ts:713-720`) is fire-and-forget and never throws. Enrichment is complete and correct: `$lib`/`$lib_version`/`$is_server` (`client.ts:574-582`), timestamp/uuid defaulting with override support, `$groups` (`client.ts:2900-2908`), `$process_person_profile=false` fallback for missing distinct id. A genuine dynamic opt-out **does** exist (`optIn()`/`optOut()` on `PostHogCoreStateless`, exposed as `enable()`/`disable()` on the Node client), checked in `enqueue()`/`sendImmediate()` with silent no-op and no network call — notably more complete than posthog-python, which the sibling audit found lacks any dynamic opt-out API at all. Gaps: (1) no runtime validation of `event`/`distinct_id` non-emptiness anywhere — an empty-string `event` flows straight through to the wire, and a falsy `distinctId` is silently replaced with a synthesized UUID rather than triggering a validation warning; (2) `before_send` hook exceptions are not caught at the Node-specific hook-invocation site (`client.ts:2935-2957`, `_runBeforeSend`, distinct from the try/catch-wrapped version in `PostHogCore` used only by browser/react-native) — an uncaught exception propagates up and is only caught one layer above by a generic `.catch` in `_sendPreparedEvent`, which drops the entire event via a bare `console.error` rather than falling back to the original, unmutated message as the spec requires ("An exception inside the callback is logged and the original message is used").
- **Backwards compatibility:** Backward-compatible — adding event/distinct_id validation and fixing the before_send exception path to preserve the original message (rather than dropping) are both additive/bug-fix-shaped changes with no public signature impact.
- **Remediation:** Add non-empty validation for `event` and `distinct_id` with a logged warning on failure; wrap the Node-specific `_runBeforeSend`'s hook invocation in its own try/catch that falls back to the pre-hook message on exception, matching `PostHogCore`'s existing browser/RN behavior.

### n6 — Capture Exception (🟡 Partial)
- **Spec requires:** `captureException(error, properties?)` emits a `$exception` event with correctly-ordered `$exception_list` (outermost/caught-first, root-cause-last), correctly-ordered stack frames (entry-point-first), ascending source-context lines, preserved (not synthesized) stack traces when available, and flat `$exception_type`/`$exception_message` top-level properties. Spec's own applicability line says `client`, but the acceptance feature `capture-exception.feature` is tagged `@both` on every scenario — treated as in-scope per acceptance-tag precedence, consistent with the sibling posthog-python audit's n5 treatment and node's own mature investment in this feature.
- **SDK currently:** `ErrorPropertiesBuilder.convertToExceptionList` (`packages/core/src/error-tracking/error-properties-builder.ts:102-129`) correctly orders `$exception_list` (caught exception first, recursively appending `.cause`, root cause last). `createStackParser` (`packages/core/src/error-tracking/parsers/index.ts:69-107`) reverses JS's native crash-site-first `Error.stack` ordering via `reverseAndStripFrames`, correctly producing entry-point-first ordering. `addContextToFrame` (`packages/node/src/extensions/error-tracking/modifiers/context-lines.node.ts:292-336`) builds strictly-ascending `pre_context`/`post_context` windows. `ErrorCoercer.getStack()` and `ObjectCoercer.coerce()` both check for an existing `.stacktrace`/`.stack` before any synthesis fallback, preserving real traces. Caller-supplied properties correctly win on collision (`ErrorTracking.buildEventMessage`, `packages/node/src/extensions/error-tracking/index.ts:45-73`). **Gap:** `ErrorPropertiesBuilder.buildFromUnknown()` (`error-properties-builder.ts:29-44`) returns only `{ $exception_list, $exception_level }` — no flat `$exception_type`/`$exception_message` are ever added on the standard `captureException()` path. These flat properties exist only in the unrelated `packages/node/src/extensions/sentry-integration.ts` (a separate Sentry-event-to-PostHog-event adapter, lines 137-145), not on the primary exception-capture path. This directly contradicts the `@both`-tagged acceptance scenario "Capturing a handled exception emits an exception event," which requires `$exception_type=TypeError`/`$exception_message=boom` as flat, top-level properties.
- **Backwards compatibility:** Backward-compatible — adding `$exception_type`/`$exception_message` as flat properties sourced from `$exception_list[0].type`/`.value` is additive and doesn't remove or rename anything currently emitted. Note: posthog-python's audit found these properties were deliberately *removed* there in a changelogged fix, suggesting worth confirming with the ingestion/product team whether these are still expected before re-adding to both SDKs.
- **Remediation:** Add `$exception_type: exceptionList[0]?.type` and `$exception_message: exceptionList[0]?.value` as flat top-level properties in `ErrorPropertiesBuilder.buildFromUnknown()` or `ErrorTracking.buildEventMessage()`.

### n7 — Debug (✅ Pass)
- Spec's own applicability line says `client` ("the audited public runtime `debug(...)` toggle is a client-side SDK surface"), and the acceptance file (`acceptance/public/debug.feature`) is tagged `@client` throughout with no scenario-level override. However, posthog-node genuinely implements the exact behavior the spec describes: `debug(enabled: boolean = true): void` is explicitly overridden at `packages/node/src/client.ts:639-642` (`super.debug(enabled); this.featureFlagsPoller?.debug(enabled)`), building on `PostHogCoreStateless.debug()` (`packages/core/src/posthog-core-stateless.ts:447-455`, installs/removes a wildcard `on('*', ...)` internal-event logger with no capture/network side effects). This mechanically satisfies all 3 acceptance scenarios: runtime enable/disable toggle works; no event is enqueued and no network request is sent when toggled; defaults to `true` when called with no argument. Node additionally forwards the toggle to the feature-flag poller for flag-polling diagnostics — a superset of the spec's baseline. Recorded as ✅ (implemented beyond the spec's own stated `client` scope) rather than ➖, following the same "implemented-beyond-carve-out" treatment applied to Set Person Properties (row 34) — the contract genuinely exists and works, so it shouldn't be marked not-applicable.

### n8 — Flush (🟡 Partial)
- **Spec requires:** `@both`. No-op on empty queue with no network call; bypass batching intervals and drain immediately; on delivery failure the failed batch must remain queued for a later retry, not silently dropped.
- **SDK currently:** `flush()` (`client.ts:270-282`) is correctly a no-op on an empty queue and drains the entire queue across as many sequential batches as needed (`_flushRoute`, `posthog-core-stateless.ts:1528-1600`). On the **v0** pipeline, a retryable failure (e.g. persistent 503) correctly skips `persistQueueChange()` so events remain queued (`posthog-core-stateless.ts:1586-1594`) — matches spec. **On the v1 pipeline, this guarantee is broken**: `V1CaptureSender.sendV1Batch` (`packages/node/src/capture-v1/sender.ts:68-71`) never throws for a handled outcome — even after exhausting its retry budget, it calls `onError()` (an emitted event) and resolves normally. Because `_flushRoute`'s `await this.sendBatch(...)` doesn't throw for the v1 analytics route, `persistQueueChange()` unconditionally runs and evicts the batch from the queue as if delivered, even when delivery ultimately failed (e.g. a persistent 503, or 429 which v1 treats as terminal/non-retryable per `sender.ts:19`'s `RETRYABLE_STATUSES`). This directly contradicts "Flush keeps events retryable when delivery fails" whenever a v1-mode client exhausts its retry budget.
- **Backwards compatibility:** Needs deprecation path — fixing v1 to re-throw on exhausted retry (so `_flushRoute` preserves the queue) changes v1's currently-documented "never throws" error-surfacing contract, which downstream code/tests may depend on; should be rolled out carefully, not as a silent behavior change.
- **Remediation:** Make `V1CaptureSender.sendV1Batch` propagate a retryable failure signal (e.g. throw or return a discriminated failure result) when its own retry budget is exhausted, so `_flushRoute` can correctly preserve the batch in the queue instead of treating it as delivered.

### n15 — Shutdown (🟡 Partial)
- **Spec requires:** `@both`. Flush pending events, stop workers permanently, **reject/no-op future captures**, be idempotent, not crash on delivery failure.
- **SDK currently:** `shutdown()`/`_shutdown()` (`client.ts:2451-2482`) correctly flushes first, then stops the feature-flag poller, clears the flush timer, and drains both `analytics`/`ai` queue routes in v1 mode.
