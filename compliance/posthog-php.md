Note on repo layout: posthog-php is a single-package, server-only SDK (`composer.json` name
`posthog/posthog-php`, PSR-4 root `lib/` → namespace `PostHog\`). Key files: `lib/Client.php`
(the main instance API: `capture`, `identify`, `alias`, `captureException`, the deprecated
single-flag getters `isFeatureEnabled`/`getFeatureFlag`/`getFeatureFlagResult`/
`getFeatureFlagPayload`, the current `evaluateFlags()` + `FeatureFlagEvaluations` snapshot API,
`getAllFlags`, `loadFlags`/local-evaluation state, `withContext`/`getContext` request-scoped
identity, `flush`/`shutdown`); `lib/PostHog.php` (static facade wrapping a lazily-constructed
default `Client`, adds `groupIdentify`); `lib/FeatureFlag.php` (local rule-matching engine —
property filters, rollout hashing, cohorts, flag dependencies); `lib/FeatureFlagEvaluations.php` /
`lib/EvaluatedFlagRecord.php` (per-request flag snapshot with deduped `$feature_flag_called`
tracking); `lib/RequestContext.php` (per-`Client`, per-Fiber context stack — the mechanism behind
`withContext()`/tracing-header extraction; a `reset()` static exists only as a test helper, not a
public reset API); `lib/HttpClient.php` (curl-based transport, retry/backoff, ETag capture,
`Retry-After` honoring); `lib/QueueConsumer.php` + `lib/Consumer/{LibCurl,Socket,File,ForkCurl,NoOp}.php`
(batching/flush/retry — PHP has no portable background timer, so `flush_interval_seconds` is
checked opportunistically on each `enqueue()`); `lib/ExceptionCapture.php` +
`lib/ExceptionPayloadBuilder.php` (global error/exception/shutdown handlers and `$exception_list`
construction); `lib/FlagDefinitionCacheProvider.php` (interface for sharing downloaded flag
definitions across workers). There is no disk-backed event queue, no ambient identity, and no
session/replay/consent state anywhere in the package.

## Notes

### n1 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Enrich events with `distinct_id`/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; run `before_send`; and — per the `@both`-tagged acceptance scenario "Capture honors opt-out state" (`acceptance/public/capture.feature:46-51`) — silently drop the event with **no network call** while opted out.
- **SDK currently:** `Client::capture()` (`lib/Client.php:410-498`) correctly resolves identity via `RequestContext`/`applyCaptureContext()` (`lib/Client.php:2246-2285`), stamps `$lib`/`$lib_version`/`$lib_consumer`/`$is_server` (`message()`, `lib/Client.php:2328-2395`), assigns timestamp/uuid, merges `$groups`, and runs `before_send` (`applyBeforeSend()`, `lib/Client.php:510-545`) — all correct. But there is **no opt-out mechanism of any kind**: `grep -rniE "opt_?out|opt_?in"` across `lib/` returns zero matches. The only capture-suppressing flag is `$enabled` (`lib/Client.php:199`), which is set exactly once in the constructor from API-key presence (`$this->enabled = $this->apiKey !== '';`, line 276) and is never reassigned anywhere else in the class — confirmed by `grep -n "enabled" lib/Client.php`, which shows only reads, never a second write. There is no way for a caller to opt an already-constructed client in or out at runtime; the disabled/no-op consumer path exists only for a missing/blank API key, not for a live app's runtime consent decision.
- **Backwards compatibility:** Backward-compatible — adding `optOutCapturing()`/`optInCapturing()`/`isOptedOut()` methods plus a mutable internal flag checked at the top of `capture()`/`identify()`/`alias()`/flag-evaluation paths is purely additive.
- **Remediation:** Add a runtime-mutable opt-out flag and `Client::optOutCapturing()`/`optInCapturing()`/`isOptedOut()` (and matching `PostHog::` facade methods), checked before enqueue in `capture()`, `identify()`, `alias()`, `captureException()`, and the flag-evaluation capture-side-effect paths.
- **Second gap this cycle (new requirement):** the `capture` spec gained "Capture drops null-valued object properties" (`openspec/specs/capture/spec.md:230`), which requires recursively omitting object members whose value is an explicit null before wire/disk serialization while leaving null *array elements* at their original indices. PHP does no such cleanup: `Client::message()` (`lib/Client.php:2328`) and the consumers (`lib/Consumer/LibCurl.php`, `Socket.php`, `ForkCurl.php`) hand the properties map straight to `json_encode`, so `["test" => null]` is serialized as `{"test":null}`. `grep -n "stripNull\|dropNull\|removeNull" lib/` returns nothing. UTC timestamp normalization — the other requirement added to this spec this cycle — **is** satisfied: `formatDateTime()` (`lib/Client.php:2157-2163`) coerces every timestamp to `UTC` and preserves microsecond precision only when present.
- **Backwards compatibility (null-property drop):** Backward-compatible — a recursive serializer-side filter changes only the wire bytes for properties that are already semantically absent; the public signature keeps accepting nulls.
- **Remediation (null-property drop):** Add a recursive `stripNullObjectMembers()` applied in `message()` after `before_send`, descending into nested maps and into maps nested inside lists, leaving list elements (including nulls) positionally intact.

### n3 — Evaluate Flags (🟡 Partial)
- **Spec requires:** `openspec/specs/evaluate-flags/spec.md` — a server SDK exposing `evaluateFlags(...)` must, under "Evaluation identity, inputs, and data sources" (spec line 46), *retain negative knowledge* for a requested key absent from both the loaded local definitions and a clean remote fallback response, in a finite-capacity in-memory store, cleared after every successful local-definition refresh, so that a permanently deleted key costs at most one clean fallback per definitions-refresh interval. It must also coordinate concurrent evaluations that overlap on the same unknown missing key onto one in-flight existence probe. Separately, "Snapshot payload access" (spec line 226) requires malformed/empty/whitespace-only serialized payloads to be **logged** and treated as absent.
- **SDK currently:** the core of the contract is implemented well. `Client::evaluateFlags()` (`lib/Client.php:1079-1272`) distinguishes a null key list from an explicitly empty one (`if ($flagKeys === []) { return new FeatureFlagEvaluations(...); }`, line 1188), scopes the `/flags` request to the requested keys, makes at most one remote request, and never lets a remote value overwrite a locally resolved one (`if (... isset($records[$key])) { continue; }`, line 1216). `FeatureFlagEvaluations` (`lib/FeatureFlagEvaluations.php`) implements lazy access tracking, `only()`/`onlyAccessed()` in-memory filtering with no I/O, a silent `getFlagPayload()`, and the `flag_missing` error path. Two gaps: (1) **no negative-knowledge retention or probe coordination exists at all** — when `$flagKeys` contains a key with no local definition, `$fallbackToRemote` is set unconditionally (`lib/Client.php:1181-1187`) on *every* call, so a deleted-but-still-requested key causes one `/flags` round trip per evaluation forever; `grep -rn "omission\|negativeKnowledge\|missingKey" lib/` returns nothing. (2) malformed serialized payloads are decoded with a bare `json_decode($rawPayload, true)` (`lib/Client.php:1230` for the remote path, `lib/Client.php:1358` in `localFlagPayload()`), which does return `null` for `"{broken"`, `""`, and `"   "` — the correct absent-payload sentinel, and it does not throw — but nothing is logged, so the operator gets no diagnostic.
- **Backwards compatibility:** Backward-compatible — both fixes are internal. A bounded missing-key store keyed to the definitions generation is new private state; adding a `warn()` call on a failed decode changes only diagnostics, and the returned value is already correct.
- **Remediation:** Add a finite-capacity per-`Client` missing-key set stamped with the flag-definition generation counter, consulted before setting `$fallbackToRemote` for a locally-undefined requested key, cleared in the definition-refresh success path (including `304`/shared-cache hydration), and never populated from a quota-limited or errors-while-computing response. Separately, replace the two bare `json_decode` calls with a helper that calls `$this->warn(...)` when `json_last_error() !== JSON_ERROR_NONE` and returns `null`.

### n4 — Event Batcher (🟡 Partial)
- **Spec requires:** `both`. Accumulate events; flush at a count threshold (`flushAt`) or on an interval timer (`flushInterval`); cap batch payload size; preserve FIFO order; explicit flush/shutdown drains immediately; spec item 11 notes "some SDKs" shrink the batch and retry on HTTP 413.
- **SDK currently:** `QueueConsumer` (`lib/QueueConsumer.php`) implements threshold flush (`batch_size`, default 100) and interval flush (`flush_interval`, default 5.0s) correctly — but because "PHP has no portable in-process background timer" (the class's own doc comment, `lib/QueueConsumer.php:10-12`), the interval check is only evaluated opportunistically inside `enqueue()` (`flushIntervalElapsed()`, checked at `lib/QueueConsumer.php:177`) rather than by a real timer/thread; a queue that receives no further `capture()` calls after the interval elapses will not flush until the next event arrives, `flush()`, or `shutdown()`/`__destruct()`. This is a reasonable, explicitly-documented PHP-process-model accommodation rather than a bug, but it is a real deviation from "trigger flush by timer" (spec item 4) taken literally. FIFO order is preserved (`array_slice`/`array_splice` from the front, `lib/QueueConsumer.php:141,146`); a pre-flight 1MB payload-size cap exists (`MAX_BATCH_PAYLOAD_SIZE`, `lib/QueueConsumer.php:18`, checked in each `Consumer\*::flushBatch()`); explicit `flush()`/destructor-time drain both work. No adaptive batch-shrink-and-retry on HTTP 413 exists (413 is correctly classified as non-retryable, so this is the same optional, "some SDKs"-only gap independently noted for posthog-python/posthog-ios, not a hard miss).
- **Backwards compatibility:** Backward-compatible — introducing a real timer (e.g. via a PSR-based event loop or an opt-in `register_tick_function`) would be additive and does not change the current opportunistic-check default.
- **Remediation:** Document the opportunistic-timer behavior clearly in public API docs (it is already documented internally); consider an opt-in true-timer mode for long-running PHP processes (queue workers, daemons) where events may not be enqueued frequently enough to trigger the opportunistic check.


### n5 — Exception Event Metadata (❌ Fail)
- **Spec requires:** `openspec/specs/exception-event-metadata/spec.md` — every entry in `$exception_list` carries a `mechanism` with a unique non-negative `exception_id`; nested entries carry `parent_id`, `mechanism.type = "chained"`, and a `mechanism.source` naming the relationship; `mechanism.handled` is serialized only where the boundary actually knows it and is **never** copied or inferred for nested entries; `mechanism.synthetic` is set per-entry when provenance is known and omitted otherwise; `$exception_level` carries one of `fatal`/`error`/`warning`/`log`/`info`/`debug` from the boundary default table; `$exception_source` uses the canonical first-party identifiers, which for this platform are exactly `php.exception_handler`, `php.error_handler`, and `php.shutdown_handler`.
- **SDK currently:** almost none of the envelope is implemented. `ExceptionPayloadBuilder::buildSingleException()` (`lib/ExceptionPayloadBuilder.php:196-208`) emits a fixed `['type' => 'generic', 'handled' => true]` mechanism for **every** entry, with no `exception_id`, no `parent_id`, and no `synthetic`. `buildExceptionList()` (`lib/ExceptionPayloadBuilder.php:24-44`) walks `getPrevious()` into a flat chain, so each cause inherits that literal `handled: true` and `type: generic` — the spec's "MUST NOT copy, invert, or otherwise derive the value solely from the outermost entry" and "every nested exception reached through another entry SHALL use `chained`" are both violated, and no linkage field ties a cause to its parent. `overridePrimaryMechanism()` (`lib/ExceptionPayloadBuilder.php:99-110`) only ever rewrites index 0. The automatic handlers use non-canonical vocabulary in both places: `mechanism.type` is `auto.exception_handler` / `auto.error_handler` / `auto.shutdown_handler` (`lib/ExceptionCapture.php:369-373, 184, 205, 273`) instead of a canonical category, and `$exception_source` is `php_exception_handler` / `php_error_handler` / `php_shutdown_handler` (underscores; `lib/ExceptionCapture.php:376, 184-186, 270-274, 425`) instead of the dotted canonical values the spec's first-party table mandates. `$exception_level` is never emitted anywhere — `grep -rn 'exception_level' lib/` returns nothing; the error handlers instead attach a PHP-specific `$php_error_severity` integer (`lib/ExceptionCapture.php:428-430`). There is no aggregate-member/entry truncation budget. The manual path (`Client::captureException()`, `lib/Client.php:581-583`) correctly omits `$exception_source` and correctly marks the outermost entry handled, which is the one part of the contract it satisfies.
- **Backwards compatibility:** Needs deprecation path — `$exception_source` and `mechanism.type` string values are already being emitted and are likely used in saved filters and issue-grouping rules, so renaming them to the canonical vocabulary changes data consumers see. Adding `exception_id`/`parent_id`/`synthetic`/`$exception_level` and omitting nested `handled` is purely additive and can ship immediately; the two renames should ship alongside, with the old values documented as replaced in a release note.
- **Remediation:** (1) Assign `mechanism.exception_id` sequentially in `buildExceptionList()` and set `parent_id` plus `mechanism.type = "chained"` and `mechanism.source = "cause"` on every `getPrevious()` entry. (2) Stop emitting `handled` from `buildSingleException()`; let only the capture boundary set it on entry 0 via `overridePrimaryMechanism()`. (3) Set `synthetic: true` on entries built by `buildFromLocation()` (a synthesized single-frame stack) and `false` on entries built from a real `Throwable` trace. (4) Rename `$exception_source` values to `php.exception_handler` / `php.error_handler` / `php.shutdown_handler` and `mechanism.type` to the canonical boundary categories. (5) Add `$exception_level` — `error` for the manual and error-handler paths, `fatal` for the shutdown/terminating path — derived from the existing `$severity` where one is known.

### n6 — Feature Flag Called Tracker (🟡 Partial)
- **Spec requires:** Dedup `$feature_flag_called` by `(flag, value, distinct_id, normalized groups)`; clear on shutdown; minimal-event mode gated by `minimalFlagCalledEvents`/`has_experiment===false`, with an allowlist that — per the most recent sdk-specs fix (commit `b59e8b4`, `fix(feature-flag-called-tracker): add session-attribution properties to minimal-event allowlist`) — includes the session-attribution properties (`$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid`) in addition to flag-identity/debug/session/platform properties, while still excluding `$referrer`.
- **SDK currently:** `Client::MINIMAL_FLAG_CALLED_EVENT_PROPERTIES` (`lib/Client.php:32-49`) contains exactly 16 entries (`$feature_flag`, `$feature_flag_response`, `$feature_flag_has_experiment`, `$feature_flag_id`, `$feature_flag_version`, `$feature_flag_reason`, `$feature_flag_request_id`, `$feature_flag_evaluated_at`, `$feature_flag_error`, `locally_evaluated`, `$groups`, `$process_person_profile`, `$session_id`, `$lib`, `$lib_version`, `$is_server`) — the flag-identity/debug/session/platform categories, but **zero session-attribution properties**. It is missing all 10 of `$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid` — the exact same gap class independently found in posthog-python and posthog-node. Everything else matches the spec precisely and is well-tested: dedup key construction combining `distinctId` + response + canonicalized (sorted-by-key, JSON-encoded) groups (`captureFlagCalledIfNeeded()`/`canonicalGroupsRepr()`, `lib/Client.php:1242-1290`); fail-safe-to-full-event gating requiring both the server gate and an explicit `has_experiment === false` (`shouldSendMinimalFlagCalledEvent()`, `lib/Client.php:528-533`); the gate persisting through `normalizeFlagDefinitionData()`/`normalizeFlagDefinitionCacheData()` so it survives external cache-provider round-trips and 304 responses (`lib/Client.php:1543,1580`); and shutdown-time dedupe-cache clearing (`Client::shutdown()` replaces `distinctIdsFeatureFlagsReported` with a fresh `SizeLimitedHash`, `lib/Client.php:358`). Note: PHP has no super-property registration mechanism at all (no `register()`), so there is currently no code path that would attach UTM/click-id values to an event in the first place — but the allowlist itself should still be forward-looking/complete per the spec's own reference-implementation note, matching how the parallel posthog-ios audit reasoned about the same absence.
- **Backwards compatibility:** Backward-compatible — adding 10 keys to a strip-allowlist array is strictly additive; it can only cause minimized events to retain more properties than before, never fewer.
- **Remediation:** Add the 10 session-attribution property names from sdk-specs commit `b59e8b4` to `Client::MINIMAL_FLAG_CALLED_EVENT_PROPERTIES` (`lib/Client.php:32-49`).


### n7 — Flag Definition Loader (🟡 Partial)
- **Spec requires:** `both`, with acceptance file `acceptance/private/flag-definition-loader.feature` tagged `@server`. Fetch/cache local-evaluation flag definitions from a privileged endpoint; ETag-based conditional fetches; external/shared cache-provider integration (sync and async); quota/auth error handling; and — per the explicit scenario "Loader refreshes after polling interval" — a background poll loop that refreshes definitions once a configured interval elapses, without an application call being the trigger.
- **SDK currently:** Everything except background polling is implemented and tested precisely: `Client::loadFlags()` (`lib/Client.php:1409-1453`) fetches from `/flags/definitions?send_cohorts&token=...` with `Authorization: Bearer <secretKey>` (`localFlags()`, `lib/Client.php:1677-1709`); ETag is captured and sent as `If-None-Match` (`lib/Client.php:1697-1699,1522`), and a `304` response preserves existing definitions while optionally refreshing the stored ETag (`fetchAndApplyFlagDefinitionsFromApi()`, `lib/Client.php:1490-1498`); the `FlagDefinitionCacheProvider` interface (`lib/FlagDefinitionCacheProvider.php`) supports external/shared caches with `shouldFetchFlagDefinitions()`/`getFlagDefinitions()`/`onFlagDefinitionsReceived()`/`shutdown()`, all called defensively with provider-failure fallback to a direct fetch (`lib/Client.php:1417-1448`), matching every scenario in the acceptance file (sync/async provider results, provider read/fetch-decision/shutdown failures) per `test/FlagDefinitionCacheProviderTest.php` and `test/EtagSupportTest.php`. However, `loadFlags()` is called once at `Client` construction (if a secret key is configured, `lib/Client.php:304-311`) and otherwise only on an explicit application call to `Client::loadFlags()` — there is **no poll loop or timer** anywhere in the codebase (`grep -n "polling\|poll_interval\|background"` finds only doc-comment references to PHP's lack of a portable background timer, `lib/QueueConsumer.php:10`, `lib/Client.php:209`, `lib/PostHog.php:33`). This is a defensible consequence of PHP's typical short-lived-request execution model (unlike a long-running Python/Node/Ruby process, a PHP request usually doesn't stay alive long enough for polling to matter, and the external cache-provider interface is the documented multi-worker alternative), but it is a literal, acceptance-scenario-visible gap against the spec's "Start and maintain a poll loop" behavior item.
- **Backwards compatibility:** Backward-compatible — adding an opt-in polling helper (e.g. a method applications can wire into a long-running worker's event loop or a cron-style external trigger) would be additive; the current one-shot/manual-refresh model would remain the default.
- **Remediation:** Document the intentional one-shot/manual-refresh design for PHP's request lifecycle explicitly (distinguishing it from long-running-process SDKs); optionally add an opt-in polling helper for PHP daemons/queue workers that do stay alive across requests.
- **Re-verified this cycle:** the spec added "Definition snapshots retain the property matching version" and "Holdout metadata survives definition loading and caching". The first is **satisfied** — `FlagDefinitionCacheProvider` (`lib/FlagDefinitionCacheProvider.php:12-52`) documents and round-trips `property_matching_version` as part of one snapshot, and `Client::flagDefinitionSnapshot()` hands it to every `computeFlagLocally()` call site (`lib/Client.php:805-812, 1021-1032, 1140-1155`). The second is **satisfied at the loader layer**: the loader stores raw definition arrays, so `filters.holdout.id` and `filters.holdout.exclusion_percentage` survive fetch, cache write, and cache hydration untruncated. The evaluator then ignores them — tracked as a separate defect under [n12], not here.

### n8 — Get Feature Flag Payload (🟡 Partial, downgraded from ✅)
- **Spec requires:** `openspec/specs/get-feature-flag-payload/spec.md:161` ("Malformed serialized payloads return no payload", added this cycle) — a malformed, empty, or whitespace-only serialized payload must return the language's no-payload sentinel, must not return the raw string, must not throw, and **"Parse failures SHALL be logged through SDK diagnostics."**
- **SDK currently:** the value behavior is already correct. `Client::getFeatureFlagPayload()` resolves through `FeatureFlagResult::getPayload()` (`lib/Client.php:986`) and the two decode sites are bare `json_decode($rawPayload, true)` calls — `lib/Client.php:863` (remote) and `lib/Client.php:1358` (`localFlagPayload()`, local evaluation). PHP's `json_decode` without `JSON_THROW_ON_ERROR` returns `null` for `"{broken"`, `""`, and `"   "` and never throws, so the caller gets `null` — the same sentinel as a known flag with no payload — and never the raw string. `localFlagPayload()` also correctly avoids double-decoding an already-decoded value (`is_string($rawPayload) ? json_decode(...) : $rawPayload`). The single unmet clause is diagnostics: neither site inspects `json_last_error()` and nothing is written to the SDK's warning channel, so a payload that silently stopped arriving is indistinguishable from a flag that has no payload configured.
- **Backwards compatibility:** Backward-compatible — logging is additive and the returned value already conforms; no caller-visible behavior changes.
- **Remediation:** Extract a private `decodePayload(?string $raw): mixed` that returns `null` and calls `$this->warn('feature flag payload is not valid JSON')` when `json_last_error() !== JSON_ERROR_NONE`, and route `lib/Client.php:863`, `lib/Client.php:1230`, and `lib/Client.php:1358` through it.

- **Backwards compatibility:** Backward-compatible — adding a new method (e.g. `Client::getAllFlagsAndPayloads()`) that internally calls `evaluateFlags()` and folds the snapshot into the two-map shape is purely additive.

### n10 — HTTP Client (🟡 Partial)
- **Spec requires:** The "Feature flag evaluation retry policy" requirement (hard `SHALL`) mandates that retries of the `/flags` endpoint use "exponential backoff starting at 300ms before the first retry, then 600ms before the second retry, doubling for each later retry," with a default budget of one retry (two total attempts), retrying only on transient transport failures and HTTP 502/504, never other status codes.
- **SDK currently:** `Client::sendFeatureFlagsRequest()` (`lib/Client.php:1887-1917`) gets the retry-eligibility classification exactly right — `isRetryableFlagsCurlError()` matches transient transport errors (curl errno 28/52/56 — timeout, connection reset, empty reply, `lib/Client.php:1931-1936`), `isRetryableFlagsStatusCode()` matches only HTTP 502/504 (`lib/Client.php:1938-1941`), and the default retry budget (`featureFlagRequestMaxRetries`, defaults to 1, `lib/Client.php:289`) matches the spec's "one retry after the initial attempt." However the **backoff timing constant is wrong**: `$backoff = 100` (`lib/Client.php:1889`, doubling thereafter, capped by `maximumBackoffDurationMs`) starts at 100ms, not the spec-mandated 300ms before the first retry (and 600ms before the second). This is confirmed by the doc comment on `PostHog::init()`/`Client::__construct()` itself, which documents "Retry backoff starts at 100ms and doubles" (`lib/Client.php:212-213`, `lib/PostHog.php:36-37`) as the intended, deliberate behavior, not an oversight — but it still deviates from the spec's explicit numeric requirement. The rest of the HTTP client (ingestion request auth/JSON payload, 200 = delivered, non-throwing retryable-failure reporting with events remaining queued, `Retry-After` honoring for ingestion in `HttpClient::retryAfterMilliseconds()`, `lib/HttpClient.php:218-241`) matches the spec's other scenarios correctly.
- **Backwards compatibility:** Backward-compatible — changing the initial backoff constant from 100ms to 300ms (and the second-retry delay to 600ms) is an internal timing change with no signature/behavior-contract change, though it will make flag-request retries take measurably longer under transient failure, which is worth a changelog callout for latency-sensitive integrations.
- **Remediation:** Change the initial backoff in `sendFeatureFlagsRequest()` (`lib/Client.php:1889`) from `100` to `300` so the schedule matches the spec's 300ms/600ms/… doubling sequence.


### n11 — Is Feature Enabled (❌ Fail)
- **Spec requires:** Hard `SHALL`, `both` applicability, explicitly documenting PHP's own current signature as the canonical shape with no carve-out: "The SDK SHALL accept a caller-supplied boolean default (`defaultValue`)... and SHALL return it whenever the flag has no value... A flag that has a value — including `false` and variant strings — always wins over the caller-supplied default."
- **SDK currently:** `Client::isFeatureEnabled()` (`lib/Client.php:615-649`) has **no `defaultValue`/`default_value` parameter at all** — its full signature is `isFeatureEnabled(string $key, ?string $distinctId = null, array $groups = [], array $personProperties = [], array $groupProperties = [], bool $onlyEvaluateLocally = false, bool $sendFeatureFlagEvents = true): null|bool`. The spec's own "Surface variants" table documents this exact signature verbatim for PHP (`openspec/specs/is-feature-enabled/spec.md:71`) with no `defaultValue` param, confirming the gap is real and current, not a stale spec artifact. On a missing/failed flag, the method unconditionally returns `null` (`doGetFeatureFlagResult()` returns `null` when `$result` is `null`, surfaced at `lib/Client.php:644-646`) — there is no way for a caller to make a missing flag resolve to `true`/`false` via this API. The module-level `PostHog::isFeatureEnabled()` facade (`lib/PostHog.php:249-268`) forwards the identical signature and has the identical gap.
- **Backwards compatibility:** Backward-compatible — adding an optional `?bool $defaultValue = null` parameter (returned only when the flag has no resolvable value) is purely additive and does not change behavior for existing callers who omit it.
- **Remediation:** Add a `defaultValue` parameter to `Client::isFeatureEnabled()` and `PostHog::isFeatureEnabled()`, returned only when `doGetFeatureFlagResult()` resolves to `null` (flag missing, not loaded, or a failed remote/local evaluation), with any present flag value (including `false`) still taking precedence.


### n12 — Local Feature Flag Evaluator (🟡 Partial, downgraded from ✅)
- **Spec requires:** `openspec/specs/local-feature-flag-evaluator/spec.md` grew substantially this cycle. Two new requirements land squarely on this SDK: "Experiment holdouts precede release conditions" (spec line 1012) — before evaluating release conditions, the evaluator must check `filters.holdout` and, when the bucketing identity falls inside the holdout, return the holdout outcome rather than the release-condition result — and "Holdout membership uses backend-compatible bucketing" (spec line 1048), which fixes the hash salt and comparison so SDK and backend agree on membership.
- **SDK currently:** the rest of the contract is in good shape, and several pieces landed since the last audit. `property_matching_version` is now threaded through the definition snapshot into `FeatureFlag::matchProperty()` (`lib/FeatureFlag.php:25`), with `computeExactMatch()` (`lib/FeatureFlag.php:608-628`) implementing both the legacy aggregate-truthiness gate (`$propertyMatchingVersion !== 2 && isTruthyOrFalsyPropertyValue($value)`) and the v2 explicit path, the vacuous empty-array `[]` case, and ANY-membership over independently stringified members — all using a dedicated `unicodeLowercase()` helper rather than ASCII `strtolower`, matching the spec's Rust-`to_lowercase` requirement. The ASCII-lowercase string-search family (`icontains`, `not_icontains`, `starts_with`, `not_starts_with`, `ends_with`, `not_ends_with`, `lib/FeatureFlag.php:53-75`) correctly uses PHP's byte-wise, locale-independent `strtolower`, which is exactly the ASCII-only behavior that requirement mandates. `is_set`/`is_not_set` presence semantics are correct: the `array_key_exists` guard at `lib/FeatureFlag.php:30-32` throws `InconclusiveMatchException` for an absent key before either operator is reached, `is_not_set` then returns `false` for a present key including an explicit null (`lib/FeatureFlag.php:35-37`), and `is_set` returns `true` for any present key regardless of truthiness (`lib/FeatureFlag.php:49-51`). **Holdouts are entirely absent:** `grep -rn "holdout" lib/ test/` returns zero matches across the whole repository, and `computeFlagLocally()` goes straight from the definition to the condition groups with no holdout gate. A flag configured with an experiment holdout will therefore be evaluated locally as if no holdout existed, silently disagreeing with the backend for every identity inside the holdout — a correctness divergence, not merely a missing feature.
- **Backwards compatibility:** Backward-compatible — holdout support reads `filters.holdout.id` and `filters.holdout.exclusion_percentage`, which already survive definition loading untouched because the loader stores raw definition arrays (see [n7]). Adding the gate changes evaluated values only for flags that actually carry a holdout, where the current value is wrong.
- **Remediation:** In `computeFlagLocally()`, before iterating condition groups, read `filters.holdout`; when present, hash the bucketing identity with the holdout's salt per the spec's "Holdout membership uses backend-compatible bucketing" requirement and return the holdout outcome when the identity falls inside `exclusion_percentage`. Keep the percentage as a float — the spec explicitly forbids truncating fractional percentages.

### n15 — Setup (🟡 Partial)
- **Spec requires:** Spec's own `## Applicability` says `client`, and the acceptance file (`acceptance/public/setup.feature`) is tagged `@client`-only, with scenarios that assume ambient, persisted SDK state: "Setup initializes storage transport queue and identity state" (checks `get distinct id should return a non-empty value`), "Setup restores persisted local state" (checks `get anonymous id`/registered super properties survive across a fresh `setup()` call from persistent storage), and "Repeated setup does not duplicate singleton state."
- **SDK currently:** `Client::__construct()` (`lib/Client.php:250-312`) and `PostHog::init()` (`lib/PostHog.php:74-115`) do perform a real one-time setup sequence — resolving the API key (env-var fallback), building the configured consumer/`HttpClient`, initializing the exception-capture handlers, and optionally eager-loading flag definitions — and `PostHog::checkClient()` (`lib/PostHog.php:615-623`) provides an idempotent-ish safety net (a disabled no-op client) if `init()` was never called. However, PHP genuinely cannot satisfy the acceptance scenarios as written: there is no ambient `getDistinctId()`/`getAnonymousId()` the SDK itself maintains (PHP has no persisted anonymous id at all — `distinct_id` is always either caller-supplied or a fresh per-call `Uuid::v4()`, `lib/Client.php:2161`), and there is no persistent storage layer to restore registered super-properties from across a `setup()` call (PHP has no `register()`/super-properties registry — see rows 38/59). The "singleton" framing also doesn't map cleanly: `PostHog::init()` always constructs a brand-new `Client` on each call (`lib/PostHog.php:111`) rather than tracking one canonical instance idempotently across repeated `init()` calls.
- **Backwards compatibility:** Unknown — whether to force-fit PHP's stateless-per-`Client`-instance design into the client-style ambient-identity/persistent-storage model the acceptance scenarios assume is a product/architecture decision, not a small patch.
- **Remediation:** No small code fix recommended; if closer parity is desired, it would require adding persistent storage and an ambient anonymous-id/super-properties layer to PHP — a much larger scope change than this capability alone. At minimum, flag upstream to sdk-specs maintainers that `setup.feature`'s scenarios assume client-only ambient state that a stateless server SDK's constructor-based "setup" cannot satisfy even in spirit, similar to the `Applicability: client` vs. acceptance-tag tension already flagged for the properties-for-flags specs (n14).

### n17 — Tracing Headers (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side: request-scoped middleware/context extracting `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` case-insensitively; sanitize (trim/strip control chars/cap length); explicit call-site values win over context; personless-capture fallback (random `distinct_id` + `$process_person_profile=false`) when no identity is resolvable anywhere; feature-flag evaluation must return an empty/no-op result **and make no network call and emit no `$feature_flag_called`** when no identity is resolvable anywhere; per-request isolation; headers never used for authentication. - **SDK currently:** The server-side consumption half is implemented thoroughly and correctly: `RequestContext::contextFromHeaders()` (`lib/RequestContext.php:110-125`) extracts both headers case-insensitively including framework-normalized/`HTTP_`-prefixed variants (`getHeader()`, `:279-293`, confirmed by `test/RequestContextTest.php:337,349` for PHP-native and Symfony/Laravel header-bag shapes) and sanitizes via `sanitizeHeaderValue()` (trim, strip control chars via regex, cap at 1000 chars, `:127-146`); `withContext()`/`applyCaptureContext()` (`lib/Client.php:2072-2169`) correctly prioritize explicit per-call `distinctId`/properties over context (`hasExplicitCaptureDistinctId()`, `:2171-2190`), and correctly fall back to a generated `Uuid::v4()` + `$process_person_profile=false` when neither an explicit nor a context distinct id exists (`:2160-2166`); `doGetFeatureFlagResult()`/`getAllFlags()`/`evaluateFlags()` all call `resolveDistinctId()` and return an empty/no-op result (`null`, `[]`, or an empty `FeatureFlagEvaluations`) with **no** `/flags` request and **no** `$feature_flag_called` emission when no distinct id is resolvable from either source (`lib/Client.php:760-764,973-977,1051-1060`) — this is confirmed correct for every current flag-evaluation entry point, unlike the parallel posthog-python finding where only the newer `evaluateFlags()` API (not the legacy `feature_enabled`/`get_feature_flag`) could exhibit this behavior; PHP's legacy `getFeatureFlag`/`isFeatureEnabled`/`getFeatureFlagResult` all route through the same `doGetFeatureFlagResult()` helper and so all correctly no-op. Request isolation is real: `RequestContext`'s stack is keyed by `(Client instance, Fiber)` (`lib/RequestContext.php:204-208`), and `test/RequestContextTest.php:182,209` assert Fiber-scoped isolation. The gap is the **client-side half**: there is no hostname-allow-list/outgoing-HTTP-interceptor mechanism for PHP to inject `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` into requests PHP itself makes to other backends (`grep -rn "tracing_headers\|tracingHeaders\|X-POSTHOG" lib/` returns zero matches outside test fixtures) — though this is architecturally awkward for a synchronous, request-scoped, server-only SDK that doesn't typically originate the kind of long-lived outgoing "application backend" calls the client-side half of this spec targets (that half is fundamentally about a browser/mobile app calling *its own* backend, a role PHP doesn't play here).
- **Backwards compatibility:** Backward-compatible — the server-side implementation needs no changes; adding an optional outgoing-request header injector would be purely additive.
- **Remediation:** No urgent fix needed for the server-side consumption half, which is essentially complete and, on the feature-flag no-op requirement specifically, more correct than the parallel posthog-python implementation. If PHP-originated outgoing requests to other PostHog-instrumented backends are a real use case, add an opt-in helper that attaches the two headers to a caller-provided HTTP client/request given the current `RequestContext`.
