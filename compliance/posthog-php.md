Note on repo layout: posthog-php is a single-package, server-only SDK (`composer.json` name
`posthog/posthog-php`, PSR-4 root `lib/` → namespace `PostHog\`). Key files: `lib/Client.php`
(2296 lines — the main instance API: `capture`, `identify`, `alias`, `captureException`, the
deprecated single-flag getters `isFeatureEnabled`/`getFeatureFlag`/`getFeatureFlagResult`/
`getFeatureFlagPayload`, the current `evaluateFlags()` + `FeatureFlagEvaluations` snapshot API,
`getAllFlags`, `loadFlags`/local-evaluation state, `withContext`/`getContext` request-scoped
identity, `flush`/`shutdown`); `lib/PostHog.php` (static facade wrapping a lazily-constructed

property filters, rollout hashing, cohorts, flag dependencies); `lib/FeatureFlagEvaluations.php` /
`lib/EvaluatedFlagRecord.php` (per-request flag snapshot with deduped `$feature_flag_called`
tracking); `lib/RequestContext.php` (per-`Client`, per-Fiber context stack — the mechanism behind
`withContext()`/tracing-header extraction; a `reset()` static exists only as a test helper, not a
public reset API); `lib/HttpClient.php` (curl-based transport, retry/backoff, ETag capture,
`Retry-After` honoring); `lib/QueueConsumer.php` + `lib/Consumer/{LibCurl,Socket,File,ForkCurl,NoOp}.php`
(batching/flush/retry — PHP has no portable background timer, so `flush_interval_seconds` is
checked opportunistically on each `enqueue()`); `lib/ExceptionCapture.php` +
`lib/ExceptionPayloadBuilder.php` (automatic + manual error-tracking capture, stack
ordering/context-line building); `lib/FlagDefinitionCacheProvider.php` (interface for sharing
local-evaluation flag definitions across workers). There is a `sdk_compliance_adapter/` directory
containing a minimal HTTP shim (`/health`, `/init`, `/capture`, `/flush`, `/state`, `/reset`) for a
separate low-level compliance test harness; it is not itself evidence for this audit beyond
confirming the basic capture/flag/flush code paths it exercises. As a server SDK with no
persistent client-side state, most client-only ambient-identity/UI/session-replay capabilities
(session management, persistent storage, consent gating, register/unregister super properties,
autocapture, screen views, surveys, bootstrap, application lifecycle, remote config, on-feature-flags
listeners) are N/A, mirroring posthog-python/posthog-node — see per-row notes for exactly which
narrower carve-outs apply and which acceptance files are tagged `@client`-only versus `@both`.

## Notes

### n1 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Enrich events with `distinct_id`/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; run `before_send`; and — per the `@both`-tagged acceptance scenario "Capture honors opt-out state" (`acceptance/public/capture.feature:46-51`) — silently drop the event with **no network call** while opted out.
- **SDK currently:** `Client::capture()` (`lib/Client.php:388-476`) correctly resolves identity via `RequestContext`/`applyCaptureContext()` (`lib/Client.php:2137-2169`), stamps `$lib`/`$lib_version`/`$lib_consumer`/`$is_server` (`message()`, `lib/Client.php:2219-2277`), assigns timestamp/uuid, merges `$groups`, and runs `before_send` (`applyBeforeSend()`, `lib/Client.php:488-517`) — all correct. But there is **no opt-out mechanism of any kind**: `grep -rniE "opt_?out|opt_?in"` across `lib/` returns zero matches. The only capture-suppressing flag is `$enabled` (`lib/Client.php:191`), which is set exactly once in the constructor from API-key presence (`$this->enabled = $this->apiKey !== '';`, line 259) and is never reassigned anywhere else in the class — confirmed by `grep -n "enabled" lib/Client.php`, which shows only reads, never a second write. There is no way for a caller to opt an already-constructed client in or out at runtime; the disabled/no-op consumer path exists only for a missing/blank API key, not for a live app's runtime consent decision.
- **Backwards compatibility:** Backward-compatible — adding `optOutCapturing()`/`optInCapturing()`/`isOptedOut()` methods plus a mutable internal flag checked at the top of `capture()`/`identify()`/`alias()`/flag-evaluation paths is purely additive.
- **Remediation:** Add a runtime-mutable opt-out flag and `Client::optOutCapturing()`/`optInCapturing()`/`isOptedOut()` (and matching `PostHog::` facade methods), checked before enqueue in `capture()`, `identify()`, `alias()`, `captureException()`, and the flag-evaluation capture-side-effect paths.

### n2 — Capture Exception (🟡 Partial)
- **Spec requires:** Acceptance scenario "Capturing a handled exception emits an exception event" (`acceptance/public/capture-exception.feature`) requires flat, top-level `$exception_type`/`$exception_message` properties on the enqueued event, in addition to the structured `$exception_list`. Also requires bottom-up frame ordering, outermost-first exception-list ordering, ascending source-context windows, and stack-trace preservation over synthesis.
- **SDK currently:** `Client::captureException()` (`lib/Client.php:543-574`) builds `$exception_list` and `$exception_handled` via `ExceptionPayloadBuilder::buildExceptionList()`/`getPrimaryHandled()`, but **never sets a top-level `$exception_type` or `$exception_message` property** — confirmed by `grep -rn "exception_type\|exception_message" lib/ test/` returning zero matches anywhere in the codebase (type/value only exist nested inside `$exception_list[0].type`/`.value`, `lib/ExceptionPayloadBuilder.php:206-208`). This directly contradicts the acceptance scenario's explicit requirement for `$exception_type=TypeError`/`$exception_message=boom` as top-level enqueued properties. Everything else is correctly implemented and tested: outermost-first `$exception_list` via `buildExceptionList()`'s `getPrevious()` walk (`lib/ExceptionPayloadBuilder.php:32-45`); bottom-up frame ordering via an explicit `array_reverse()` with a comment documenting the PHP-innermost-first → PostHog-outermost-first conversion (`lib/ExceptionPayloadBuilder.php:236-244`); ascending `pre_context`/`context_line`/`post_context` windows (`addContextLines()`, `lib/ExceptionPayloadBuilder.php:291-320`); and stack preservation (throw-site reconciliation heuristics, `normalizeThrowableTrace()`, `lib/ExceptionPayloadBuilder.php:136-169`) rather than synthesis, confirmed by `test/ExceptionPayloadBuilderTest.php`.
- **Backwards compatibility:** Backward-compatible — adding `$exception_type`/`$exception_message` (sourced from `$exception_list[0].type`/`.value`) as flat top-level properties is additive and does not remove or rename any currently-emitted field.
- **Remediation:** In `Client::captureException()` (and the equivalent auto-capture path in `ExceptionCapture::sendExceptionEvent()`, `lib/ExceptionCapture.php:399-450`), add `$properties['$exception_type']`/`$properties['$exception_message']` mirrored from the first (outermost) entry of the built `$exception_list`.

### n3 — Event Batcher (🟡 Partial)
- **Spec requires:** `both`. Accumulate events; flush at a count threshold (`flushAt`) or on an interval timer (`flushInterval`); cap batch payload size; preserve FIFO order; explicit flush/shutdown drains immediately; spec item 11 notes "some SDKs" shrink the batch and retry on HTTP 413.
- **SDK currently:** `QueueConsumer` (`lib/QueueConsumer.php`) implements threshold flush (`batch_size`, default 100) and interval flush (`flush_interval`, default 5.0s) correctly — but because "PHP has no portable in-process background timer" (the class's own doc comment, `lib/QueueConsumer.php:10-12`), the interval check is only evaluated opportunistically inside `enqueue()` (`flushIntervalElapsed()`, checked at `lib/QueueConsumer.php:177`) rather than by a real timer/thread; a queue that receives no further `capture()` calls after the interval elapses will not flush until the next event arrives, `flush()`, or `shutdown()`/`__destruct()`. This is a reasonable, explicitly-documented PHP-process-model accommodation rather than a bug, but it is a real deviation from "trigger flush by timer" (spec item 4) taken literally. FIFO order is preserved (`array_slice`/`array_splice` from the front, `lib/QueueConsumer.php:141,146`); a pre-flight 1MB payload-size cap exists (`MAX_BATCH_PAYLOAD_SIZE`, `lib/QueueConsumer.php:18`, checked in each `Consumer\*::flushBatch()`); explicit `flush()`/destructor-time drain both work. No adaptive batch-shrink-and-retry on HTTP 413 exists (413 is correctly classified as non-retryable, so this is the same optional, "some SDKs"-only gap independently noted for posthog-python/posthog-ios, not a hard miss).
- **Backwards compatibility:** Backward-compatible — introducing a real timer (e.g. via a PSR-based event loop or an opt-in `register_tick_function`) would be additive and does not change the current opportunistic-check default.
- **Remediation:** Document the opportunistic-timer behavior clearly in public API docs (it is already documented internally); consider an opt-in true-timer mode for long-running PHP processes (queue workers, daemons) where events may not be enqueued frequently enough to trigger the opportunistic check.

### n4 — Feature Flag Called Tracker (🟡 Partial)
- **Spec requires:** Dedup `$feature_flag_called` by `(flag, value, distinct_id, normalized groups)`; clear on shutdown; minimal-event mode gated by `minimalFlagCalledEvents`/`has_experiment===false`, with an allowlist that — per the most recent sdk-specs fix (commit `b59e8b4`, `fix(feature-flag-called-tracker): add session-attribution properties to minimal-event allowlist`) — includes the session-attribution properties (`$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid`) in addition to flag-identity/debug/session/platform properties, while still excluding `$referrer`.
- **SDK currently:** `Client::MINIMAL_FLAG_CALLED_EVENT_PROPERTIES` (`lib/Client.php:32-49`) contains exactly 16 entries (`$feature_flag`, `$feature_flag_response`, `$feature_flag_has_experiment`, `$feature_flag_id`, `$feature_flag_version`, `$feature_flag_reason`, `$feature_flag_request_id`, `$feature_flag_evaluated_at`, `$feature_flag_error`, `locally_evaluated`, `$groups`, `$process_person_profile`, `$session_id`, `$lib`, `$lib_version`, `$is_server`) — the flag-identity/debug/session/platform categories, but **zero session-attribution properties**. It is missing all 10 of `$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid` — the exact same gap class independently found in posthog-python and posthog-node. Everything else matches the spec precisely and is well-tested: dedup key construction combining `distinctId` + response + canonicalized (sorted-by-key, JSON-encoded) groups (`captureFlagCalledIfNeeded()`/`canonicalGroupsRepr()`, `lib/Client.php:1242-1290`); fail-safe-to-full-event gating requiring both the server gate and an explicit `has_experiment === false` (`shouldSendMinimalFlagCalledEvent()`, `lib/Client.php:528-533`); the gate persisting through `normalizeFlagDefinitionData()`/`normalizeFlagDefinitionCacheData()` so it survives external cache-provider round-trips and 304 responses (`lib/Client.php:1543,1580`); and shutdown-time dedupe-cache clearing (`Client::shutdown()` replaces `distinctIdsFeatureFlagsReported` with a fresh `SizeLimitedHash`, `lib/Client.php:358`). Note: PHP has no super-property registration mechanism at all (no `register()`), so there is currently no code path that would attach UTM/click-id values to an event in the first place — but the allowlist itself should still be forward-looking/complete per the spec's own reference-implementation note, matching how the parallel posthog-ios audit reasoned about the same absence.
- **Backwards compatibility:** Backward-compatible — adding 10 keys to a strip-allowlist array is strictly additive; it can only cause minimized events to retain more properties than before, never fewer.
- **Remediation:** Add the 10 session-attribution property names from sdk-specs commit `b59e8b4` to `Client::MINIMAL_FLAG_CALLED_EVENT_PROPERTIES` (`lib/Client.php:32-49`).

### n5 — Flag Definition Loader (🟡 Partial)
- **Spec requires:** `both`, with acceptance file `acceptance/private/flag-definition-loader.feature` tagged `@server`. Fetch/cache local-evaluation flag definitions from a privileged endpoint; ETag-based conditional fetches; external/shared cache-provider integration (sync and async); quota/auth error handling; and — per the explicit scenario "Loader refreshes after polling interval" — a background poll loop that refreshes definitions once a configured interval elapses, without an application call being the trigger.
- **SDK currently:** Everything except background polling is implemented and tested precisely: `Client::loadFlags()` (`lib/Client.php:1409-1453`) fetches from `/flags/definitions?send_cohorts&token=...` with `Authorization: Bearer <secretKey>` (`localFlags()`, `lib/Client.php:1677-1709`); ETag is captured and sent as `If-None-Match` (`lib/Client.php:1697-1699,1522`), and a `304` response preserves existing definitions while optionally refreshing the stored ETag (`fetchAndApplyFlagDefinitionsFromApi()`, `lib/Client.php:1490-1498`); the `FlagDefinitionCacheProvider` interface (`lib/FlagDefinitionCacheProvider.php`) supports external/shared caches with `shouldFetchFlagDefinitions()`/`getFlagDefinitions()`/`onFlagDefinitionsReceived()`/`shutdown()`, all called defensively with provider-failure fallback to a direct fetch (`lib/Client.php:1417-1448`), matching every scenario in the acceptance file (sync/async provider results, provider read/fetch-decision/shutdown failures) per `test/FlagDefinitionCacheProviderTest.php` and `test/EtagSupportTest.php`. However, `loadFlags()` is called once at `Client` construction (if a secret key is configured, `lib/Client.php:304-311`) and otherwise only on an explicit application call to `Client::loadFlags()` — there is **no poll loop or timer** anywhere in the codebase (`grep -n "polling\|poll_interval\|background"` finds only doc-comment references to PHP's lack of a portable background timer, `lib/QueueConsumer.php:10`, `lib/Client.php:209`, `lib/PostHog.php:33`). This is a defensible consequence of PHP's typical short-lived-request execution model (unlike a long-running Python/Node/Ruby process, a PHP request usually doesn't stay alive long enough for polling to matter, and the external cache-provider interface is the documented multi-worker alternative), but it is a literal, acceptance-scenario-visible gap against the spec's "Start and maintain a poll loop" behavior item.
- **Backwards compatibility:** Backward-compatible — adding an opt-in polling helper (e.g. a method applications can wire into a long-running worker's event loop or a cron-style external trigger) would be additive; the current one-shot/manual-refresh model would remain the default.
- **Remediation:** Document the intentional one-shot/manual-refresh design for PHP's request lifecycle explicitly (distinguishing it from long-running-process SDKs); optionally add an opt-in polling helper for PHP daemons/queue workers that do stay alive across requests.

### n6 — Get Feature Flags And Payloads (🟡 Partial)
- **Spec requires:** A bulk getter returning flag values and their payloads together in one call — canonically `{ flags, payloads }` or `{ featureFlags, featureFlagPayloads }` — verified without needing a second per-key call.
- **SDK currently:** No method with this name or shape exists anywhere in `lib/` (`grep -n "getFeatureFlagsAndPayloads\|getAllFlagsAndPayloads\|AndPayloads" lib/*.php` returns zero matches). The underlying data is reachable — `Client::evaluateFlags()` (`lib/Client.php:1042-1226`) returns a `FeatureFlagEvaluations` snapshot exposing `getKeys()` (`lib/FeatureFlagEvaluations.php:49-52`), `getFlag($key)` (`:74-84`), and `getFlagPayload($key)` (`:93-96`) — so a caller *can* reconstruct both maps by iterating `getKeys()` and calling `getFlag()`/`getFlagPayload()` per key — but there is no single canonical call that returns the paired `{flags, payloads}` (or `{featureFlags, featureFlagPayloads}`) result shape the spec's acceptance scenarios expect ("the returned feature flag values should be... / the returned feature flag payloads should be..." from one call).
- **Backwards compatibility:** Backward-compatible — adding a new method (e.g. `Client::getAllFlagsAndPayloads()`) that internally calls `evaluateFlags()` and folds the snapshot into the two-map shape is purely additive.
- **Remediation:** Add `Client::getAllFlagsAndPayloads($distinctId, ...)` returning `['featureFlags' => [...], 'featureFlagPayloads' => [...]]`, built from an internal `evaluateFlags()` call folded over `getKeys()`/`getFlag()`/`getFlagPayload()` (using the payload-silent, non-tracking accessor so the bulk read doesn't fire `$feature_flag_called` per key).

### n7 — HTTP Client (🟡 Partial)
- **Spec requires:** The "Feature flag evaluation retry policy" requirement (hard `SHALL`) mandates that retries of the `/flags` endpoint use "exponential backoff starting at 300ms before the first retry, then 600ms before the second retry, doubling for each later retry," with a default budget of one retry (two total attempts), retrying only on transient transport failures and HTTP 502/504, never other status codes.
- **SDK currently:** `Client::sendFeatureFlagsRequest()` (`lib/Client.php:1887-1917`) gets the retry-eligibility classification exactly right — `isRetryableFlagsCurlError()` matches transient transport errors (curl errno 28/52/56 — timeout, connection reset, empty reply, `lib/Client.php:1931-1936`), `isRetryableFlagsStatusCode()` matches only HTTP 502/504 (`lib/Client.php:1938-1941`), and the default retry budget (`featureFlagRequestMaxRetries`, defaults to 1, `lib/Client.php:289`) matches the spec's "one retry after the initial attempt." However the **backoff timing constant is wrong**: `$backoff = 100` (`lib/Client.php:1889`, doubling thereafter, capped by `maximumBackoffDurationMs`) starts at 100ms, not the spec-mandated 300ms before the first retry (and 600ms before the second). This is confirmed by the doc comment on `PostHog::init()`/`Client::__construct()` itself, which documents "Retry backoff starts at 100ms and doubles" (`lib/Client.php:212-213`, `lib/PostHog.php:36-37`) as the intended, deliberate behavior, not an oversight — but it still deviates from the spec's explicit numeric requirement. The rest of the HTTP client (ingestion request auth/JSON payload, 200 = delivered, non-throwing retryable-failure reporting with events remaining queued, `Retry-After` honoring for ingestion in `HttpClient::retryAfterMilliseconds()`, `lib/HttpClient.php:218-241`) matches the spec's other scenarios correctly.
- **Backwards compatibility:** Backward-compatible — changing the initial backoff constant from 100ms to 300ms (and the second-retry delay to 600ms) is an internal timing change with no signature/behavior-contract change, though it will make flag-request retries take measurably longer under transient failure, which is worth a changelog callout for latency-sensitive integrations.
- **Remediation:** Change the initial backoff in `sendFeatureFlagsRequest()` (`lib/Client.php:1889`) from `100` to `300` so the schedule matches the spec's 300ms/600ms/… doubling sequence.

### n8 — Is Feature Enabled (❌ Fail)
- **Spec requires:** Hard `SHALL`, `both` applicability, explicitly documenting PHP's own current signature as the canonical shape with no carve-out: "The SDK SHALL accept a caller-supplied boolean default (`defaultValue`)... and SHALL return it whenever the flag has no value... A flag that has a value — including `false` and variant strings — always wins over the caller-supplied default."
- **SDK currently:** `Client::isFeatureEnabled()` (`lib/Client.php:615-649`) has **no `defaultValue`/`default_value` parameter at all** — its full signature is `isFeatureEnabled(string $key, ?string $distinctId = null, array $groups = [], array $personProperties = [], array $groupProperties = [], bool $onlyEvaluateLocally = false, bool $sendFeatureFlagEvents = true): null|bool`. The spec's own "Surface variants" table documents this exact signature verbatim for PHP (`openspec/specs/is-feature-enabled/spec.md:71`) with no `defaultValue` param, confirming the gap is real and current, not a stale spec artifact. On a missing/failed flag, the method unconditionally returns `null` (`doGetFeatureFlagResult()` returns `null` when `$result` is `null`, surfaced at `lib/Client.php:644-646`) — there is no way for a caller to make a missing flag resolve to `true`/`false` via this API. The module-level `PostHog::isFeatureEnabled()` facade (`lib/PostHog.php:249-268`) forwards the identical signature and has the identical gap.
- **Backwards compatibility:** Backward-compatible — adding an optional `?bool $defaultValue = null` parameter (returned only when the flag has no resolvable value) is purely additive and does not change behavior for existing callers who omit it.
- **Remediation:** Add a `defaultValue` parameter to `Client::isFeatureEnabled()` and `PostHog::isFeatureEnabled()`, returned only when `doGetFeatureFlagResult()` resolves to `null` (flag missing, not loaded, or a failed remote/local evaluation), with any present flag value (including `false`) still taking precedence.

### n9 — Logs (❌ Fail)
- **Spec requires:** A `captureLog`/logger API producing OTLP-shaped log records shipped via `POST {host}/i/v1/logs`, with severity mapping, batching/rate-capping, and retry/413 handling.
- **SDK currently:** No implementation exists at all. `grep -rn "captureLog\|i/v1/logs\|logRecord\|severityNumber" lib/` returns zero matches. There is no logs-specific queue, transport route, or severity-mapping table anywhere in `lib/`.
- **Backwards compatibility:** Backward-compatible — a net-new, purely additive subsystem.
- **Remediation:** Implement a `captureLog`/`Logger` surface mirroring the client SDKs' OTLP-log shape, wired to a new `/i/v1/logs` transport with its own batching/rate-cap policy, reusing the existing `QueueConsumer`/`HttpClient` machinery where practical.

### n10 — Set/Reset Person/Group Properties For Flags (❌ Fail, all four contracts)
- **Spec requires:** Each of these four specs' own `## Applicability` line says `client` ("Server SDKs usually take/pass person/group properties directly on each flag-evaluation call instead of maintaining a persistent local override cache/store"). However, all four acceptance feature files (`set-person-properties-for-flags.feature`, `set-group-properties-for-flags.feature`, `reset-person-properties-for-flags.feature`, `reset-group-properties-for-flags.feature`) are tagged `@public @canonical_behavior @acceptance @..._for_flags @both` at the feature level *and* on every individual scenario, with concrete, generically-written scenarios ("Set person properties stores overrides for future flag evaluation," "Person property overrides are sent with flag reloads") that make no client-only assumption and are mechanically satisfiable server-side. Consistent with the precedent set auditing posthog-python (same finding, same acceptance-precedence rationale) and posthog-node, this audit treats these as in-scope-but-unimplemented rather than N/A.
- **SDK currently:** `grep -rn "person_properties_for_flags\|group_properties_for_flags\|PropertiesForFlags"` across `/tmp/audit-posthog-php/lib` and `/tmp/audit-posthog-php/test` returns zero matches for all four. `personProperties`/`groupProperties` exist only as per-call parameters on `getFeatureFlag`/`getAllFlags`/`evaluateFlags` (e.g. `lib/Client.php:751-759,966-972,1042-1049`), never persisted between calls — there is no stateful override cache and no `setPersonPropertiesForFlags()`/`setGroupPropertiesForFlags()`/`resetPersonPropertiesForFlags()`/`resetGroupPropertiesForFlags()` method anywhere in `Client.php`, `FeatureFlag.php`, `FeatureFlagEvaluations.php`, or `RequestContext.php`.
- **Backwards compatibility:** Backward-compatible — a new opt-in stateful override store (naturally scoped to `RequestContext`'s existing per-`Client`, per-Fiber context stack, since PHP already has that request-scoping mechanism for `distinctId`/`sessionId`) would be purely additive; no existing call signature needs to change.
- **Remediation:** Add `Client::setPersonPropertiesForFlags()`/`setGroupPropertiesForFlags()`/`resetPersonPropertiesForFlags()`/`resetGroupPropertiesForFlags()`, backed by a `RequestContext`-scoped override store consulted as a default by `getFeatureFlag`/`getAllFlags`/`evaluateFlags`, overridable by explicit per-call `personProperties`/`groupProperties`. Also worth flagging upstream to sdk-specs maintainers: the spec-prose `Applicability: client` and the acceptance files' `@both` tags are inconsistent and should be reconciled (same flag raised in the posthog-python audit).

### n11 — Setup (🟡 Partial)
- **Spec requires:** Spec's own `## Applicability` says `client`, and the acceptance file (`acceptance/public/setup.feature`) is tagged `@client`-only, with scenarios that assume ambient, persisted SDK state: "Setup initializes storage transport queue and identity state" (checks `get distinct id should return a non-empty value`), "Setup restores persisted local state" (checks `get anonymous id`/registered super properties survive across a fresh `setup()` call from persistent storage), and "Repeated setup does not duplicate singleton state."
- **SDK currently:** `Client::__construct()` (`lib/Client.php:250-312`) and `PostHog::init()` (`lib/PostHog.php:74-115`) do perform a real one-time setup sequence — resolving the API key (env-var fallback), building the configured consumer/`HttpClient`, initializing the exception-capture handlers, and optionally eager-loading flag definitions — and `PostHog::checkClient()` (`lib/PostHog.php:615-623`) provides an idempotent-ish safety net (a disabled no-op client) if `init()` was never called. This satisfies the general "become ready to send events" concept the spec describes. However, PHP genuinely cannot satisfy the acceptance scenarios as written: there is no ambient `getDistinctId()`/`getAnonymousId()` the SDK itself maintains (PHP has no persisted anonymous id at all — `distinct_id` is always either caller-supplied or a fresh per-call `Uuid::v4()`, `lib/Client.php:2161`), and there is no persistent storage layer to restore registered super-properties from across a `setup()` call (PHP has no `register()`/super-properties registry — see rows 38/59). The "singleton" framing also doesn't map cleanly: `PostHog::init()` always constructs a brand-new `Client` on each call (`lib/PostHog.php:111`) rather than tracking one canonical instance idempotently across repeated `init()` calls.
- **Backwards compatibility:** Unknown — whether to force-fit PHP's stateless-per-`Client`-instance design into the client-style ambient-identity/persistent-storage model the acceptance scenarios assume is a product/architecture decision, not a small patch.
- **Remediation:** No small code fix recommended; if closer parity is desired, it would require adding persistent storage and an ambient anonymous-id/super-properties layer to PHP — a much larger scope change than this capability alone. At minimum, flag upstream to sdk-specs maintainers that `setup.feature`'s scenarios assume client-only ambient state that a stateless server SDK's constructor-based "setup" cannot satisfy even in spirit, similar to the `Applicability: client` vs. acceptance-tag tension already flagged for the properties-for-flags specs (n10).

### n12 — Traces (❌ Fail)
- **Spec requires:** A `startSpan`/`withSpan` API producing OTLP spans shipped to `POST {host}/i/v1/traces`, independent of LLM-analytics-as-events, requiring no OpenTelemetry runtime dependency.
- **SDK currently:** No implementation exists. `grep -rniE "startSpan|withSpan|i/v1/traces|resourceSpans|scopeSpans" lib/` returns zero matches. `composer.json`'s only runtime dependency is `symfony/clock`; there is no AI/LLM-observability module, OTel bridge, or traces transport of any kind in this repository.
- **Backwards compatibility:** Backward-compatible — a net-new, additive subsystem.
- **Remediation:** Implement a dependency-free span-handle API (`setAttribute`/`addEvent`/`setStatus`/`recordException`/`end`) plus `startSpan`/`withSpan`, an in-memory buffered span queue, and a `/i/v1/traces` transport, reusing the existing `HttpClient`/`QueueConsumer` machinery.

### n13 — Tracing Headers (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side: request-scoped middleware/context extracting `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` case-insensitively; sanitize (trim/strip control chars/cap length); explicit call-site values win over context; personless-capture fallback (random `distinct_id` + `$process_person_profile=false`) when no identity is resolvable anywhere; feature-flag evaluation must return an empty/no-op result **and make no network call and emit no `$feature_flag_called`** when no identity is resolvable anywhere; per-request isolation; headers never used for authentication. Client-side: an opt-in hostname allow-list that injects the same headers into outgoing application HTTP requests.
- **SDK currently:** The server-side consumption half is implemented thoroughly and correctly: `RequestContext::contextFromHeaders()` (`lib/RequestContext.php:110-125`) extracts both headers case-insensitively including framework-normalized/`HTTP_`-prefixed variants (`getHeader()`, `:279-293`, confirmed by `test/RequestContextTest.php:337,349` for PHP-native and Symfony/Laravel header-bag shapes) and sanitizes via `sanitizeHeaderValue()` (trim, strip control chars via regex, cap at 1000 chars, `:127-146`); `withContext()`/`applyCaptureContext()` (`lib/Client.php:2072-2169`) correctly prioritize explicit per-call `distinctId`/properties over context (`hasExplicitCaptureDistinctId()`, `:2171-2190`), and correctly fall back to a generated `Uuid::v4()` + `$process_person_profile=false` when neither an explicit nor a context distinct id exists (`:2160-2166`); `doGetFeatureFlagResult()`/`getAllFlags()`/`evaluateFlags()` all call `resolveDistinctId()` and return an empty/no-op result (`null`, `[]`, or an empty `FeatureFlagEvaluations`) with **no** `/flags` request and **no** `$feature_flag_called` emission when no distinct id is resolvable from either source (`lib/Client.php:760-764,973-977,1051-1060`) — this is confirmed correct for every current flag-evaluation entry point, unlike the parallel posthog-python finding where only the newer `evaluateFlags()` API (not the legacy `feature_enabled`/`get_feature_flag`) could exhibit this behavior; PHP's legacy `getFeatureFlag`/`isFeatureEnabled`/`getFeatureFlagResult` all route through the same `doGetFeatureFlagResult()` helper and so all correctly no-op. Request isolation is real: `RequestContext`'s stack is keyed by `(Client instance, Fiber)` (`lib/RequestContext.php:204-208`), and `test/RequestContextTest.php:182,209` assert Fiber-scoped isolation. The gap is the **client-side half**: there is no hostname-allow-list/outgoing-HTTP-interceptor mechanism for PHP to inject `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` into requests PHP itself makes to other backends (`grep -rn "tracing_headers\|tracingHeaders\|X-POSTHOG" lib/` returns zero matches outside test fixtures) — though this is architecturally awkward for a synchronous, request-scoped, server-only SDK that doesn't typically originate the kind of long-lived outgoing "application backend" calls the client-side half of this spec targets (that half is fundamentally about a browser/mobile app calling *its own* backend, a role PHP doesn't play here).
- **Backwards compatibility:** Backward-compatible — the server-side implementation needs no changes; adding an optional outgoing-request header injector would be purely additive.
- **Remediation:** No urgent fix needed for the server-side consumption half, which is essentially complete and, on the feature-flag no-op requirement specifically, more correct than the parallel posthog-python implementation. If PHP-originated outgoing requests to other PostHog-instrumented backends are a real use case, add an opt-in helper that attaches the two headers to a caller-provided HTTP client/request given the current `RequestContext`.
