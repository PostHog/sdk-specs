## Notes

### n1 — Logs (❌ Fail)
- **Spec requires:** A `captureLog`/logger API that produces OTLP-shaped log records and ships them via `POST {host}/i/v1/logs`, with severity-number mapping, batching/rate-capping, gzip, and retry/413 handling.
- **SDK currently:** No implementation at all. `grep` for `captureLog`, `i/v1/logs`, `logRecord`, `severityNumber` across the repo returns zero matches. `posthog/_logging.py` is exclusively stdlib `logging`-based internal SDK diagnostics (prefixes messages with `"[PostHog]"`) — unrelated to the product Logs capability. `posthog/metrics_capture.py` implements a separate, unrelated OTLP *metrics* pipeline (ships to `/i/v1/metrics`, statsd-style `count`/`gauge`/`histogram`), with no `body`/`severityNumber`/log-record concept. No `logs`/`traces` acceptance feature file exists yet (`acceptance/public|private/logs.feature` doesn't exist), so there are no scenario tags to cross-check either.
- **Backwards compatibility:** Backward-compatible — this is a net-new, purely additive subsystem; nothing existing needs to change or be removed.
- **Remediation:** Implement a `capture_log`/`Logger` surface mirroring the client SDKs' OTLP-log shape, wired to a new `/i/v1/logs` transport, with its own batching/rate-cap policy.

### n2 — Traces (❌ Fail)
- **Spec requires:** A `startSpan`/`withSpan` API producing OTLP spans shipped to `POST {host}/i/v1/traces`, explicitly distinct from LLM-analytics-as-events and requiring no OpenTelemetry runtime dependency.
- **SDK currently:** No `startSpan`/`start_span` or `/i/v1/traces` route exists anywhere (`posthog/client.py`, `posthog/request.py`). What exists instead: (a) LLM observability captured as ordinary `$ai_generation` analytics events tagged with `$ai_trace_id` (`posthog/ai/utils.py`) — the spec's own explicitly-excluded case ("LLM analytics traces captured as analytics events, not OTLP"); (b) `posthog/ai/otel/{processor,exporter}.py`, which *depends on* the external `opentelemetry-sdk`/`opentelemetry-exporter-otlp-proto-http` packages (contradicting the "no OTel runtime dependency" requirement) and forwards only AI-semantic-convention spans to a different endpoint, `/i/v0/ai/otel`, not `/i/v1/traces`; and (c) `exception_utils.py::_get_current_otel_span_properties()`, which only *reads* an ambient third-party OTel span's `trace_id`/`span_id` to stamp onto `$exception` events — it does not create spans or implement any part of this capability.
- **Backwards compatibility:** Backward-compatible — a net-new subsystem alongside the existing AI-events/OTel-bridge features; no removal needed.
- **Remediation:** Implement a dependency-free `start_span`/`with_span` API shipping OTLP spans to `/i/v1/traces`, independent of the `posthog/ai/otel` bridge.

### n3 — Tracing Headers (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side responsibilities: request-scoped middleware extracting `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` (case-insensitively) into context; sanitize (trim/strip control chars/cap length); explicit call-site values take precedence over context; personless-capture fallback (random `distinct_id` + `$process_person_profile=false`) when no identity is resolvable; flag-evaluation APIs should no-op/return-empty (no network call, no `$feature_flag_called`) when no identity is resolvable anywhere; per-request isolation; headers never used for auth. Acceptance file `acceptance/private/tracing-headers.feature` has 2 `@client` and 5 `@server` scenarios.
- **SDK currently:** `posthog/contexts.py` implements genuine `contextvars.ContextVar`-based per-task isolation with fork-safety (`os.register_at_fork`). `posthog/integrations/django.py` implements real middleware with header extraction, sanitization (`_sanitize_tracing_header_value`: strips C0/C1 control chars via regex, trims whitespace, caps at `_MAX_TRACING_HEADER_LENGTH = 1000`), and sync+ASGI-async support; `posthog/integrations/celery.py` propagates the same headers producer→worker (as Celery message headers, not HTTP). Personless fallback matches spec exactly (`get_identity_state()` falls back to context, else generates a random id and sets `$process_person_profile=False`). **Improved since last audit:** `Client.evaluate_flags()` (`client.py` ~4013-4085) now falls back to `get_context_distinct_id()` when `distinct_id` is omitted, and returns an *empty* `FeatureFlagEvaluations` snapshot (no `/flags` request, no `$feature_flag_called`) when no identity is resolvable anywhere — directly satisfying the spec's flag-evaluation-without-identity requirement, closing a gap the previous audit had flagged. Remaining gaps: (1) the legacy, still-widely-used `get_feature_flag()`/`get_all_flags()`/`feature_enabled()` still require `distinct_id` as a mandatory positional argument with no context-fallback and no empty/no-op path; (2) only Django and Celery have first-class integrations — no Flask/FastAPI-specific middleware exists (a `playgrounds/fastapi-exception-capture/app.py` demo calls `capture_exception` manually with an explicit `distinct_id`, it does not use `contexts.new_context()`/header extraction, so it's an example, not an integration).
- **Backwards compatibility:** Backward-compatible — adding an optional context-fallback default for `distinct_id` on the legacy flag APIs, and adding Flask/FastAPI middleware, are both purely additive.
- **Remediation:** Make `distinct_id` optional (falling back to `contexts.py`'s ambient value, else no-op) on `feature_enabled`/`get_feature_flag`/`get_all_flags`; add Flask/FastAPI middleware modules alongside the existing Django/Celery ones.

### n4 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Enrich events with `distinct_id`/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; honor an opt-out state so that capture is dropped silently with no network call (acceptance scenario "Capture honors opt-out state" is tagged `@both`); support a `before_send` hook that can mutate/drop events.
- **SDK currently:** `Client._capture`/`_enqueue` correctly resolves identity via `get_identity_state()`, stamps `$lib`/`$lib_version`, timestamp/uuid (including a new "normalize SDK event timestamps to UTC" fix in 7.39.1), merges `super_properties`, runs `before_send`. `capture()` returns the event UUID or `None` on drop. However, re-confirmed via `grep -rn "opt_out\|opt_in\|is_opted_out" posthog/client.py posthog/__init__.py` → zero matches: there is still no dynamic, runtime-toggleable opt-out API. The only short-circuit is the constructor-time `disabled` flag (`client.py:887`, `self.disabled = disabled or not self.api_key`, checked at multiple call sites) — a static kill-switch set once at construction, not the dynamic per-call `opt_out_capturing()`/`is_opted_out()` API pair other server SDKs (e.g. posthog-node) expose.
- **Backwards compatibility:** Backward-compatible — adding `opt_in()`/`opt_out()`/`is_opted_out()` methods that toggle a new or existing internal flag is purely additive.
- **Remediation:** Add a dynamic `opt_out_capturing()` / `opt_in_capturing()` / `is_opted_out()` API on `Client`, distinct from the static `disabled` kill switch, mirroring other server SDKs.

### n5 — Capture Exception (🟡 Partial)
- **Spec requires:** `captureException(error, properties?)` emits a `$exception` event with correctly-ordered `$exception_list` (outermost/caught-first, root-cause-last), correctly-ordered stack frames, ascending source-context lines, preserved (not synthesized) stack traces when available, and flat `$exception_type`/`$exception_message` top-level properties (asserted explicitly by acceptance scenario "Capturing a handled exception emits an exception event", `capture-exception.feature:12-21`). Spec's own `## Applicability` line still says `client`, but every scenario in `capture-exception.feature` is tagged `@both` — treated as in-scope per the acceptance-tag-precedence convention.
- **SDK currently:** `Client.capture_exception` (`posthog/client.py:1988`) correctly builds ordered `$exception_list` via `exceptions_from_error_tuple`/`exceptions_from_error` (confirmed by `test_exception_capture.py:320,342,367` canonical-order tests), correct frame ordering (Python's native `tb.tb_next` linked-list traversal is already outermost-call-first, matching the spec's required order without needing reversal), correct ascending `pre_context`/`context_line`/`post_context` windows (`get_lines_from_file`), and preserves existing `__traceback__` rather than synthesizing one except when no real traceback exists (`exc_info_from_error`/`construct_artificial_traceback`). However, **no top-level `$exception_type`/`$exception_message` properties are ever emitted** — `grep` for these strings across the SDK (excluding tests) returns zero matches; the SDK only nests `type`/`value` inside `$exception_list[0]`. This is deliberate and unreversed: `posthog/CHANGELOG.md` records `## 7.3.1 - 2025-12-06` → `fix: remove unused $exception_message and $exception_type`, and current HEAD is 7.39.1 (36+ releases later) with no re-add found in CHANGELOG or code. This directly contradicts the acceptance scenario, which expects `$exception_type=TypeError`/`$exception_message=boom` as enqueued properties. (Note: the deeper wire-format issues around `mechanism`/`handled`/`synthetic`/`$exception_source` are tracked separately under Exception Event Metadata, n14, to avoid double-counting — this note is scoped to the capture-exception spec's narrower ordering/flat-property requirements.)
- **Backwards compatibility:** Backward-compatible — re-adding `$exception_type`/`$exception_message` as flat properties (mirroring `$exception_list[0].type`/`.value`) is additive and doesn't remove or rename anything currently emitted; confirm no downstream ingestion/UI conflict was the reason they were removed before reverting.
- **Remediation:** Re-add `$exception_type` and `$exception_message` as flat top-level properties on the `$exception` event, sourced from `$exception_list[0]`.

### n6 — Flush (🟡 Partial)
- **Spec requires:** `@both`. No-op on empty queue with no network call; bypass `flush_at`/`flush_interval` and drain immediately; on delivery failure (e.g. 503) must not throw, and the failed event must remain queued for a later retry.
- **SDK currently:** `Client.flush(timeout_seconds=10)` (`posthog/client.py:2426`) delegates to per-lane blocking on `queue.unfinished_tasks`, correctly no-ops on an empty queue and bypasses batching intervals, and is wrapped so it never throws — matching the spec on those points. But `Consumer.upload()` (`consumer.py:167-193`) unconditionally calls `queue.task_done()` in a `finally` block regardless of send success, and once `is_retryable()`'s retry budget (`consumer.py:310-322`) is exhausted, `upload()` catches/logs/calls `on_error` — the batch is **not re-enqueued**, it is permanently dropped. `flush()` itself doesn't throw (matches spec), but failed events are not retained for retry as required; the SDK's own `join()`/`shutdown()` docstrings explicitly acknowledge "Failed or undrainable events may be dropped."
- **Backwards compatibility:** Breaking — re-enqueueing failed batches changes delivery/ordering semantics (duplicate-send risk, unbounded queue growth under sustained outage) that the current design deliberately avoids. Any fix should be opt-in rather than a silent default-behavior change.
- **Remediation:** Add an opt-in "retain failed batches for next flush cycle" mode, clearly documented as changing delivery-ordering guarantees; keep drop-on-exhaustion as the default to avoid surprising existing integrations.

### n7 — Get Distinct ID (🟡 Partial)
- **Spec requires:** Spec's own `## Applicability` says `client`, but the acceptance feature `get-distinct-id.feature` is tagged `@both` at the feature level and contains an explicit `@server` scenario: "Server SDKs do not expose ambient distinct id state" — `WHEN get distinct id is called on a server SDK THEN the SDK should report that no ambient distinct id is available.` This models a defined, satisfiable server contract: server SDKs are expected to expose *some* callable answering this question, even if the answer is "no ambient id available."
- **SDK currently:** No `get_distinct_id()` method exists on `Client` or at module level (`posthog/__init__.py`) at all — confirmed via `grep -rn "def get_distinct_id" posthog/*.py` (zero matches). `contexts.py`'s internal helpers (e.g. `get_context_distinct_id()`) only read an explicitly-set `contextvars` value inside a `with new_context()` block for internal event-enrichment use, and are not a general-purpose, always-callable public API answering the acceptance scenario's question. There is no public symbol a caller can invoke to get the "no ambient id available" answer the scenario expects.
- **Backwards compatibility:** Backward-compatible — adding a `get_distinct_id()` that returns `None` (or a documented sentinel) outside of an active context, and returns the context's id inside one, is purely additive.
- **Remediation:** Add a public `Client.get_distinct_id()` / module-level `posthog.get_distinct_id()` that returns the current context's distinct id if set, else `None`, satisfying the `@server` scenario explicitly.

### n8 — Get Feature Flag Payload (🟡 Partial)
- **Spec requires:** `get_feature_flag_payload(key, distinct_id, ...)` evaluated standalone (independent of any prior `get_feature_flag` call), suppressing `$feature_flag_called` by default (`send_feature_flag_events=False`), returning `None` on a missing flag without raising.
- **SDK currently:** `Client.get_feature_flag_payload` (`posthog/client.py:3582-3595`) correctly defaults `send_feature_flag_events=False`. But the **module-level** free function `posthog.get_feature_flag_payload` (`posthog/__init__.py:936-947`) still defaults `send_feature_flag_events=True` (line 944), contradicting the `Client` method's spec-correct default — top-level callers (the SDK's most common usage pattern, `import posthog; posthog.get_feature_flag_payload(...)`) get unwanted `$feature_flag_called` events by default.
- **Backwards compatibility:** Backward-compatible — flipping the `__init__.py` module-level default from `True` to `False` only reduces unwanted analytics events; no signature change. Worth a changelog callout since it changes a default side effect for existing callers relying on the current default.
- **Remediation:** Change `posthog/__init__.py`'s `get_feature_flag_payload` default `send_feature_flag_events` to `False`, matching `Client.get_feature_flag_payload`.

### n9 — Is Feature Enabled (🟡 Partial, upgraded from ❌)
- **Spec requires:** `both`. The SDK SHALL accept a caller-supplied boolean default and return it whenever the flag has no value (missing key, not loaded, failed request); a flag with any value (including `False`/variant) always wins over the default.
- **SDK currently:** The legacy, primary-surface `Client.feature_enabled` (`posthog/client.py:3171-3235`) still has **no `default_value` parameter at all** — signature is `feature_enabled(key, distinct_id, *, groups, person_properties, group_properties, only_evaluate_locally, send_feature_flag_events=True, disable_geoip, device_id)` — and unconditionally returns `None` on a missing/failed flag, with no way for a caller to make it resolve to `True`/`False` on a miss. It is now marked with a `DeprecationWarning` pointing at the newer API. Its designated successor, `Client.evaluate_flags(...).is_enabled(key, default_value=False)` (`posthog/feature_flag_evaluations.py:93-109`), **does** accept and correctly honor a caller-supplied `default_value`, confirmed by `test_is_enabled_prefers_flag_value_over_default_value` — fully satisfying this spec's requirement, just via the newer two-step call shape rather than the single legacy method. Since a fully compliant, non-deprecated path exists on the same SDK, this is upgraded from the previous ❌ to 🟡 (primary/most-discoverable legacy method still non-compliant; successor is compliant).
- **Backwards compatibility:** Backward-compatible — adding `default_value` to `feature_enabled()` is a purely additive optional parameter, though arguably low-priority given the method is being sunset in favor of `evaluate_flags()`.
- **Remediation:** Either add `default_value: bool = False` to legacy `feature_enabled()` for parity, or explicitly document `evaluate_flags(...).is_enabled(default_value=...)` as the spec-compliant replacement and steer callers there.

### n10 — Set/Reset Person/Group Properties For Flags (❌ Fail, all four contracts)
- **Spec requires:** Each of these four specs' own `## Applicability` line says `client` ("Server SDKs usually take person/group properties directly on each flag-evaluation call instead of maintaining a persistent local override store"). However, all four acceptance feature files (`set-person-properties-for-flags.feature`, `set-group-properties-for-flags.feature`, `reset-person-properties-for-flags.feature`, `reset-group-properties-for-flags.feature`) are tagged `@both` at the feature level *and* on every individual scenario (re-confirmed by direct read), with concrete, generically-written scenarios that make no client-only assumption and are mechanically satisfiable server-side. Per this audit's acceptance-precedence convention, these are treated as in-scope-but-unimplemented rather than N/A. (By contrast, the sibling `Set Person Properties` contract's acceptance file stayed `@client`-only with no override, so it correctly remains ➖.)
- **SDK currently:** `grep -rn "person_properties_for_flags\|group_properties_for_flags\|properties_for_flags"` across the entire repo returns zero matches for all four. `person_properties`/`group_properties` exist only as per-call kwargs on `get_feature_flag`/`get_all_flags`/`evaluate_flags`, never persisted between calls; `feature_flag_evaluations.py`'s `FeatureFlagEvaluations` is an immutable per-call snapshot, not a mutable persistent override cache; `contexts.py` (542 lines, read in full) has no property-override-store pattern either. `group_identify()` emits a `$groupidentify` **event** to update the group profile server-side but is not a local override cache consulted by subsequent flag-evaluation calls, so it doesn't satisfy these contracts. No `reset_*_properties_for_flags()`/`set_*_properties_for_flags()` methods exist anywhere.
- **Backwards compatibility:** Backward-compatible — a new opt-in stateful override cache (e.g. scoped to `contexts.py`'s per-request/task context, mirroring the existing `contextvars`-based session/distinct-id pattern) would be purely additive; no existing call signature needs to change.
- **Remediation:** Add `set_person_properties_for_flags()`/`set_group_properties_for_flags()`/`reset_person_properties_for_flags()`/`reset_group_properties_for_flags()` on `Client`, backed by a context-scoped override store consulted by the flag-evaluation call sites as a default merged with (and overridable by) explicit per-call `person_properties`/`group_properties`. Also worth flagging upstream to sdk-specs maintainers: the spec-prose `Applicability: client` and the acceptance files' `@both` tags are inconsistent and should be reconciled.

### n11 — Shutdown (🟡 Partial)
- **Spec requires:** `@both`. Flush pending events, stop workers permanently, reject/no-op future captures, be idempotent, and not crash on delivery failure (record a delivery warning instead). Error Handling section now says Promise-based SDKs SHOULD *resolve* (not reject) on shutdown-timeout, logging a critical diagnostic instead — this clause explicitly scopes to "Promise-based SDKs."
- **SDK currently:** `Client.shutdown()` (`posthog/client.py:2766`, fully synchronous/void, no `timeoutMs`/Promise return type — the Promise-timeout-resolve clause is confirmed N/A for Python, matching the spec's own "Surface Variants" table listing `Python: shutdown(): void`) delegates to lifecycle helpers that: close every lane then drain queues (`_shutdown_once`), join consumer threads and stop the feature-flag poller / flag-definition cache provider (`_join_once`), explicitly clear the feature-flag-called dedupe tracker (`self.distinct_ids_feature_flags_reported.clear()`), and check `self._shutdown_complete` for idempotency (tested extensively, including join/shutdown race conditions, in `test_client.py`). `_Lane.enqueue()` checks `self._closed` and drops-with-log any event received after shutdown. `Consumer.upload()` never propagates delivery-failure exceptions (logs + optional `on_error`, always calls `queue.task_done()`), and the whole `shutdown()` method is wrapped so it cannot throw. One remaining deviation: calling `shutdown()` from within an `on_error`/lifecycle-callback context is deferred to a background daemon thread (`_defer_lifecycle_from_callback`) rather than blocking synchronously — an intentional, documented anti-deadlock measure for that narrow reentrant case, not a spec violation (the spec doesn't test or forbid this), but a real, worth-flagging deviation from naive synchronous-shutdown expectations.
- **Backwards compatibility:** Needs deprecation path — the callback-deferral behavior is intentional (avoids a deadlock) and shouldn't silently change; document it as a known, accepted deviation rather than "fixing" it away, since doing so risks reintroducing the deadlock it was designed to prevent.
- **Remediation:** Document the callback-deferral edge case explicitly in the public API docs as an accepted platform-specific variation; no code change recommended given the deadlock risk. (Downgraded from being the sole open item — all other Shutdown requirements are confirmed compliant on re-verification.)

### n12 — Before Send Hook (🟡 Partial)
- **Spec requires:** `both` applicability, acceptance `@both`. A `beforeSend(event) -> event | null` hook run after event assembly and before enqueue; can mutate or drop (`null`/`None` return); spec explicitly frames multi-hook chaining as an optional capability ("Some SDKs allow multiple hooks... Support hook chaining **when configured as an array**"), stopping the chain on drop; hook exceptions must not crash the caller.
- **SDK currently:** Single choke point `_enqueue()` (`posthog/client.py`), fed by `capture`, `set`/`set_once`, `group_identify`, `alias`, `capture_exception`, `capture_ai`, and `$feature_flag_called` emission — covers all event types. `before_send` executes after `clean(msg)` and property assembly; returning `None` drops the event (logged); a mutated dict is re-cleaned and used; hook exceptions are caught, logged, and fall back to the original message — confirmed via `posthog/test/test_before_send.py`. Deviation: only a single callable is supported (`_set_before_send()`; `BeforeSendCallback = Callable[[dict], Optional[dict]]`, `types.py`) — no `List[BeforeSendFn]` chaining, so the optional "some SDKs" chaining behavior is unimplemented. None of the acceptance scenarios test chaining, so the acceptance suite itself passes; this is a narrower gap than a hard `SHALL`.
- **Backwards compatibility:** Backward-compatible — widening the parameter type to accept `Union[Callable, List[Callable]]` doesn't break existing single-callable callers.
- **Remediation:** Accept a list of callables in addition to a single callable in `_set_before_send()`, running each in order and stopping the chain on a `None`/drop return.

### n13 — Event Batcher (🟡 Partial)
- **Spec requires:** `both`. Accumulate events; flush at a count threshold (`flushAt`) or on an interval timer (`flushInterval`); cap total batch payload size; preserve FIFO order; explicit flush/shutdown drains immediately; spec notes "some SDKs" shrink the batch and retry on HTTP 413.
- **SDK currently:** Defaults `flush_at=100`, `flush_interval=5.0`s, `max_queue_size=10000`. `Consumer.next()` flushes on count threshold, interval timeout, or the `BATCH_SIZE_LIMIT` (5 MiB) cap; a per-event cap `MAX_MSG_SIZE` (900 KiB, or `AI_MAX_MSG_SIZE` 8 MiB on the AI lane) drops oversized single events before batching. FIFO preserved via stdlib `queue.Queue`. Explicit drain via `flush()`/`shutdown()`. Re-confirmed via `grep -rn "413" posthog/`: `consumer.py::is_retryable()` excludes 413 from the retryable set, and `capture_v1.py`'s `_TERMINAL_STATUSES` explicitly includes 413 as terminal (dropped, not retried/shrunk) — no 413-triggered adaptive batch-size shrink-and-retry exists anywhere in the ingestion path. This is an explicitly optional ("some SDKs") spec item, so this is a minor deviation, not a hard gap.
- **Backwards compatibility:** Backward-compatible — adding 413-triggered shrink-and-retry logic is additive and doesn't change existing behavior for other status codes.
- **Remediation:** Low priority given the spec frames this as optional; if pursued, add a batch-split-and-retry path specifically for HTTP 413 responses.

### n14 — Exception Event Metadata (❌ Fail)
- **Spec requires:** `both` applicability. Canonical `$exception_list` envelope where every entry has a `mechanism` object; `mechanism.handled` SHALL be serialized when the capture boundary knows whether the exception escaped the application boundary, and the producer "MUST NOT serialize unknown as `false`" (explicit anti-pattern); `mechanism.synthetic` similarly MUST NOT default to `false` when unknown; nested-exception tree linkage via `mechanism.exception_id`/`parent_id`/`source` (canonical `source` values: `cause`, `context`, `unwrap`, `member`, `suppressed`, `inner`), with a 50-entry truncation cap; `$exception_source` set only from concrete capture-boundary knowledge (e.g. `django.middleware`, `celery.task_failure`), never inferred from installed dependencies/stack frames, and never conflated with `mechanism.type`; `$exception_level` normalization; typed/explicit mechanism overrides take precedence over an application's arbitrary properties bag (properties MUST NOT silently clobber SDK-owned envelope fields); native debug-image metadata (N/A for pure Python).
- **SDK currently:** `single_exception_from_error_tuple` (`posthog/exception_utils.py:526-528`) hardcodes `exception_value["mechanism"] = mechanism.copy() if mechanism else {"type": "generic", "handled": True}` — this is the SDK's **only** mechanism-construction call site (also duplicated in `posthog/mcp/_exceptions.py`), and it defaults `handled` to `True` whenever no mechanism is explicitly supplied, which is the exact anti-pattern the spec calls out ("MUST NOT serialize unknown as false... or guess"), except worse — it asserts a specific, frequently-wrong value rather than merely guessing false. This is confirmed by the SDK's **own passing test**: `test_exception_capture.py::test_excepthook` (line ~275) raises an uncaught `ZeroDivisionError` all the way to `sys.excepthook` — a textbook case of an exception escaping the application boundary, which the spec requires `handled: false` for — and asserts the wire payload contains `"mechanism": {"type": "generic", "handled": true}`. `mechanism.synthetic` is never populated anywhere (`grep -rn synthetic` → zero hits), including in `construct_artificial_traceback()`, a textbook `synthetic: true` case. `$exception_source` is never set anywhere (`grep -rn "exception_source"` → zero hits outside unrelated files); Django's `process_exception` and Celery's failure handler both call bare `capture_exception(exception)` with no source/category metadata, so no `django.middleware`/`celery.task_failure` values are ever emitted. Nested-exception tree linkage is absent on the common (non-`ExceptionGroup`) path: `exceptions_from_error_tuple` calls `single_exception_from_error_tuple` with no `exception_id`/`parent_id`/`source` args for ordinary `raise B from A`/implicit-`__context__` chains, so every entry looks like an independent root; only the Python 3.11+ `ExceptionGroup`-only path has any linkage, and even there `source` values are raw Python internals (`"__cause__"`, `"__context__"`) rather than the canonical `cause`/`context` vocabulary. No 50-entry cap exists anywhere. `$exception_level` is never set by the core `capture_exception` path at all. Precedence is backwards: `client.py`'s exception-properties assembly spreads the caller's `properties` dict **last** (`{"$exception_list": ..., **_get_current_otel_span_properties(), **properties}`), so an application's arbitrary property bag can silently override `$exception_list` itself, with no allowlist/blocklist protecting SDK-owned keys. Debug-image metadata is correctly and appropriately never set (pure Python has no native/instruction-address frames) — this one aspect is compliant by virtue of being correctly out of scope.
- **Backwards compatibility:** Mixed — threading boundary-specific `mechanism`/`$exception_source` metadata through `capture_exception`/`ExceptionCapture`/Django/Celery integrations, adding tree linkage for the plain-chain path, and adding `$exception_level` normalization are all additive (Backward-compatible). Fixing the properties-merge precedence to protect reserved keys is narrowing/breaking for any caller currently (ab)using `properties` to override `$exception_list` — low real-world risk since that's already a bug today, but technically an observable behavior change. Remapping `ExceptionGroup`'s non-canonical `source` values to the canonical vocabulary is a breaking wire-value change for those specific already-nonconformant values.
- **Remediation:** (1) Change the mechanism default from `{"type": "generic", "handled": True}` to a linkage-only mechanism when `handled` is genuinely unknown, and thread an explicit `handled=False` from `sys.excepthook`/uncaught-exception paths since those definitively escaped the process; (2) set `mechanism.synthetic` explicitly in `construct_artificial_traceback()` and omit it elsewhere; (3) add `$exception_source` values from Django/Celery/FastAPI integration call sites; (4) pass `exception_id`/`parent_id`/`source` through the plain chained-exception path, not just the `ExceptionGroup` path, and cap the chain at 50 entries; (5) add `$exception_level` normalization to the core path; (6) reorder the properties merge so SDK-owned envelope keys (`$exception_list`, `$exception_level`, `$exception_source`) can't be overridden by the caller's arbitrary `properties` dict.

### n15 — Feature Flag Cache (🟡 Partial)
- **Spec requires:** Spec prose applicability says `client`, but the acceptance file (`acceptance/private/feature-flag-cache.feature`) is tagged `@both` with generic scenarios ("Cache serves reads without a network request," "Cache is cleared on identity reset") that are mechanically applicable server-side too — treated as in-scope per this audit's acceptance-precedence rule (this spec/acceptance-tag mismatch persists unresolved since the last audit). Requires an internal store serving evaluated flag values/payloads from local memory as the *primary* read path (no network call on a cache hit), populated on load, cleared on reset/identity invalidation.
- **SDK currently:** `posthog/utils.py`'s `FlagCache`/`RedisFlagCache` implement a genuine per-`(distinct_id, flag_key)` evaluated-result cache with TTL/version/LRU eviction, written on every evaluation via `set_cached_flag`. Re-confirmed the read path is still **never exercised on the normal/happy path**: `_get_stale_flag_fallback()` is called exclusively from exception handlers (`QuotaLimitError`, timeouts, connection errors, `APIError`, generic `Exception`) inside `_get_feature_flag_result`, so every ordinary call still re-evaluates locally or re-fetches remotely; the cache never short-circuits a normal call the way "serves reads without a network request" requires. There is still no client-side `reset()`-equivalent method (server SDK, stateless per-call), so "cache cleared on identity reset" has no code path to satisfy — though `flag_cache.invalidate_version()` does fire on flag-*definition* changes (a different, narrower invalidation trigger).
- **Backwards compatibility:** Backward-compatible — making `FlagCache` a primary read-path (opt-in, since server SDKs often want per-request freshness) would be additive; no removal needed.
- **Remediation:** Either (a) document that `FlagCache` is intentionally fallback-only (a staleness-tolerance mechanism, not a read-path optimization) and note the spec/acceptance-tag mismatch upstream, or (b) add an opt-in "serve from cache first" mode consulted before remote/local evaluation.

### n16 — Retry Queue (🟡 Partial)
- **Spec requires:** `both`. In-memory/persisted queue with backpressure/drop-when-full; flush on size/timer/explicit trigger; classify retryable (network errors, 5xx, 429, timeouts) vs. non-retryable (most 4xx) failures; exponential/linear backoff honoring `Retry-After`; retryable failures keep the same events queued/stored for a later, separate flush attempt; success removal by identity/stable-id (not index) so concurrently-captured events aren't confused with the in-flight batch; terminal/exhausted failures drop the batch.
- **SDK currently:** In-memory `queue.Queue(max_queue_size=10000)` per lane; full-queue drops with a warning log (`_Lane.enqueue`) — no cross-restart persistence, which the spec allows. Retry classification in `consumer.py::is_retryable()` correctly treats network exceptions, 408/429, and 5xx as retryable and other 4xx (including 413) as terminal. Backoff is exponential, base-doubling, capped, and floors on server `Retry-After` — matches spec, and the dedicated feature-flags retry path (`request.py::flags()`) implements a separate, precisely-specified 300ms/600ms-doubling, 502/504-only, max-one-retry-by-default policy matching a newly-added spec requirement exactly. Deviation (unchanged from previous audit): retries happen **synchronously inside the same blocking `_send()`/`upload()` call** on the already-dequeued batch, not by re-enqueueing into `self.queue` for a later, independent `Consumer.next()` flush cycle as the spec's general model describes; once dequeued, an item is never returned to the queue, and if all attempts fail within that one call, the batch is permanently dropped (via `on_error`), not preserved for a subsequent independent flush. The "concurrent events not mistaken for in-flight batch" requirement is naturally satisfied by `queue.Queue.get()`'s removal-based dequeue. No 413-shrink-and-retry (optional per spec), consistent with the Event Batcher finding (n13).
- **Backwards compatibility:** Needs deprecation path — converting to a true requeue-for-next-flush model changes `on_error` callback timing and consumer-thread blocking semantics (currently blocks synchronously through multiple attempts × capped backoff), an observable behavior change for existing integrations that time or depend on current `on_error`/blocking timing.
- **Remediation:** If pursued, introduce a requeue-on-exhaustion path as an opt-in mode (e.g. a new constructor flag) rather than changing the default synchronous-retry-then-drop behavior, to avoid silently changing blocking/timing semantics for existing integrations.
