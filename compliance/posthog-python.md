## Notes

### n1 — Logs (❌ Fail)
- **Spec requires:** A `captureLog`/logger API that produces OTLP-shaped log records and ships them via `POST {host}/i/v1/logs`, with severity-number mapping, batching/rate-capping, gzip, and retry/413 handling.
- **SDK currently:** No implementation at all. `grep` for `captureLog`, `i/v1/logs`, `logRecord`, `severityNumber` across the repo returns zero matches. `posthog/_logging.py` is exclusively stdlib `logging`-based internal SDK diagnostics (prefixes messages with `"[PostHog]"`) — unrelated to the product Logs capability. `posthog/metrics_capture.py` implements a separate, unrelated OTLP *metrics* pipeline.
- **Backwards compatibility:** Backward-compatible — this is a net-new, purely additive subsystem; nothing existing needs to change or be removed.
- **Remediation:** Implement a `capture_log`/`Logger` surface mirroring the client SDKs' OTLP-log shape, wired to a new `/i/v1/logs` transport, with its own batching/rate-cap policy.

### n2 — Traces (❌ Fail)
- **Spec requires:** A `startSpan`/`withSpan` API producing OTLP spans shipped to `POST {host}/i/v1/traces`, explicitly distinct from LLM-analytics-as-events and requiring no OpenTelemetry runtime dependency.
- **SDK currently:** No `startSpan` or `/i/v1/traces` route exists anywhere (`posthog/client.py`, `posthog/request.py`). What exists instead: (a) LLM observability captured as ordinary `$ai_generation` analytics events tagged with `$ai_trace_id` (`posthog/ai/utils.py:468,527,621,680,751,835`) — the spec's own explicitly-excluded case ("LLM analytics traces captured as analytics events, not OTLP"); and (b) `posthog/ai/otel/processor.py`, which *depends on* the external `opentelemetry-sdk`/`opentelemetry-exporter-otlp-proto-http` packages (contradicting the "no OTel runtime dependency" requirement) and forwards only AI-semantic-convention spans to a different endpoint, `/i/v0/ai/otel`, not `/i/v1/traces`.
- **Backwards compatibility:** Backward-compatible — a net-new subsystem alongside the existing AI-events/OTel-bridge features; no removal needed.
- **Remediation:** Implement a dependency-free `start_span`/`with_span` API shipping OTLP spans to `/i/v1/traces`, independent of the `posthog/ai/otel` bridge.

### n3 — Tracing Headers (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side responsibilities: request-scoped middleware extracting `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` (case-insensitively) into context; sanitize (trim/strip control chars/cap length); explicit call-site values take precedence over context; personless-capture fallback (random `distinct_id` + `$process_person_profile=false`) when no identity is resolvable; flag-evaluation APIs should no-op/return-empty (no network call, no `$feature_flag_called`) when no identity is resolvable anywhere; per-request isolation; headers never used for auth.
- **SDK currently:** `posthog/contexts.py` implements genuine `contextvars.ContextVar`-based per-task isolation with fork-safety (`os.register_at_fork`, `contexts.py:145-146`). `posthog/integrations/django.py` implements real middleware with header extraction (`django.py:171-181`), sanitization (`_sanitize_tracing_header_value`, `django.py:26-52`), and sync+ASGI-async support. `posthog/integrations/celery.py` propagates the same headers producer→worker. Personless fallback matches spec exactly (`client.py:136-146` `get_identity_state()`, `client.py:1497-1500` sets `$process_person_profile=False`). Gaps: (1) the identity-required-for-flags no-op behavior is only honored by the newer `evaluate_flags()`/`FeatureFlagEvaluations` API (`client.py:3935-3948`) — the older, still-primary `feature_enabled`/`get_feature_flag`/`get_all_flags` APIs require `distinct_id` as a mandatory positional argument with no context-fallback and no empty/no-op path, so they can't exhibit the spec's described failure mode but also can't benefit from the context-fallback convenience the spec permits; (2) only Django and Celery integrations exist — no Flask/FastAPI-specific middleware, narrowing real-world framework coverage.
- **Backwards compatibility:** Backward-compatible — adding an optional context-fallback default for `distinct_id` on the legacy flag APIs, and adding Flask/FastAPI middleware, are both purely additive.
- **Remediation:** Make `distinct_id` optional (falling back to `contexts.py` ambient value, else no-op) on `feature_enabled`/`get_feature_flag`/`get_all_flags`; add Flask/FastAPI middleware modules alongside the existing Django/Celery ones.

### n4 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Enrich events with `distinct_id`/timestamp/uuid/`$lib`+`$lib_version`/super-properties/`$groups`; honor an opt-out state so that capture is dropped silently with no network call (acceptance scenario "Capture honors opt-out state" is tagged `@both`); support a `before_send` hook that can mutate/drop events.
- **SDK currently:** `Client._capture`/`_enqueue` (`posthog/client.py:1476-1606`, `2107-2252`) correctly resolves identity via `get_identity_state()` (`client.py:136-146`), stamps `$lib`/`$lib_version` (`2141-2142`), timestamp/uuid (`2117-2136`), merges `super_properties` (`2150-2151`), and runs `before_send` (`2170-2181`). However there is no dynamic, runtime-toggleable opt-out API (`grep` for `opt_out`/`opt_in`/`is_opted_out` across `posthog/*.py` returns zero matches). The only short-circuit is the constructor-time `disabled` flag (`client.py:812`, checked at `2114`), a static kill-switch set once at construction — not the dynamic per-call opt-out toggle the `@both`-tagged acceptance scenario models (it does satisfy the literal scenario if `disabled` is treated as the opt-out mechanism, but there's no dedicated `opt_out_capturing()`/`is_opted_out()` API pair as other server SDKs, e.g. posthog-node, expose).
- **Backwards compatibility:** Backward-compatible — adding `opt_in()`/`opt_out()`/`is_opted_out()` methods that toggle a new or existing internal flag is purely additive.
- **Remediation:** Add a dynamic `opt_out_capturing()` / `opt_in_capturing()` / `is_opted_out()` API on `Client`, distinct from the static `disabled` kill switch, mirroring other server SDKs.

### n5 — Capture Exception (🟡 Partial)
- **Spec requires:** `captureException(error, properties?)` emits a `$exception` event with correctly-ordered `$exception_list` (outermost/caught-first, root-cause-last), correctly-ordered stack frames, ascending source-context lines, preserved (not synthesized) stack traces when available, and flat `$exception_type`/`$exception_message` top-level properties. Note: spec's own `## Applicability` line says `client` ("audited implementations live in client/mobile SDKs"), but the acceptance feature `capture-exception.feature` is tagged `@both` at every scenario, and posthog-python has a mature, dedicated implementation — treated as in-scope per the acceptance tags (more precise than stale spec prose) and the SDK's own investment in the feature.
- **SDK currently:** `Client.capture_exception` (`posthog/client.py:1871`) correctly builds ordered `$exception_list` via `exceptions_from_error_tuple`/`walk_exception_chain` (`exception_utils.py:582,709`, confirmed by `test_exception_capture.py:320`), correct bottom-up frame ordering (`iter_stacks`, `exception_utils.py:336`), correct ascending `pre_context`/`context_line`/`post_context` windows (`get_lines_from_file`, `exception_utils.py:345`), and preserves existing `__traceback__` rather than synthesizing one (`exc_info_from_error`, `exception_utils.py:853`). However, **no top-level `$exception_type`/`$exception_message` properties are ever emitted** — `grep` for these strings across the SDK (excluding tests) returns zero matches; the SDK only nests `type`/`value` inside `$exception_list[0]`. This is deliberate: `posthog/CHANGELOG.md:692` records `## 7.3.1 - 2025-12-06` → `fix: remove unused $exception_message and $exception_type`. This directly contradicts the acceptance scenario "Capturing a handled exception emits an exception event" (`capture-exception.feature:12-21`), which requires `$exception_type=TypeError`/`$exception_message=boom` as enqueued properties.
- **Backwards compatibility:** Backward-compatible — re-adding `$exception_type`/`$exception_message` as flat properties (mirroring `$exception_list[0].type`/`.value`) is additive and doesn't remove or rename anything currently emitted; confirm no downstream ingestion/UI conflict was the reason they were removed before reverting.
- **Remediation:** Re-add `$exception_type` and `$exception_message` as flat top-level properties on the `$exception` event, sourced from `$exception_list[0]`.

### n6 — Flush (🟡 Partial)
- **Spec requires:** `@both`. No-op on empty queue with no network call; bypass `flush_at`/`flush_interval` and drain immediately; on delivery failure (e.g. 503) must not throw, and the failed event must remain queued for a later retry.
- **SDK currently:** `Client.flush()` (`posthog/client.py:2289-2318`) correctly blocks on `queue.unfinished_tasks` (`416-458`), is a no-op on an empty queue, and bypasses batching intervals — matching the spec on those points. But `Consumer.upload()` (`consumer.py:167-193`) unconditionally calls `queue.task_done()` in a `finally` block regardless of send success, and `Consumer._send()` (`consumer.py:307-345`) exhausts `max_retries` (default 3) then raises; `upload()` catches/logs/calls `on_error`, but the batch is **not re-enqueued** — it is permanently dropped. `flush()` itself doesn't throw (matches spec), but failed events are not retained for retry as required.
- **Backwards compatibility:** Breaking — re-enqueueing failed batches changes delivery/ordering semantics (duplicate-send risk, unbounded queue growth under sustained outage) that the current design deliberately avoids (its own docstrings state "Failed or undrainable events may be dropped"). Any fix should be opt-in rather than a silent default-behavior change.
- **Remediation:** Add an opt-in "retain failed batches for next flush cycle" mode, clearly documented as changing delivery-ordering guarantees; keep drop-on-exhaustion as the default to avoid surprising existing integrations.

### n7 — Get Distinct ID (🟡 Partial)
- **Spec requires:** Spec's own `## Applicability` says `client`, but the acceptance feature `get-distinct-id.feature` is tagged `@both` at the feature level and contains an explicit `@server` scenario: "Server SDKs do not expose ambient distinct id state" — `WHEN get distinct id is called on a server SDK THEN the SDK should report that no ambient distinct id is available." This models a defined, satisfiable server contract: server SDKs are expected to expose *some* callable answering this question, even if the answer is "no ambient id."
- **SDK currently:** No `get_distinct_id()` method exists on `Client` or at module level (`posthog/__init__.py`) at all. `ContextScope.get_distinct_id()` (`contexts.py:74-79`) only reads an explicitly-set `contextvars` value inside a `with new_context()` block, not a general ambient-identity API answering the acceptance scenario's question. There's no public, always-available symbol a caller can invoke to get the "no ambient id" answer the scenario expects.
- **Backwards compatibility:** Backward-compatible — adding a `get_distinct_id()` that returns `None` (or raises a documented sentinel) outside of an active context, and returns the context's id inside one, is purely additive.
- **Remediation:** Add a public `Client.get_distinct_id()` / module-level `posthog.get_distinct_id()` that returns the current context's distinct id if set, else `None`, satisfying the `@server` scenario explicitly.

### n8 — Get Feature Flag Payload (🟡 Partial)
- **Spec requires:** `get_feature_flag_payload(key, distinct_id, ...)` evaluated standalone (independent of any prior `get_feature_flag` call), suppressing `$feature_flag_called` by default (`send_feature_flag_events=False`), returning `None` on a missing flag without raising.
- **SDK currently:** `Client.get_feature_flag_payload` (`posthog/client.py:3445-3458`) correctly defaults `send_feature_flag_events=False`, confirmed by `test_get_feature_flag_payload_does_not_send_feature_flag_called_events`. But the **module-level** free function `posthog.get_feature_flag_payload` in `posthog/__init__.py` (~896-946) defaults `send_feature_flag_events=True`, contradicting the `Client` method's spec-correct default — top-level callers (the SDK's most common usage pattern, `import posthog; posthog.get_feature_flag_payload(...)`) get unwanted `$feature_flag_called` events by default. Secondary, smaller asymmetry: `match_value` correctly overrides the payload lookup on the local-eval path but the remote-eval path always reflects the server's actual evaluated value regardless of `match_value` override (`types.py:274-279`).
- **Backwards compatibility:** Backward-compatible — flipping the `__init__.py` module-level default from `True` to `False` only reduces unwanted analytics events; no signature change. Worth a changelog callout since it changes a default side effect (fewer `$feature_flag_called` events sent) for existing callers relying on the current default.
- **Remediation:** Change `posthog/__init__.py`'s `get_feature_flag_payload` default `send_feature_flag_events` to `False`, matching `Client.get_feature_flag_payload`.

### n9 — Group Identify (🟡 Partial)
- **Spec requires:** `both` applicability. Validate that `group_type`/`group_key` are present (drop + warn otherwise — acceptance scenario "Group identify requires type and key" is tagged `@both`); build `$groupidentify` with `$group_type`/`$group_key`/`$group_set`.
- **SDK currently:** `Client.group_identify()` (`posthog/client.py:1745-1803`) correctly builds the `$groupidentify` event shape and enqueues it (`1803`) — matches the happy-path scenario. But there is **no validation** of `group_type`/`group_key` presence/emptiness anywhere in the function or in `_enqueue`; calling with a missing or empty key still enqueues an event, directly contradicting the `@both`-tagged acceptance scenario, which expects zero events plus a validation warning when type/key are missing.
- **Backwards compatibility:** Needs deprecation path — adding a drop-on-missing-key check changes behavior for any caller currently getting an event enqueued with a falsy/empty type or key; roll out as a warning first, then start dropping in a later minor/major release.
- **Remediation:** Add presence/emptiness validation on `group_type`/`group_key` in `group_identify()`, logging a warning and returning without enqueueing when either is missing/empty — phase in via a deprecation warning first.

### n10 — Is Feature Enabled (❌ Fail)
- **Spec requires:** Hard `SHALL`, `@both`, no SDK carve-out for omitting the parameter: "The SDK SHALL accept a caller-supplied boolean default... and SHALL return it whenever the flag has no value" (missing key, not loaded, failed request). A flag with any value (including `False`/variant) always wins over the default.
- **SDK currently:** `Client.feature_enabled` (`posthog/client.py:3034-3098`) has **no `default_value` parameter at all** — signature is `feature_enabled(key, distinct_id, *, groups, person_properties, group_properties, only_evaluate_locally, send_feature_flag_events=True, disable_geoip, device_id)`. On a missing/failed flag it unconditionally returns `None` (line 3096-3097), confirmed by `test_feature_enabled_doesnt_exist` — there is no way for a caller to make it resolve to `True`/`False` on a miss. The SDK's own deprecation successor, `evaluate_flags(...).is_enabled()` (`posthog/feature_flag_evaluations.py:93-109`), does have `default_value: bool = False` and correctly prefers a present value over the default (`test_is_enabled_prefers_flag_value_over_default_value`) — but neither `is_enabled()` nor `get_flag()` support a per-call tracking-suppression parameter; every access unconditionally calls `capture_flag_called_event_if_needed` (`feature_flag_evaluations.py:270-279`), only deduped by `(distinct_id, flag, value)`, failing the "suppress tracking" acceptance scenario on the successor API too. Neither the current primary API nor its designated successor fully satisfies the spec.
- **Backwards compatibility:** Backward-compatible — adding `default_value` to `feature_enabled()` and a tracking-suppression kwarg to `is_enabled()`/`get_flag()` are both purely additive optional parameters.
- **Remediation:** Add `default_value: bool = False` to `feature_enabled()` (or, since it's deprecated, prioritize adding it and a `send_feature_flag_event` kwarg to `evaluate_flags(...).is_enabled()` instead, and message that as the fix).

### n11 — Set/Reset Person/Group Properties For Flags (❌ Fail, all four contracts)
- **Spec requires:** Each of these four specs' own `## Applicability` line says `client` ("Server SDKs usually take person/group properties directly on each flag-evaluation call instead of maintaining a persistent local override store"). However, all four acceptance feature files (`set-person-properties-for-flags.feature`, `set-group-properties-for-flags.feature`, `reset-person-properties-for-flags.feature`, `reset-group-properties-for-flags.feature`) are tagged `@both` at the feature level *and* on every individual scenario, with concrete, generically-written scenarios (e.g. "Set person properties stores overrides for future flag evaluation," "Reset person properties affects subsequent flag evaluations") that make no client-only assumption and are mechanically satisfiable server-side. Per this audit's instructions to weight acceptance-test precision over spec prose, these are treated as in-scope-but-unimplemented rather than N/A.
- **SDK currently:** `grep -rn "person_properties_for_flags\|group_properties_for_flags"` across `/tmp/audit-posthog-python` returns zero matches for all four. `person_properties`/`group_properties` exist only as per-call kwargs on `get_feature_flag`/`get_all_flags`/`evaluate_flags` (e.g. `client.py:3350,3803`), never persisted between calls; there is no stateful override cache and no `reset_*_properties_for_flags()` method anywhere in `client.py`, `feature_flags.py`, or `contexts.py`.
- **Backwards compatibility:** Backward-compatible — a new opt-in stateful override cache (e.g. scoped to `contexts.py`'s per-request/task context, mirroring the existing `contextvars`-based session/distinct-id pattern) would be purely additive; no existing call signature needs to change.
- **Remediation:** Add `set_person_properties_for_flags()`/`set_group_properties_for_flags()`/`reset_person_properties_for_flags()`/`reset_group_properties_for_flags()` on `Client`, backed by a context-scoped override store consulted by the flag-evaluation call sites as a default merged with (and overridable by) explicit per-call `person_properties`/`group_properties`. Also worth flagging upstream to sdk-specs maintainers: the spec-prose `Applicability: client` and the acceptance files' `@both` tags are inconsistent and should be reconciled.

### n12 — Shutdown (🟡 Partial)
- **Spec requires:** `@both`. Flush pending events, stop workers permanently, reject/no-op future captures, be idempotent, and not crash on delivery failure (record a delivery warning instead).
- **SDK currently:** `Client.shutdown()` (`posthog/client.py:2628-2658`, wrapped in `@no_throw()`) delegates to `_run_lifecycle` (`2485-2577`): closes lanes (`405-408`), drains (`_flush_or_discard_queues`, `2419-2430`), joins consumer threads (`480-534`), stops the feature-flag poller (`poller.py:14-16`), clears the flag-called dedupe tracker (`2512-2515`). Idempotent via `_shutdown_complete` flag (`2525`, checked `2650-2654`). Post-shutdown `capture()` is dropped via a closed-lane check (`2239`). `consumer.upload()`'s `self.log.error(...)` (`consumer.py:181`) satisfies "record a delivery warning" loosely. Shares the same drop-on-failure behavior as `flush` (see n6) — failed batches during shutdown drain are not retained, though the shutdown scenario itself doesn't strictly require retry-retention. One additional deviation: calling `shutdown()` from within an `on_error`/lifecycle-callback context is silently deferred to a background daemon thread rather than blocking synchronously (`_defer_lifecycle_from_callback`, `2341-2368`) — an intentional, documented anti-deadlock measure, but a real deviation from synchronous shutdown semantics.
- **Backwards compatibility:** Needs deprecation path — the callback-deferral behavior is intentional (avoids a deadlock) and shouldn't silently change; document it as a known, accepted deviation rather than "fixing" it away, since doing so risks reintroducing the deadlock it was designed to prevent.
- **Remediation:** Document the callback-deferral edge case explicitly in the public API docs as an accepted platform-specific variation; no code change recommended given the deadlock risk.

### n13 — Before Send Hook (🟡 Partial)
- **Spec requires:** `both` applicability, acceptance `@both`. A `beforeSend(event) -> event | null` hook run after event assembly and before enqueue; can mutate or drop (`null`/`None` return); spec describes an optional-but-real capability where "some SDKs allow multiple hooks" chained, stopping on drop; hook exceptions must not crash the caller.
- **SDK currently:** Single choke point `_enqueue()` (`posthog/client.py:2107`), fed by `capture`, `set`/`set_once`, `group_identify`, `alias`, `capture_exception`, and `$feature_flag_called` emission — covers all event types. `before_send` executes at `client.py:2170-2181`, after `clean(msg)` and property assembly; returning `None` drops the event (`2173-2175`, logged); a mutated dict is re-cleaned and used (`2178`); hook exceptions are caught, logged, and fall back to the original message (`2179-2181`) — confirmed via `posthog/test/test_before_send.py`. Deviation: only a single callable is supported (`_set_before_send()`, `client.py:1041-1049`; `BeforeSendCallback = Callable[[dict], Optional[dict]]`, `types.py:9`) — no `List[BeforeSendFn]` chaining. None of the 3 acceptance scenarios test chaining (so the acceptance suite itself passes), but the fuller spec narrative describing multi-hook chaining is not met.
- **Backwards compatibility:** Backward-compatible — widening the parameter type to accept `Union[Callable, List[Callable]]` doesn't break existing single-callable callers.
- **Remediation:** Accept a list of callables in addition to a single callable in `_set_before_send()`, running each in order and stopping the chain on a `None`/drop return.

### n14 — Event Batcher (🟡 Partial)
- **Spec requires:** `both`. Accumulate events; flush at a count threshold (`flushAt`) or on an interval timer (`flushInterval`); cap total batch payload size; preserve FIFO order; explicit flush/shutdown drains immediately; spec notes "some SDKs" shrink the batch and retry on HTTP 413.
- **SDK currently:** Defaults `flush_at=100`, `flush_interval=5.0`s, `max_queue_size=10000` (`client.py:595-599`, mirrored in `consumer.py:107-113`). `Consumer.next()` (`consumer.py:214-286`) flushes on count threshold, interval timeout, or the `BATCH_SIZE_LIMIT = 5 MiB` cap (`consumer.py:32`); a per-event cap `MAX_MSG_SIZE = 900 KiB` (`consumer.py:21`) drops oversized single events before batching. FIFO preserved via stdlib `queue.Queue`. Explicit drain via `flush()`/`shutdown()`. Deviation: no 413-triggered adaptive batch-size shrink-and-retry — 413 is treated as a terminal, non-retryable status in both the v0 retry set (`consumer.py`) and v1 (`capture_v1.py:87` `_TERMINAL_STATUSES`). This is an explicitly optional ("some SDKs") spec item, so this is a minor deviation, not a hard gap.
- **Backwards compatibility:** Backward-compatible — adding 413-triggered shrink-and-retry logic is additive and doesn't change existing behavior for other status codes.
- **Remediation:** Low priority given the spec frames this as optional; if pursued, add a batch-split-and-retry path specifically for HTTP 413 responses.

### n15 — Feature Flag Cache (🟡 Partial)
- **Spec requires:** Spec prose applicability says `client`, but the acceptance file (`acceptance/private/feature-flag-cache.feature`) is tagged `@both` with generic scenarios ("Cache serves reads without a network request," "Cache is cleared on identity reset") that are mechanically applicable server-side too — treated as in-scope per this audit's acceptance-precedence rule. Requires an internal store serving evaluated flag values/payloads from local memory as the *primary* read path (no network call on a cache hit), populated on load, cleared on reset/identity invalidation.
- **SDK currently:** `posthog/utils.py:180-306` (`FlagCache`) and `:309+` (`RedisFlagCache`) implement a genuine per-`(distinct_id, flag_key)` evaluated-result cache with TTL/version/LRU eviction, wired in via `client.py:4153-4239` (`_initialize_flag_cache`) and written on every evaluation (`client.py:3179-3187,3224-3227`). But the **read path is never exercised on the normal/happy path** — `get_cached_flag` (a fresh read) is called only from tests, never from production code in `client.py`. Only `_get_stale_flag_fallback` (`client.py:3099-3109`) reads it, and only from exception handlers (`QuotaLimitError`, timeouts, connection errors, `APIError`, generic `Exception`, `client.py:3226-3252`) — so every ordinary call still re-evaluates locally or re-fetches remotely; the cache never short-circuits a normal call the way "serves reads without a network request" requires. There is also no `reset()`-equivalent method in posthog-python at all, so "cache cleared on identity reset" has no code path to satisfy.
- **Backwards compatibility:** Backward-compatible — making `FlagCache` a primary read-path (opt-in, since server SDKs often want per-request freshness) would be additive; no removal needed.
- **Remediation:** Either (a) document that `FlagCache` is intentionally fallback-only (a staleness-tolerance mechanism, not a read-path optimization) and note the spec/acceptance-tag mismatch upstream, or (b) add an opt-in "serve from cache first" mode consulted before remote/local evaluation.

### n16 — Feature Flag Called Tracker (🟡 Partial)
- **Spec requires:** Dedup `$feature_flag_called` by `(flag, value, distinct_id, normalized groups)`; bounded/LRU eviction (never a full clear under memory pressure); clear on shutdown; minimal-event mode gated by `minimalFlagCalledEvents`/`has_experiment===false`, with an allowlist that — per the most recent sdk-specs fix (commit `b59e8b4`, `fix(feature-flag-called-tracker): add session-attribution properties to minimal-event allowlist`) — includes 10 session-attribution properties (`$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid`) in addition to the pre-existing 21 core properties, while still excluding `$referrer`.
- **SDK currently:** `posthog/client.py:219-251` `_MINIMAL_FLAG_CALLED_EVENT_PROPERTIES` contains exactly the 21 pre-fix core properties but is **missing all 10 of the session-attribution properties** added by the sdk-specs fix in `b59e8b4` — i.e. posthog-python's allowlist reflects the spec's *previous* version, not its current one. Dedup key construction (`client.py:3646-3649`), gating logic (`client.py:3667`, fails safe on unknown `has_experiment`), bounded LRU eviction (`utils.py:154-174` `SizeLimitedDict`, incremental eviction, never a full clear), and shutdown-time clearing (`client.py:2508-2513`) all match the spec exactly and are well-tested (`test_feature_flag_called_minimization.py`, `test_size_limited_dict.py`). `test_feature_flag_called_minimization.py:82,107` explicitly assert generic super-properties are stripped, with no test carving out the UTM/referring-domain exceptions the spec now requires.
- **Backwards compatibility:** Backward-compatible — adding 10 keys to a filter allowlist is strictly additive; it can only make minimized events retain *more* previously-stripped properties in the rare case a caller has UTM/attribution data in `super_properties`, never less.
- **Remediation:** Add the 10 session-attribution property names from sdk-specs commit `b59e8b4` to `_MINIMAL_FLAG_CALLED_EVENT_PROPERTIES` in `posthog/client.py`.

### n17 — Retry Queue (🟡 Partial)
- **Spec requires:** `both`. In-memory/persisted queue with backpressure/drop-when-full; flush on size/timer/explicit trigger; classify retryable (network errors, 5xx, 429, timeouts) vs. non-retryable (most 4xx) failures; exponential/linear backoff honoring `Retry-After`; retryable failures keep the same events queued/stored for a later, separate flush attempt; success removal by identity/stable-id (not index) so concurrently-captured events aren't confused with the in-flight batch; terminal/exhausted failures drop the batch.
- **SDK currently:** In-memory `queue.Queue(max_queue_size=10000)` per lane (`client.py:330,595`); full-queue drops with a warning log (`client.py:2235-2251`, `_Lane.enqueue`, `client.py:377-387`) — no cross-restart persistence, which the spec allows. Retry classification in `is_retryable()` (`consumer.py:310-322`) correctly treats network exceptions, 408/429, and 5xx as retryable and other 4xx as terminal. Backoff via `_backoff()` (`capture_v1.py:425-440`): exponential base 1s doubling, capped 30s, floored by server `Retry-After` — matches spec. Deviation: retries happen **synchronously inside the same blocking `_send()`/`upload()` call** on the already-dequeued batch (an in-process attempt loop with `time.sleep` backoff), not by re-enqueueing into `self.queue` for a later, independent `Consumer.next()` flush cycle as the spec describes. Once dequeued via `queue.get()`, an item is never returned to the queue; if all attempts (default 10 retries) fail within that one call, the batch is permanently dropped (via `on_error`), not preserved for a subsequent independent flush. The "concurrent events not mistaken for in-flight batch" requirement is naturally satisfied by `queue.Queue.get()`'s removal-based dequeue, so no gap there. No 413-shrink-and-retry (optional per spec), consistent with the Event Batcher finding (n14).
- **Backwards compatibility:** Needs deprecation path — converting to a true requeue-for-next-flush model changes `on_error` callback timing and consumer-thread blocking semantics (currently blocks synchronously through up to ~10 attempts × capped 30s backoff), an observable behavior change for existing integrations that time or depend on current `on_error`/blocking timing.
- **Remediation:** If pursued, introduce a requeue-on-exhaustion path as an opt-in mode (e.g. a new constructor flag) rather than changing the default synchronous-retry-then-drop behavior, to avoid silently changing blocking/timing semantics for existing integrations.
