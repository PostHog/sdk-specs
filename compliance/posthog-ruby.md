Note on repo layout: `posthog-ruby` is a monorepo containing the core gem plus a Rails
integration gem. Core SDK logic lives at `lib/posthog/`: `client.rb` — the main public API
surface (`capture`, `identify`, `group_identify`, `alias`, `capture_exception`, the deprecated
single-flag getters, `evaluate_flags`/`FeatureFlagEvaluations`, `flush`, `shutdown`);
`feature_flags.rb` — `FeatureFlagsPoller`, the local-evaluation engine, ETag-based definition
polling, and flag/cohort/semver matching; `feature_flag_evaluations.rb` — the snapshot class;
`feature_flag_result.rb` — the structured single-flag result and the shared `parse_payload`
helper; `flag_definition_cache.rb` — the `FlagDefinitionCacheProvider` interface for distributed
definition caching; `field_parser.rb` — wire-format event hashes; `message_batch.rb`/
`send_worker.rb`/`noop_worker.rb` — batching and the background worker; `transport.rb`/
`backoff_policy.rb` — HTTP transport and retry/backoff; `exception_capture.rb` — `$exception_list`
and stacktrace building; `internal/context.rb` — per-thread request context.

**New since the last audit:** a substantial `lib/posthog/mcp/` subtree (~4,000 lines: MCP server
instrumentation, sanitization, truncation, session/identity tracking, a Rack middleware). It is a
product integration layered on top of the client, not an implementation of any cross-SDK contract
in `openspec/specs/`, so it is out of scope for every row below and is excluded from the greps
cited in the notes.

**Re-audit note (this run):** This is a re-audit. The SDK was last audited 2026-08-06 at
`31c187f` against sdk-specs `6369cae`; the repo has since advanced to `185060a`, but outside the
new `mcp/` subtree the core changed very little — a `headers` transport option, `send_batch`
accepting any 2xx rather than exactly 200, a nil-body guard in `Transport`, and two rubocop
comment renames. Selection this run was driven by rule 1 (affected by spec changes): the
sdk-specs delta is dominated by server-side flag semantics — `local-feature-flag-evaluator`
(+929 lines), `evaluate-flags` (+209), the three `get-feature-flag-*` payload contracts, and
`flag-definition-loader` (+73) — plus a `flush`/`shutdown` amendment (PR #35) written specifically
around this SDK's signature. Four contracts were audited here for the first time (Capture AI,
Evaluate Flags, Exception Event Metadata, Session Replay Debug Properties), taking the matrix
from 59 to 63 rows. **One row improved on a code change:** Before Send Hook now drops the event
when a hook raises, which is what the amended spec requires (the previous audit recorded the
older fall-back-to-original behavior). **Four rows were downgraded on new spec requirements**
rather than regressions — the three payload contracts and Local Feature Flag Evaluator — and
three of those four trace to a single helper, `FeatureFlagResult.parse_payload`, returning the
raw string when `JSON.parse` fails.

## Notes

### n1 — Alias (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side flow: "Validate inputs. Both the existing id and the alias target id must be present." The `@both`-tagged acceptance scenario "Alias is dropped when required identities are missing" expects: no event enqueued, and "the SDK should record a validation warning" — i.e. drop + warn, not raise. (The spec's own Error-handling section does note "some [server SDKs] raise validation errors (for example Ruby and Go validators)" as an acknowledged variation, but the concrete acceptance scenario's THEN clause still specifies drop-and-warn semantics, not an uncaught exception propagating to caller code.)
- **SDK currently:** `Client#alias` (`lib/posthog/client.rb:447-453`) delegates to `FieldParser.parse_for_alias` (`lib/posthog/field_parser.rb:105-124`), which calls `check_presence!(alias_field, 'alias')` (`field_parser.rb:111`) and, via `parse_common_fields`, `check_presence!(distinct_id, 'distinct_id')`. `check_presence!` (`field_parser.rb:182-186`) unconditionally `raise ArgumentError` on nil/empty. This is confirmed as intentional, tested behavior: `spec/posthog/client_spec.rb:1522` (`expect { client.alias distinct_id: 1234 }.to raise_error(ArgumentError)`) and `:1526` (missing `alias`) both hard-assert the raise. A raised `ArgumentError` propagating to caller code in a Rails controller/Sidekiq job is a crash, not the spec's "drop silently + log a validation warning."
- **Backwards compatibility:** Breaking — the SDK's own test suite hard-asserts the raise; flipping to drop+warn changes an observable, documented, tested behavior for any caller currently relying on (or incidentally catching) the exception.
- **Remediation:** Change `check_presence!`-driven validation failures in `alias` (and the shared `parse_common_fields` distinct_id check) to log a warning and return a sentinel (no event enqueued) instead of raising, ideally behind a deprecation window (warn-then-raise for one minor, then drop-silently by default) given the existing tested contract.


### n2 — Before Send Hook (🟡 Partial)
- **Spec requires:** `both` applicability, acceptance `@both`. A `beforeSend(event) -> event | null` hook run before enqueue; mutate or drop (`null`/`nil` return); spec notes some SDKs support hook chaining via an array of hooks, run in order, stopping the chain on a drop. **Changed this cycle** (PR [#43](https://github.com/PostHog/sdk-specs/pull/43), a breaking spec change): "If any before-send hook throws, the SDK SHALL catch the exception, record a warning, stop the remaining hook chain, and **drop the event**. The SDK MUST NOT enqueue the original event or the last successfully transformed value."
- **SDK currently:** `@before_send = opts[:before_send]` (`lib/posthog/client.rb:225`), invoked from `process_before_send` (`client.rb:1122-1141`), called from `enqueue` (`client.rb:1150`). Correctly mutates/drops on `nil` return (`client.rb:1129-1133`) and, on a raised exception inside the hook, catches it, logs `"Error in beforeSend function - dropping event"`, and returns `nil` so `enqueue` drops the event (`lib/posthog/client.rb:1136-1139`, with `return false if action.nil? || action.empty?` at `client.rb:1152`) — **this satisfies the new drop-on-throw requirement**, and is a change since the previous audit, which recorded the older fall-back-to-original behavior. All 3 published acceptance scenarios pass. Gap: `@before_send` is treated as a single callable only — `process_before_send` calls `@before_send.call(action)` directly with no branch for an `Array` of hooks; passing an array of procs would raise `NoMethodError` (`Array#call`), which is caught by the same `rescue StandardError` and silently masked as a fallback to the original event rather than the spec's intended sequential chain-with-early-stop-on-drop semantics.
- **Backwards compatibility:** Backward-compatible — branching on `@before_send.is_a?(Array)` in `process_before_send` and reducing over the hooks (stopping on a `nil`/drop) is purely additive; existing single-callable configuration is unaffected.
- **Remediation:** Add array-of-hooks support to `process_before_send`: iterate in order, feed each hook's output into the next, stop and drop on any hook returning `nil`.


### n3 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Error handling: "**Drop silently** on: disabled SDK, opted-out user, empty/invalid event name, invalid distinct id (server)... **Never throw** to the caller under normal operation. Capture is latency-sensitive and lives on the hot path of application code; SDKs are expected to absorb all I/O and serialization errors internally." Also implies a dynamic opt-out mechanism the `@both`-tagged capture acceptance scenarios can exercise.
- **SDK currently:** Two distinct gaps. (1) `Client#capture` (`client.rb:291-371`) delegates to `FieldParser.parse_for_capture` (`field_parser.rb:24-47`), which calls `check_presence!(event, 'event')` (`field_parser.rb:30`) — `client.capture(distinct_id: 'user')` (no `event`) raises `ArgumentError`, confirmed by the SDK's own test at `spec/posthog/client_spec.rb:325-329` (`expect { client.capture(distinct_id: 'user') }.to raise_error(ArgumentError)`), directly contradicting the spec's "drop silently on empty/invalid event name... never throw." (2) There is no dynamic, runtime-toggleable opt-out API anywhere: `grep` for `opt_out`/`opt_in`/`is_opted_out` across `lib/posthog/*.rb` returns zero matches. The only short-circuit is the constructor-time `@disabled` flag (`client.rb:142`, checked at `client.rb:292`), a static kill-switch set once when the API key is missing/blank — not a dynamic per-call opt-out toggle a caller can flip at runtime.
- **Backwards compatibility:** Breaking for (1) — the SDK's own test suite hard-asserts the raise, so silencing it changes tested behavior; should ship as a deprecation-then-change. Backward-compatible for (2) — adding new `opt_out_capturing()`/`opt_in_capturing()`/`is_opted_out?()` methods is purely additive.
- **Remediation:** Change the missing/empty `event` validation path to log-and-drop (return `false`) instead of raising, on a deprecation timeline given existing test coverage. Separately, add a dynamic opt-out API distinct from the static `@disabled` kill switch.
- **Two new `capture` requirements this cycle:** (1) "Capture drops null-valued object properties" (`openspec/specs/capture/spec.md:230`) requires recursively omitting object members whose value is an explicit null before wire and disk serialization, while leaving null *array elements* at their indices. Ruby does no such cleanup — `grep -rn 'compact' lib/posthog/field_parser.rb lib/posthog/message_batch.rb lib/posthog/client.rb` returns nothing, and `FieldParser` (`lib/posthog/field_parser.rb:130-160`) hands the properties hash straight through to `MessageBatch`/`JSON.generate`, so `{ test: nil }` goes out as `{"test":null}`. (2) UTC timestamp normalization is **satisfied** — `FieldParser` stamps `timestamp: time_in_iso8601(timestamp.getutc)` (`lib/posthog/field_parser.rb:153`), coercing any caller-supplied zone to UTC. One narrow deviation inside that second requirement: the spec asks for sub-second precision to be preserved "when the input carries it", but `Utils.time_in_iso8601` hardcodes `fraction_digits = 3` (`lib/posthog/utils.rb:74`), so a microsecond-precision `Time` is truncated to milliseconds.
- **Backwards compatibility (null-property drop):** Backward-compatible — a serializer-side recursive filter only removes members that are already semantically absent, and the public API keeps accepting nils.
- **Remediation (null-property drop):** Add a recursive `strip_null_object_members` in `FieldParser`, applied after `before_send`, that deletes nil-valued hash members (descending into nested hashes and into hashes nested inside arrays) while leaving array elements positionally intact; separately, let `time_in_iso8601` pass through the input's own sub-second precision.

### n5 — Evaluate Flags (🟡 Partial)
- **Spec requires:** `openspec/specs/evaluate-flags/spec.md`. Under "Evaluation identity, inputs, and data sources" (spec line 46) a server SDK with a local-definition refresh lifecycle SHALL retain finite-capacity negative knowledge for a requested key absent from both the loaded definitions and a clean remote fallback, clear it after every successful definitions refresh, and coordinate concurrent evaluations onto one in-flight existence probe for the same unknown key. Under "Snapshot payload access" (spec line 226) a malformed serialized payload SHALL be logged and returned as the no-payload sentinel, "never the malformed raw string".
- **SDK currently:** the snapshot API itself is in good shape. `Client#evaluate_flags` (`lib/posthog/client.rb:643-773`) distinguishes a nil `flag_keys` from an explicitly empty one (`return FeatureFlagEvaluations.new(...flags: {}...) if flag_keys && flag_keys.empty?`, `client.rb:660-664`), skips the `/flags` round trip when every requested key resolved locally (`all_requested_flags_resolved_locally`, `client.rb:722`), makes at most one remote request, and never lets a remote record overwrite a local one (`next if locally_evaluated_keys.include?(key_str)`, `client.rb:741`). `FeatureFlagEvaluations` (`lib/posthog/feature_flag_evaluations.rb`) implements lazy access tracking in `_record_access`, silent `get_flag_payload`, and no-I/O `only`/`only_accessed` filters. Two gaps: (1) **no negative-knowledge retention or probe coordination exists** — `grep -rn 'omission\|negative_knowledge\|missing_key' lib/` returns nothing, so a requested-but-deleted key re-probes `/flags` on every single call forever, with no definitions-generation bookkeeping and no coalescing of concurrent probes. (2) the snapshot's payloads are built by `FeatureFlagResult.parse_payload` (`client.rb:696` local, `client.rb:750` remote), which **returns the raw serialized string** when `JSON.parse` raises (`lib/posthog/feature_flag_result.rb:74-78`) — the exact outcome the spec forbids; see [n10], which tracks the same defect from the payload-getter contract's angle.
- **Backwards compatibility:** Backward-compatible for the negative-knowledge work (new private state, no signature change). **Needs deprecation path** for the payload fix: callers who today receive a raw malformed string and rescue on it would start receiving `nil`, so the change should ship with a release note even though the current behavior is the defect.
- **Remediation:** Add a bounded per-poller missing-key set stamped with the flag-definition generation, consulted before deciding to call `get_flags`, cleared on every successful `load_feature_flags` (including the not-modified and shared-cache-hydration paths), and never populated from a quota-limited or `errorsWhileComputingFlags` response. Separately, fix `FeatureFlagResult.parse_payload` to log through the SDK logger and return `nil` on `JSON::ParserError` instead of the raw string (see [n10]).

### n6 — Exception Event Metadata (❌ Fail)
- **Spec requires:** `openspec/specs/exception-event-metadata/spec.md`. Nested entries SHALL carry `mechanism.type = "chained"`, `mechanism.source`, `parent_id`, and a unique `exception_id`; each nested entry SHALL preserve *its own* independently known handled state and the producer "MUST NOT copy, invert, or otherwise derive the value solely from the outermost entry" — when unknown it SHALL omit `mechanism.handled`. `mechanism.synthetic` SHALL be set per-entry when provenance is known. `$exception_level` SHALL be derived from the boundary default table and serialized as one of `fatal`/`error`/`warning`/`log`/`info`/`debug`. `$exception_source` SHALL name the concrete integration (`rails.middleware`, `rails.error_reporter`, `rails.active_job` for this platform). And: "Application property bags MUST NOT override SDK-owned `$exception_list`, `$exception_level`, `$exception_source`, `$debug_images`, or processor-owned properties."
- **SDK currently:** Ruby is the furthest along of the server SDKs audited this cycle on the linkage half of this contract, and fails the ownership and per-entry halves. Implemented correctly: `ExceptionCapture.chain_mechanism` (`lib/posthog/exception_capture.rb:60-69`) assigns a sequential `exception_id` to every entry and sets `'type' => 'chained'`, `'source' => 'cause'`, and `'parent_id' => exception_id - 1` on every non-outermost entry; `build_exception_list` (`exception_capture.rb:38-55`) walks `cause` outermost-first, caps the chain at `MAX_CHAINED_EXCEPTIONS = 50` (`exception_capture.rb:26`), and guards against cause cycles with an identity-compared `seen` set. Four defects: (1) `chain_mechanism` starts from `root_mechanism.merge(...)`, so every nested entry **inherits the outermost's `handled`** — with the module default `DEFAULT_MECHANISM = { 'type' => 'generic', 'handled' => true }` (`exception_capture.rb:28`) a cause is always stamped `handled: true`, and an integration passing `mechanism: { 'handled' => false }` stamps every cause `handled: false`; the spec requires omission in both cases. (2) `mechanism.synthetic` is never emitted anywhere — `grep -rn 'synthetic' lib/` returns nothing — including for the string-input path (`coerce_exception_input`, `exception_capture.rb:230`), which converts a non-exception into an exception representation and is exactly the case the spec's table marks `synthetic: true`. (3) `$exception_level` is never emitted — `grep -rn 'exception_level' lib/` returns nothing — so no capture boundary carries the `error`/`fatal` default the spec's table mandates. (4) `Client#capture_exception` (`lib/posthog/client.rb:410-429`) builds `properties = { '$exception_list' => exception_list }` and then runs `properties.merge!(additional_properties)` (`client.rb:418`), so a caller passing `additional_properties` containing `'$exception_list'` (or `'$exception_level'`, or `'$exception_source'`) silently overwrites the SDK-owned value — the precedence rule is inverted relative to the spec's MUST NOT. `$exception_source` itself is never set by the core gem on any path.

It is merged into the exception properties at the single capture boundary (`lib/posthog/client.rb:451`). Re-checked at `c08fd1b`, defects (1)–(4) above all still hold: `grep -rn 'synthetic\|exception_level' lib/` still returns nothing, `chain_mechanism` still merges `root_mechanism` into nested entries (`lib/posthog/exception_capture.rb:60-69`), and `capture_exception` still merges `additional_properties` last. The row stays ❌.
- **Backwards compatibility:** Backward-compatible for (1), (2), and (3) — omitting a nested `handled` that was never independently known, and adding `synthetic`/`$exception_level`, only make the envelope more accurate; no public signature changes. **Breaking for (4)** in the strict sense: callers currently relying on `additional_properties` to hand-override `$exception_list` would stop being able to, but the spec classifies that override as something an SDK must not permit, so it should ship with the next major and be called out in the release notes.

(2) Set `synthetic` on the entries the SDK actually knows about — `true` for `coerce_exception_input`'s string/non-exception path, `false` for a real `Exception` whose backtrace is used as-is. (3) Add `$exception_level` with the boundary default `error` for `capture_exception` and `fatal` for terminating boundaries, normalizing any integration-supplied severity through the spec's alias table. (4) Merge `additional_properties` **first** and let the SDK-owned `$exception_list`/`$exception_level`/`$exception_source` keys win, dropping any caller-supplied reserved key with a logged warning.

### n8 — Flush (🟡 Partial)
- **Spec requires:** `@both`. No-op on empty queue with no network call (matches); bypass `flush_at`/`flush_interval` and attempt delivery now (matches); acceptance scenario "Flush keeps events retryable when delivery fails": on a 503 (or other retryable failure), the call must not throw, and the failed event "should remain queued for retry."
- **SDK currently:** `Client#flush` (`client.rb:226-249`) correctly no-ops on an empty queue and bypasses batching intervals via `@worker.request_flush`. However, `SendWorker#run` (`send_worker.rb:58-77`) calls `send_batch` then unconditionally clears the in-flight batch in an `ensure` block (`send_worker.rb:69-73`: `begin send_batch ... ensure @lock.synchronize { @batch.clear } ... end`), regardless of whether `send_batch` succeeded. `Transport#send` (`transport.rb:68-94`) exhausts its own bounded retry budget (`@retries`, default from `Defaults::Request::RETRIES`) internally and returns a `Response` object on both success and terminal failure — it does not raise for a normal terminal failure, so `flush()` itself never throws (satisfying that half of the scenario). But once `Transport#send`'s internal retries are exhausted, the batch is gone: it is never re-added to `@queue`, so the failed event is **not** preserved for a later retry cycle, directly contradicting "the event named Save should remain queued for retry."
- **Backwards compatibility:** Breaking — re-enqueueing failed batches changes delivery/ordering semantics (potential duplicate-send on subsequent retry, unbounded-queue-growth risk during a sustained outage) that the current design doesn't guard against; should ship as an explicit opt-in mode rather than a silent default-behavior change.
- **Remediation:** On terminal (post-retry-budget) failure in `send_batch`, re-enqueue the batch's messages back onto `@queue` (respecting `max_queue_size`) instead of discarding them in the `ensure` block, ideally gated behind an opt-in flag to avoid surprising existing integrations that depend on today's drop-on-exhaustion behavior.

### n10 — Get Feature Flag Payload (❌ Fail, downgraded from ✅)
- **Spec requires:** `openspec/specs/get-feature-flag-payload/spec.md:161`, "Malformed serialized payloads return no payload" (new this cycle): "When a feature flag payload is represented as serialized JSON, the SDK SHALL decode it before exposing it as a payload value. If decoding fails, including for empty or whitespace-only serialized input, the SDK SHALL return the same sentinel used for a known flag with no payload ... and MUST NOT return the raw string or throw to the caller. Parse failures SHALL be logged through SDK diagnostics." The requirement explicitly supersedes the older "missing/unparsed payloads" wording that this row was previously scored ✅ against, and it also covers accessors that return serialized strings: "Serialized payloads SHALL be validated as JSON before public payload access, including accessors that return serialized strings without a typed decoding helper."
- **SDK currently:** two separate paths, both non-conforming. (a) The public `Client#get_feature_flag_payload` (`lib/posthog/client.rb:817-839`) delegates to `FeatureFlagsPoller#get_feature_flag_payload` (`lib/posthog/feature_flags.rb:442-472`), whose local branch returns `_compute_flag_payload_locally(...)` (`feature_flags.rb:1096-1107`) — a bare `snapshot[:flags_by_key].dig(key, :filters, :payloads, ...)` lookup with **no JSON decode and no validation at all**. A malformed payload is therefore handed to the caller verbatim as its raw serialized string, which is exactly the outcome the requirement names as impermissible; a whitespace-only payload likewise comes back as `"   "`. (b) The decoding helper that *is* used by the result-shaped and snapshot APIs, `FeatureFlagResult.parse_payload` (`lib/posthog/feature_flag_result.rb:69-79`), does attempt `JSON.parse` but its rescue clause returns the input unchanged: `rescue JSON::ParserError; payload; end` (`feature_flag_result.rb:76-78`) — again the raw string. Empty string is the one case handled correctly (`return nil if payload.empty?`, `feature_flag_result.rb:72`). Nothing is logged on either path. This single helper is the root cause shared with [n5], [n11], and [n12].
- **Backwards compatibility:** Needs deprecation path — integrations that today receive the raw string for a malformed payload (or rely on the undecoded local-path string) would begin receiving `nil`. That is the spec's required behavior and the current behavior is the defect, but it is an observable return-value change on a public (albeit already-deprecated) getter, so it should ship with the deprecation of `get_feature_flag_payload` rather than as a silent patch.
- **Remediation:** Change `FeatureFlagResult.parse_payload`'s rescue to log through the SDK logger and return `nil`, and treat a whitespace-only string as malformed rather than passing it through. Route `FeatureFlagsPoller#get_feature_flag_payload`'s local branch (and `get_feature_payloads`' remote branch) through the same helper so the deprecated getter and the snapshot accessor agree, as "Bulk payload decoding agrees with single-flag APIs" requires.

- **Remediation:** Add `set_person_properties_for_flags()`/`set_group_properties_for_flags()`/`reset_person_properties_for_flags()`/`reset_group_properties_for_flags()` on `Client`, backed by a context-scoped override store consulted by the flag-evaluation call sites as a default, mergeable with (and overridable by) explicit per-call `person_properties:`/`group_properties:`. Also worth flagging upstream to sdk-specs maintainers: the spec-prose `Applicability: client` and the acceptance files' `@both` tags are inconsistent and should be reconciled.


### n18 — Retry Queue (🟡 Partial)
- **Spec requires:** `both`. In-memory queue with backpressure/drop-when-full and a capacity warning; flush on size/timer/explicit trigger; classify retryable (network errors, 5xx, 408, 429) vs. non-retryable (other 4xx) failures; retryable failures keep the same events queued for a later, separate flush attempt; success removal by stable identity, not index, so events captured concurrently while a batch is in flight are not mistaken for the just-sent batch and dropped.
- **SDK currently:** In-memory `Queue.new` per client (`client.rb:139`), bounded by `@max_queue_size` (default `Defaults::Queue::MAX_SIZE`); full-queue enqueue attempts are dropped with a logged warning (`client.rb:1120-1140`, `enqueue`) — matches the capacity-warning requirement. `Transport#should_retry_request?` (`transport.rb:107-116`) correctly classifies 5xx/408/429 as retryable and other 4xx as terminal (logged, not retried). Concurrent-capture-during-flush safety is naturally satisfied by Ruby's `Queue#pop`, which removes by dequeue rather than by index, so events enqueued mid-flush cannot be confused with the in-flight batch. Gap: once a batch is dequeued via `SendWorker#build_batch`/`consume_message_from_queue!` (`send_worker.rb:138-166`) and handed to `Transport#send`, `Transport#send` performs its own bounded in-request retry loop (`retry_with_backoff`, `transport.rb:125-144`, honoring `Retry-After` via `parse_retry_after`, `transport.rb:154-165`) but once that retry budget (`@retries`) is exhausted, the batch is not returned to `@queue` for a later, independent flush cycle — `SendWorker#run`'s `ensure @batch.clear` (`send_worker.rb:69-73`) discards it unconditionally, matching the same drop-on-exhaustion behavior noted under Flush (n8). This is the identical underlying root cause as n8, viewed from the retry-queue contract's angle.
- **Backwards compatibility:** Needs deprecation path — converting to a true requeue-on-exhaustion model changes `on_error` callback timing/frequency and worker-loop blocking semantics, an observable change for integrations that depend on today's timing.
- **Remediation:** Same fix as n8: re-enqueue the batch (respecting `max_queue_size`) on terminal transport failure instead of discarding it in `SendWorker#run`'s `ensure` block, behind an opt-in flag given the existing behavior is relied upon today.

### n20 — Tracing Headers (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side responsibilities: request-scoped middleware extracting `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` case-insensitively into context; sanitize (trim/strip control chars/cap length); explicit call-site values take precedence over context; personless-capture fallback (random `distinct_id` + `$process_person_profile=false`) when no identity is resolvable anywhere; **"Require identity for feature-flag evaluation. If server-side feature-flag evaluation... is called with no explicit distinct id and request context also has no distinct id, the SDK MUST return an empty/no-op evaluation result and MUST NOT make a feature-flag request or emit `$feature_flag_called` events."**; per-request isolation; headers never used for auth.
- **SDK currently:** `Internal::Context` (`internal/context.rb`) implements genuine per-request/fiber-local state via `ActiveSupport::IsolatedExecutionState` (when Rails is present) or `Thread.current` otherwise (`internal/context.rb:25-31`), satisfying request isolation. `posthog-rails`'s `TracingHeaders` module (`posthog-rails/lib/posthog/rails/tracing_headers.rb`) correctly extracts `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` case-insensitively (`header_candidates`, `tracing_headers.rb:51-55`, checking canonical/downcased/Rack-`HTTP_`-prefixed forms) and sanitizes (trim/strip control chars/cap at 1000 chars, `sanitize_header_value`, `tracing_headers.rb:16-23`). `Client#capture`'s `enrich_capture_attrs_with_context` (`client.rb:943-964`) correctly implements explicit-value precedence over context and the personless fallback (random UUID + `$process_person_profile: false`, `client.rb:958-963`) when no distinct_id is resolvable anywhere — this matches spec precisely for `capture`. **Gap:** none of the flag-evaluation methods consult `Internal::Context` at all — `is_feature_enabled`, `get_feature_flag`, `get_feature_flag_result`, `get_all_flags`, `get_feature_flag_payload`, and `get_all_flags_and_payloads` all take `distinct_id` as a required positional argument (e.g. `client.rb:476`, `client.rb:536`) with no context-fallback and no nil/blank-distinct_id no-op guard — calling one of these with `nil`/`''` either raises (via downstream `to_s`/hashing) or, worse, proceeds to make a real `/flags` HTTP request and can emit `$feature_flag_called`, contradicting the spec's `MUST NOT make a feature-flag request or emit $feature_flag_called events` requirement. Only the newer canonical `evaluate_flags` (`client.rb:614-740`) has any guard at all — a nil/empty `distinct_id` short-circuits to an empty snapshot (`client.rb:625-627`) — but even `evaluate_flags` does not fall back to `Internal::Context`'s ambient distinct_id when the explicit argument is absent; it only no-ops rather than resolving context first. Only Rails has this middleware; there is no Sinatra/Grape/plain-Rack-specific middleware, though `Internal::Context` and `TracingHeaders` are framework-agnostic enough to be wired up manually.
- **2026-11-09 re-verification — the span-context bridge added this cycle is implemented; the flag-evaluation gap above is unchanged.** [#129](https://github.com/PostHog/sdk-specs/pull/129) added five requirements for enriching application spans with analytics context. `PostHog::Internal::SpanContext` plus `PostHog::OTel::ContextSpanProcessor` (`lib/posthog/internal/span_context.rb`, `lib/posthog/otel/context_span_processor.rb`) satisfy them: enrichment happens at span start so a child span snapshots the IDs and keeps them after the request scope ends and after another request sets different ones; only `posthogDistinctId` and `sessionId` are written; a span that is not recording is skipped, so enrichment never creates a recording or changes a sampling decision; a key the span already carries is left alone, so explicit span attributes win; `nil`/empty IDs are skipped rather than generated; string values are duplicated and frozen before being attached, which is what keeps a captured value stable; and the whole body is wrapped in `rescue StandardError; nil` so a failed lookup leaves the request untouched. `apply_current` guards on `defined?(::OpenTelemetry::Trace)`, keeping the tracing dependency optional. Request isolation comes from the existing fiber-local `Internal::Context`. Re-checked at `c08fd1b`, the flag-evaluation identity gap recorded above is unchanged.
- **Backwards compatibility:** Backward-compatible — making `distinct_id` fall back to `Internal::Context.current&.distinct_id` when omitted/nil (with a no-op/empty-result guard when neither is present) on the legacy flag APIs, and adding the same context-fallback to `evaluate_flags`, are both purely additive; existing explicit-`distinct_id` call sites are unaffected.
- **Remediation:** Add `Internal::Context` fallback resolution to all flag-evaluation methods (`is_feature_enabled`, `get_feature_flag`, `get_feature_flag_result`, `get_all_flags`, `get_feature_flag_payload`, `get_all_flags_and_payloads`, `evaluate_flags`) so that when no explicit `distinct_id` is passed, the ambient request-context id is used if present; when neither is present, no-op (empty/nil result, no HTTP request, no `$feature_flag_called`) rather than raising or proceeding with a blank identity.

### n21 — MCP Analytics (🟡 Partial)

- **Spec requires:** `openspec/specs/mcp-analytics/spec.md`, `server` scope, an add-on package rather than a core client method. One-call observer-only instrumentation whose failures never reach the handler or the client; exactly one `$mcp_tool_call` per final outcome carrying the required `$mcp_tool_name`, `$mcp_is_error`, `$mcp_duration_ms`, `$mcp_source`, **`$mcp_interface`** and `$session_id`; failure capture with a low-cardinality `$mcp_error_type` and a sanitized `$mcp_error_message`; the cross-SDK-deterministic `$session_id` derivation; **client conversation ids read from a tool call's `_meta`** for ChatGPT (`openai/session`), OpenAI Codex (`sessionId`) and VS Code (`vscode.conversationId`), each gated on that row's client-recognition rule and each winning over a conversation handle ([#175](https://github.com/PostHog/sdk-specs/pull/175), [#176](https://github.com/PostHog/sdk-specs/pull/176)); bounded per-session state; and tool arguments, results and error text relayed **after the credential passes only**, with no pattern-based personal-data pass ([#194](https://github.com/PostHog/sdk-specs/pull/194), which reverted the payload half of [#190](https://github.com/PostHog/sdk-specs/pull/190)).

The 2026-09-28 audit treated the subtree as out of scope on the strength of that table. - **SDK currently:** Substantial and broadly on-contract. The package emits `$mcp_tool_call`, `$mcp_unknown_tool`, `$mcp_initialize`, `$mcp_tools_list`, `$mcp_prompts_list`, `$mcp_prompt_get`, `$mcp_resources_list`, `$mcp_resource_read` and `$mcp_missing_capability`, and carries `$mcp_source`, `$mcp_is_error`, `$mcp_duration_ms`, `$mcp_tool_name`, `$mcp_resource_name`, `$mcp_tool_description`, `$mcp_tool_category`, `$mcp_error_type`, `$mcp_error_message`, `$mcp_intent`, `$mcp_intent_source`, `$mcp_llm_model`, `$mcp_llm_model_source`, `$mcp_conversation_id`, `$mcp_listed_tool_names`, `$mcp_parameters`, `$mcp_response`, and the full client/server identity set (`$mcp_client_name`, `$mcp_client_version`, `$mcp_client_user_agent`, `$mcp_protocol_version`, `$mcp_server_name`, `$mcp_server_version`, `$mcp_vendor_client`). It has a before-send hook (`lib/posthog/mcp/options.rb`, `sink.rb`), a feedback surface (`analytics.rb`, `tools.rb`), session derivation and a PostHog session token (`session.rb`, `session_token.rb`), and dedicated sanitization and truncation modules. **Three gaps found.** (1) **`$mcp_interface` is never emitted** — it is `required` on every event in the property reference, and `grep -rn 'mcp_interface' lib/posthog/mcp/` returns zero matches, so every Ruby MCP event is missing a required property that distinguishes an MCP server from the reserved `webmcp` value. (3) **`$mcp_input_required`, `$mcp_error_status`, `$mcp_input_keys`, `$mcp_input_aliases_used` and `$mcp_server_build` are absent.** The first is a `SHOULD`, the rest are `MAY`s, so only `$mcp_input_required` counts against the row. - **Backwards compatibility:** Backward-compatible for all three. `$mcp_interface` is a new property on events the package already builds. Reading client conversation ids adds a rung above the existing handle resolution; it changes which `$session_id` some calls get, but only for clients that send an id today and are being grouped worse without it, and it adds nothing the MCP client can see. `$mcp_input_required` is a new optional event.
- **Remediation:** (1) Add `$mcp_interface` with the value `"mcp"` to the shared property set in `lib/posthog/mcp/event_builder.rb`/`constants.rb` so it lands on every event including the `$exception` side-car. (2) Implement the "Session identity" client table in `lib/posthog/mcp/conversation_id.rb`: recognize the three clients by `User-Agent` (or client name, case-insensitively, in table order), read only that row's `_meta` key, derive `$session_id` from `"<key>:<value>"` with the existing FNV-1a derivation, never send the raw value, suppress `$mcp_conversation_id` on a call that carries one, and treat ChatGPT as handle-free. (3) Emit `$mcp_input_required` with `$mcp_input_request_methods` for an `input_required` round, which is also what keeps the retry's `$mcp_tool_call` duration honest.
