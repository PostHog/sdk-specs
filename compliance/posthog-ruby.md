Note on repo layout: `posthog-ruby` is a monorepo containing the core gem plus a Rails
integration gem. Core SDK logic lives at `lib/posthog/`: `client.rb` — the main public API
surface (`Client` class: `capture`, `identify`, `group_identify`, `alias`, `capture_exception`,
`is_feature_enabled`/`get_feature_flag`/`get_feature_flag_result` (deprecated single-flag path),
`evaluate_flags`/`FeatureFlagEvaluations` (canonical snapshot path), `flush`, `shutdown`);
`feature_flags.rb` — `FeatureFlagsPoller`, the local-evaluation engine, ETag-based definition
polling, and flag/cohort/semver matching; `feature_flag_evaluations.rb` — the `FeatureFlagEvaluations`
snapshot class (`enabled?`/`get_flag`/`get_flag_payload`/`only`/`only_accessed`);
`flag_definition_cache.rb` — the `FlagDefinitionCacheProvider` interface for distributed flag-
definition caching (e.g. Redis); `field_parser.rb` — builds wire-format event hashes for
capture/identify/group_identify/alias; `message_batch.rb`/`send_worker.rb`/`noop_worker.rb` —
batching/background worker; `transport.rb`/`backoff_policy.rb` — HTTP transport and retry/backoff;
`exception_capture.rb` — exception-list/stacktrace building; `internal/context.rb` — per-
request/fiber-local context (distinct_id/session_id/properties), used internally by the Rails
integration. A separate `posthog-rails/` gem (`posthog-rails/lib/posthog/rails/`) adds Rails-
specific integrations: `tracing_headers.rb`/`request_context.rb` (middleware extracting
`X-POSTHOG-*` headers), `capture_exceptions.rb`/`error_subscriber.rb`/`rescued_exception_interceptor.rb`
(automatic exception capture), `active_job.rb`, and `logs/` (opt-in OTLP log forwarding — a
capability the core `posthog-ruby` gem does not have on its own). This is a server-side SDK: no
persistent process/UI, stateless per call, used from Rails/Sidekiq/plain Ruby apps. All file
paths below are relative to `/tmp/audit-posthog-ruby/` unless noted.

## Notes

### n1 — Alias (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side flow: "Validate inputs. Both the existing id and the alias target id must be present." The `@both`-tagged acceptance scenario "Alias is dropped when required identities are missing" expects: no event enqueued, and "the SDK should record a validation warning" — i.e. drop + warn, not raise. (The spec's own Error-handling section does note "some [server SDKs] raise validation errors (for example Ruby and Go validators)" as an acknowledged variation, but the concrete acceptance scenario's THEN clause still specifies drop-and-warn semantics, not an uncaught exception propagating to caller code.)
- **SDK currently:** `Client#alias` (`lib/posthog/client.rb:447-453`) delegates to `FieldParser.parse_for_alias` (`lib/posthog/field_parser.rb:105-124`), which calls `check_presence!(alias_field, 'alias')` (`field_parser.rb:111`) and, via `parse_common_fields`, `check_presence!(distinct_id, 'distinct_id')`. `check_presence!` (`field_parser.rb:182-186`) unconditionally `raise ArgumentError` on nil/empty. This is confirmed as intentional, tested behavior: `spec/posthog/client_spec.rb:1522` (`expect { client.alias distinct_id: 1234 }.to raise_error(ArgumentError)`) and `:1526` (missing `alias`) both hard-assert the raise. A raised `ArgumentError` propagating to caller code in a Rails controller/Sidekiq job is a crash, not the spec's "drop silently + log a validation warning."
- **Backwards compatibility:** Breaking — the SDK's own test suite hard-asserts the raise; flipping to drop+warn changes an observable, documented, tested behavior for any caller currently relying on (or incidentally catching) the exception.
- **Remediation:** Change `check_presence!`-driven validation failures in `alias` (and the shared `parse_common_fields` distinct_id check) to log a warning and return a sentinel (no event enqueued) instead of raising, ideally behind a deprecation window (warn-then-raise for one minor, then drop-silently by default) given the existing tested contract.

### n2 — Before Send Hook (🟡 Partial)
- **Spec requires:** `both` applicability, acceptance `@both`. A `beforeSend(event) -> event | null` hook run before enqueue; mutate or drop (`null`/`nil` return); on hook exception, must not crash the caller; spec notes some SDKs support hook chaining via an array of hooks, run in order, stopping the chain on a drop.
- **SDK currently:** `@before_send = opts[:before_send]` (`lib/posthog/client.rb:210`), invoked from `process_before_send` (`client.rb:1086-1104`), called from `enqueue` (`client.rb:1112`). Correctly mutates/drops on `nil` return (`client.rb:1093-1096`) and, on a raised exception inside the hook, catches it, logs, and falls back to the original (pre-hook) event (`client.rb:1100-1103`) — satisfying "must not crash the caller." All 3 published acceptance scenarios pass. Gap: `@before_send` is treated as a single callable only — `process_before_send` calls `@before_send.call(action)` directly with no branch for an `Array` of hooks; passing an array of procs would raise `NoMethodError` (`Array#call`), which is caught by the same `rescue StandardError` and silently masked as a fallback to the original event rather than the spec's intended sequential chain-with-early-stop-on-drop semantics.
- **Backwards compatibility:** Backward-compatible — branching on `@before_send.is_a?(Array)` in `process_before_send` and reducing over the hooks (stopping on a `nil`/drop) is purely additive; existing single-callable configuration is unaffected.
- **Remediation:** Add array-of-hooks support to `process_before_send`: iterate in order, feed each hook's output into the next, stop and drop on any hook returning `nil`.

### n3 — Capture (🟡 Partial)
- **Spec requires:** `both` applicability. Error handling: "**Drop silently** on: disabled SDK, opted-out user, empty/invalid event name, invalid distinct id (server)... **Never throw** to the caller under normal operation. Capture is latency-sensitive and lives on the hot path of application code; SDKs are expected to absorb all I/O and serialization errors internally." Also implies a dynamic opt-out mechanism the `@both`-tagged capture acceptance scenarios can exercise.
- **SDK currently:** Two distinct gaps. (1) `Client#capture` (`client.rb:291-371`) delegates to `FieldParser.parse_for_capture` (`field_parser.rb:24-47`), which calls `check_presence!(event, 'event')` (`field_parser.rb:30`) — `client.capture(distinct_id: 'user')` (no `event`) raises `ArgumentError`, confirmed by the SDK's own test at `spec/posthog/client_spec.rb:325-329` (`expect { client.capture(distinct_id: 'user') }.to raise_error(ArgumentError)`), directly contradicting the spec's "drop silently on empty/invalid event name... never throw." (2) There is no dynamic, runtime-toggleable opt-out API anywhere: `grep` for `opt_out`/`opt_in`/`is_opted_out` across `lib/posthog/*.rb` returns zero matches. The only short-circuit is the constructor-time `@disabled` flag (`client.rb:142`, checked at `client.rb:292`), a static kill-switch set once when the API key is missing/blank — not a dynamic per-call opt-out toggle a caller can flip at runtime.
- **Backwards compatibility:** Breaking for (1) — the SDK's own test suite hard-asserts the raise, so silencing it changes tested behavior; should ship as a deprecation-then-change. Backward-compatible for (2) — adding new `opt_out_capturing()`/`opt_in_capturing()`/`is_opted_out?()` methods is purely additive.
- **Remediation:** Change the missing/empty `event` validation path to log-and-drop (return `false`) instead of raising, on a deprecation timeline given existing test coverage. Separately, add a dynamic opt-out API distinct from the static `@disabled` kill switch.

### n4 — Capture Exception (🟡 Partial)
- **Spec requires:** Acceptance feature `capture-exception.feature` is tagged `@both` at the file level and on every scenario (overriding the spec's own stale `Applicability: client` prose, which the spec's own text acknowledges: "the audited implementations live in client/mobile SDKs..."). Scenario "Capturing a handled exception emits an exception event" requires flat top-level `$exception_type` and `$exception_message` properties on the enqueued `$exception` event (`capture-exception.feature:12-20`: `$exception_type = TypeError`, `$exception_message = boom`).
- **SDK currently:** `Client#capture_exception` (`client.rb:386-405`) builds `properties = { '$exception_list' => exception_list }` (`client.rb:393`) via `ExceptionCapture.build_exception_list` (`exception_capture.rb:38-55`), which nests `type`/`value` only inside `$exception_list[0]` (`exception_capture.rb:87-93`, `build_single_exception_from_data`). No flat `$exception_type`/`$exception_message` top-level property is ever set — confirmed by reading the full `capture_exception` method and `ExceptionCapture` module; no such keys are constructed anywhere. This directly fails the acceptance scenario's expected properties. Other aspects are correct and well-tested: outermost-first/root-cause-last cause-chain ordering (`build_exception_list`, `exception_capture.rb:38-55`, capped at 50 via `MAX_CHAINED_EXCEPTIONS`), bottom-up-reversed stack frames (`build_stacktrace`, `exception_capture.rb:97-110`), ascending `pre_context`/`context_line`/`post_context` (`add_context_lines`, `exception_capture.rb:210-226`), and non-standard thrown values (e.g. an Integer or Symbol) correctly produce no event without throwing (`coerce_exception_input` returns `[nil, nil, nil]` for unsupported types, `exception_capture.rb:230-244`; `build_exception_list` returns `nil` on empty; `capture_exception` returns early at `client.rb:391`) — satisfying the "normalizes non-standard thrown values... should not throw" scenario.
- **Backwards compatibility:** Backward-compatible — adding `$exception_type`/`$exception_message` as flat properties sourced from `$exception_list[0].type`/`.value` is additive; no existing field is removed or renamed.
- **Remediation:** Add `properties['$exception_type']` / `properties['$exception_message']` in `capture_exception`, sourced from the first entry of the built `$exception_list`.

### n5 — Feature Flag Called Tracker (🟡 Partial)
- **Spec requires:** Dedup `$feature_flag_called` by `(flag, value, distinct_id, normalized groups)`; bounded eviction that "SHOULD evict the oldest or least-recently-used entries incrementally... SHOULD NOT clear the entire tracker, because doing so can flood analytics with duplicate `$feature_flag_called` events"; clear fully only on identity reset / shutdown. Minimal-event mode: when gated on by the server (`minimalFlagCalledEvents`/`minimal_flag_called_events`) and the flag's `has_experiment` is exactly `false`, reduce properties to an allowlist that — per the most recent sdk-specs fix (commit `b59e8b4`, "add session-attribution properties to minimal-event allowlist") — must include 10 session-attribution properties (`$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid`) in addition to the pre-existing core properties, while still excluding `$referrer`.
- **SDK currently:** `MINIMAL_FLAG_CALLED_EVENT_PROPERTIES` (`client.rb:30-48`) contains 16 core properties (`$feature_flag`, `$feature_flag_response`, `$feature_flag_has_experiment`, `$feature_flag_id`, `$feature_flag_version`, `$feature_flag_reason`, `$feature_flag_request_id`, `$feature_flag_evaluated_at`, `$feature_flag_error`, `locally_evaluated`, `$groups`, `$process_person_profile`, `$session_id`, `$is_server`, `$lib`, `$lib_version`) but is **missing all 10 of the session-attribution properties** added by sdk-specs commit `b59e8b4` — none of `$referring_domain`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gad_source`, `mc_cid`, `gclid`, `fbclid` are present (it does correctly exclude `$referrer`, but that's moot without the offsetting allowlist entries). Ruby's request-scoped `Internal::Context` mechanism (used by posthog-rails) allows arbitrary caller-supplied properties, including UTM/attribution values, to flow into captured events — these would be silently stripped by a minimized event, contradicting the spec's rationale that "a minimized event can be [a session's] first event; stripping these would silently null out the whole session's attribution." Separately, the outer dedupe cache `@distinct_id_has_sent_flag_calls` is a `SizeLimitedHash` (`utils.rb:148-162`), whose `[]=` does `clear if length >= @max_length` (`utils.rb:159`) before inserting — a **full wipe** of all tracked distinct_ids once the map reaches `Defaults::MAX_HASH_SIZE` (50,000), not incremental LRU eviction of a single oldest entry, contradicting the "SHOULD NOT clear the entire tracker" guidance (a SHOULD, not a SHALL). The per-distinct_id inner `SizeLimitedArray` (`utils.rb:167-180`) does correctly evict incrementally (`shift` on overflow) — only the outer hash has the full-clear behavior. Core gating logic is otherwise correct: minimization triggers only when `minimal_flag_called_events == true && has_experiment == false` (`client.rb:1062`, `feature_flag_evaluations.rb:198`), fails safe to the full event on any missing signal, and the gate persists through the `FlagDefinitionCacheProvider` round-trip (`feature_flags.rb:1244-1258`, `flag_definition_cache.rb`).
- **Backwards compatibility:** Backward-compatible for both fixes — adding entries to an allowlist only retains more data in minimized events (strictly additive, no removal); replacing full-`clear` with true LRU eviction is an internal memory-management change with no public API impact.
- **Remediation:** Add the 10 session-attribution property names from sdk-specs commit `b59e8b4` to `MINIMAL_FLAG_CALLED_EVENT_PROPERTIES` in `client.rb`. Separately, replace `SizeLimitedHash`'s full-`clear`-on-capacity behavior with incremental oldest-entry eviction (e.g. track insertion order and evict one entry per overflow, or switch to a proper LRU structure).

### n6 — Flush (🟡 Partial)
- **Spec requires:** `@both`. No-op on empty queue with no network call (matches); bypass `flush_at`/`flush_interval` and attempt delivery now (matches); acceptance scenario "Flush keeps events retryable when delivery fails": on a 503 (or other retryable failure), the call must not throw, and the failed event "should remain queued for retry."
- **SDK currently:** `Client#flush` (`client.rb:226-249`) correctly no-ops on an empty queue and bypasses batching intervals via `@worker.request_flush`. However, `SendWorker#run` (`send_worker.rb:58-77`) calls `send_batch` then unconditionally clears the in-flight batch in an `ensure` block (`send_worker.rb:69-73`: `begin send_batch ... ensure @lock.synchronize { @batch.clear } ... end`), regardless of whether `send_batch` succeeded. `Transport#send` (`transport.rb:68-94`) exhausts its own bounded retry budget (`@retries`, default from `Defaults::Request::RETRIES`) internally and returns a `Response` object on both success and terminal failure — it does not raise for a normal terminal failure, so `flush()` itself never throws (satisfying that half of the scenario). But once `Transport#send`'s internal retries are exhausted, the batch is gone: it is never re-added to `@queue`, so the failed event is **not** preserved for a later retry cycle, directly contradicting "the event named Save should remain queued for retry."
- **Backwards compatibility:** Breaking — re-enqueueing failed batches changes delivery/ordering semantics (potential duplicate-send on subsequent retry, unbounded-queue-growth risk during a sustained outage) that the current design doesn't guard against; should ship as an explicit opt-in mode rather than a silent default-behavior change.
- **Remediation:** On terminal (post-retry-budget) failure in `send_batch`, re-enqueue the batch's messages back onto `@queue` (respecting `max_queue_size`) instead of discarding them in the `ensure` block, ideally gated behind an opt-in flag to avoid surprising existing integrations that depend on today's drop-on-exhaustion behavior.

### n7 — Get Distinct ID (🟡 Partial)
- **Spec requires:** Spec's own `## Applicability` line says `client`, but the acceptance feature `get-distinct-id.feature` is tagged `@both` at the feature level (confirmed: `acceptance/public/get-distinct-id.feature:1`) and contains an explicit `@server` scenario: "Server SDKs do not expose ambient distinct id state" — `WHEN get distinct id is called on a server SDK THEN the SDK should report that no ambient distinct id is available." This models a defined, satisfiable server contract: server SDKs are expected to expose *some* callable answering this question, even if the answer is "no ambient id."
- **SDK currently:** No `get_distinct_id` method exists anywhere in the SDK — confirmed via `grep -rn "def get_distinct_id\|get_distinct_id" lib/` returning zero matches. There is no public, always-available symbol a caller can invoke to get the "no ambient id available" answer the `@server` scenario expects.
- **Backwards compatibility:** Backward-compatible — adding a `Client#get_distinct_id` that always returns `nil` (or a documented sentinel indicating "no ambient distinct id", since Ruby is stateless per call) is purely additive.
- **Remediation:** Add a public `Client#get_distinct_id` that returns `nil`/a "not available" sentinel, satisfying the `@server` scenario explicitly (mirrors the same gap and fix identified in posthog-python).

### n8 — Group Identify (🟡 Partial)
- **Spec requires:** `both` applicability, acceptance `@both`. "Group identify requires type and key" scenario: `WHEN group identify is called without a group key THEN no event named "$groupidentify" should be enqueued AND the SDK should record a validation warning` — drop + warn, not raise.
- **SDK currently:** `Client#group_identify` (`client.rb:432-438`) delegates to `FieldParser.parse_for_group_identify` (`field_parser.rb:74-98`), which calls `check_presence!(group_type, 'group type')` and `check_presence!(group_key, 'group_key')` (`field_parser.rb:79-80`) — both `raise ArgumentError` on nil/empty (`field_parser.rb:182-186`). Confirmed as tested, intentional behavior: `spec/posthog/client_spec.rb:1471` (`expect { client.group_identify({}) }.to raise_error(ArgumentError)`). This contradicts the acceptance scenario's drop-and-warn expectation; the happy-path event shape itself (`$group_type`/`$group_key`/`$group_set`, `field_parser.rb:88-97`) is correct and matches spec.
- **Backwards compatibility:** Breaking — the SDK's own test suite hard-asserts the raise; changing to drop+warn is an observable behavior change that should be deprecation-gated, not a silent flip.
- **Remediation:** Same remediation family as n1/n3: change `check_presence!` failures for `group_type`/`group_key` to log-and-drop instead of raising, on a deprecation timeline.

### n9 — Is Feature Enabled (❌ Fail)
- **Spec requires:** Hard `SHALL`, `@both`, no server-SDK carve-out: "The SDK SHALL accept a caller-supplied boolean default (`defaultValue`...) and SHALL return it whenever the flag has no value: flags not loaded yet, a failed flags request, or no flag with that key in the loaded flags. A flag that has a value — including `false` and variant strings — always wins over the caller-supplied default." The spec's own documented Ruby surface variant is `is_feature_enabled(key, distinct_id, groups: {}, person_properties: {}, group_properties: {}, only_evaluate_locally: false, send_feature_flag_events: true)` — note this illustrative signature is itself missing a default parameter, meaning the spec's own example is stale relative to its own SHALL text.
- **SDK currently:** `Client#is_feature_enabled` (`client.rb:475-483`) has exactly the signature quoted above — **no `default_value`/`defaultValue` parameter anywhere.** On a missing/unloaded/failed flag it unconditionally returns `nil` (`client.rb:498`: `return nil if response.nil?`); there is no way for a caller to make a miss resolve to a caller-chosen `true`/`false`. The SDK's newer canonical path, `FeatureFlagEvaluations#enabled?` (`feature_flag_evaluations.rb:85-90`), also has **no `default_value` parameter**: `def enabled?(key) ... flag&.enabled ? true : false end` — it collapses every miss to a hardcoded `false` rather than accepting a caller override. Neither the legacy nor the canonical API satisfies the spec's default-value contract. This mirrors the identical gap independently confirmed in posthog-python and posthog-node.
- **Backwards compatibility:** Backward-compatible — adding an optional `default_value:` keyword (defaulting to `nil` for `is_feature_enabled`, or a `nil`-sentinel-then-`false` pattern for `enabled?`) is purely additive; existing callers who don't pass it see identical behavior.
- **Remediation:** Add `default_value: nil` to `is_feature_enabled`, returning it (when non-nil) instead of the current unconditional `nil`/`false` collapse on a miss. Add an equivalent `default_value:` keyword to `FeatureFlagEvaluations#enabled?`, distinguishing "no default supplied" (current `false` behavior) from an explicit caller-supplied default.

### n10 — Logs (🟡 Partial)
- **Spec requires:** A `captureLog`/logger API producing OTLP-shaped log records (six severity levels including `trace`) shipped via `POST {host}/i/v1/logs` with the project token as a URL query parameter, batching/rate-capping, and `feature_flags`-array context enrichment alongside distinct-id/session-id correlation.
- **SDK currently: gem-boundary split is the critical fact.** The **core `posthog-ruby` gem has no Logs capability at all** — `grep -rln "capture_log\|i/v1/logs\|severityNumber\|severity_number" lib/` returns zero matches; `lib/posthog/logging.rb` is exclusively internal SDK diagnostic logging (prefixes messages with the SDK's own log prefix), unrelated to the product Logs capability. A plain-Ruby, Sinatra, or Sidekiq-only app using core `posthog-ruby` (no Rails) gets no Logs feature whatsoever. The separate **`posthog-rails` gem** (`posthog-rails/lib/posthog/rails/logs/`) does implement an opt-in OTLP logs pipeline, but as a `Logger` subclass (`logs/appender.rb`) riding on third-party `opentelemetry-logs-sdk`/`opentelemetry-exporter-otlp-logs` gems rather than a bespoke `captureLog` facade on the PostHog client itself — a materially different public API shape than the spec's documented capture API. Within that Rails-only path: severity mapping (`logs/severity.rb`) correctly maps debug/info/warn/error/fatal to OTLP severity numbers 5/9/13/17/21 with an unknown→info fallback, but the spec's six-level model includes `trace`(=1), which Ruby's five-level `Logger`-subclass design has no slot for. Endpoint construction (`logs/setup.rb:207-210`, `logs_endpoint`) correctly builds `{host}/i/v1/logs`, but authenticates via an `Authorization: Bearer` header (`logs/setup.rb:174`) rather than the spec's `?token={projectApiKey}` query parameter. Auto-attached context (`logs/appender.rb`) stamps `posthogDistinctId`/`sessionId` but omits the spec-mandated `feature_flags` array. Rate-capping (`logs/rate_limiter.rb`, 60s window, default 6,000/min, `logs/configuration.rb`) matches the spec's intent closely. A `before_send`-on-exception path drops the record entirely rather than the spec's "swallow the hook error, keep the prior value" — a deliberate, documented deviation. Batching/retry/wire-format is delegated entirely to the third-party OTel exporter, not built to this spec's own batching/retry contract, and is unverifiable in detail from this repo since the OTel gems aren't vendored.
- **Backwards compatibility:** Backward-compatible for the additive fixes (adding `feature_flags` to the auto-attached attributes, adding a `trace` severity mapping). The auth-header-vs-query-param mismatch needs verification against what PostHog's `/i/v1/logs` endpoint actually accepts before changing, since flipping it blindly could break currently-working Rails integrations if the endpoint only validates one form. Building a core-gem Logs capability (independent of Rails/OTel) is a large net-new addition, not a modification of existing behavior.
- **Remediation:** Prioritize: (1) document clearly that Logs support requires the separate `posthog-rails` gem — core `posthog-ruby` users have no path to this feature today; (2) add `feature_flags` to the Rails appender's auto-attached attributes; (3) add a `trace`-level severity mapping; (4) verify and, if needed, align the auth mechanism with `/i/v1/logs`'s actual accepted contract.

### n11 — Set/Reset Person/Group Properties For Flags (❌ Fail, all four contracts)

THEN person properties for flags should include...", "...flag reloads... THEN the feature flag request should include person property X") that make no client-only assumption and are mechanically satisfiable server-side. Per this audit's instructions to weight acceptance-test precision over stale spec prose (matching the precedent already set in the posthog-python compliance audit for these same four contracts), these are treated as in-scope-but-unimplemented rather than N/A.

Also worth flagging upstream to sdk-specs maintainers: the spec-prose `Applicability: client` and the acceptance files' `@both` tags are inconsistent and should be reconciled.

### n12 — Retry Queue (🟡 Partial)
- **Spec requires:** `both`. In-memory queue with backpressure/drop-when-full and a capacity warning; flush on size/timer/explicit trigger; classify retryable (network errors, 5xx, 408, 429) vs. non-retryable (other 4xx) failures; retryable failures keep the same events queued for a later, separate flush attempt; success removal by stable identity, not index, so events captured concurrently while a batch is in flight are not mistaken for the just-sent batch and dropped.
- **SDK currently:** In-memory `Queue.new` per client (`client.rb:139`), bounded by `@max_queue_size` (default `Defaults::Queue::MAX_SIZE`); full-queue enqueue attempts are dropped with a logged warning (`client.rb:1120-1140`, `enqueue`) — matches the capacity-warning requirement. `Transport#should_retry_request?` (`transport.rb:107-116`) correctly classifies 5xx/408/429 as retryable and other 4xx as terminal (logged, not retried). Concurrent-capture-during-flush safety is naturally satisfied by Ruby's `Queue#pop`, which removes by dequeue rather than by index, so events enqueued mid-flush cannot be confused with the in-flight batch. Gap: once a batch is dequeued via `SendWorker#build_batch`/`consume_message_from_queue!` (`send_worker.rb:138-166`) and handed to `Transport#send`, `Transport#send` performs its own bounded in-request retry loop (`retry_with_backoff`, `transport.rb:125-144`, honoring `Retry-After` via `parse_retry_after`, `transport.rb:154-165`) but once that retry budget (`@retries`) is exhausted, the batch is not returned to `@queue` for a later, independent flush cycle — `SendWorker#run`'s `ensure @batch.clear` (`send_worker.rb:69-73`) discards it unconditionally, matching the same drop-on-exhaustion behavior noted under Flush (n6). This is the identical underlying root cause as n6, viewed from the retry-queue contract's angle.
- **Backwards compatibility:** Needs deprecation path — converting to a true requeue-on-exhaustion model changes `on_error` callback timing/frequency and worker-loop blocking semantics, an observable change for integrations that depend on today's timing.
- **Remediation:** Same fix as n6: re-enqueue the batch (respecting `max_queue_size`) on terminal transport failure instead of discarding it in `SendWorker#run`'s `ensure` block, behind an opt-in flag given the existing behavior is relied upon today.

### n14 — Tracing Headers (🟡 Partial)
- **Spec requires:** `both` applicability. Server-side responsibilities: request-scoped middleware extracting `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` case-insensitively into context; sanitize (trim/strip control chars/cap length); explicit call-site values take precedence over context; personless-capture fallback (random `distinct_id` + `$process_person_profile=false`) when no identity is resolvable anywhere; **"Require identity for feature-flag evaluation. If server-side feature-flag evaluation... is called with no explicit distinct id and request context also has no distinct id, the SDK MUST return an empty/no-op evaluation result and MUST NOT make a feature-flag request or emit `$feature_flag_called` events."**; per-request isolation; headers never used for auth.
- **SDK currently:** `Internal::Context` (`internal/context.rb`) implements genuine per-request/fiber-local state via `ActiveSupport::IsolatedExecutionState` (when Rails is present) or `Thread.current` otherwise (`internal/context.rb:25-31`), satisfying request isolation. `posthog-rails`'s `TracingHeaders` module (`posthog-rails/lib/posthog/rails/tracing_headers.rb`) correctly extracts `X-POSTHOG-DISTINCT-ID`/`X-POSTHOG-SESSION-ID` case-insensitively (`header_candidates`, `tracing_headers.rb:51-55`, checking canonical/downcased/Rack-`HTTP_`-prefixed forms) and sanitizes (trim/strip control chars/cap at 1000 chars, `sanitize_header_value`, `tracing_headers.rb:16-23`). `Client#capture`'s `enrich_capture_attrs_with_context` (`client.rb:943-964`) correctly implements explicit-value precedence over context and the personless fallback (random UUID + `$process_person_profile: false`, `client.rb:958-963`) when no distinct_id is resolvable anywhere — this matches spec precisely for `capture`. **Gap:** none of the flag-evaluation methods consult `Internal::Context` at all — `is_feature_enabled`, `get_feature_flag`, `get_feature_flag_result`, `get_all_flags`, `get_feature_flag_payload`, and `get_all_flags_and_payloads` all take `distinct_id` as a required positional argument (e.g. `client.rb:476`, `client.rb:536`) with no context-fallback and no nil/blank-distinct_id no-op guard — calling one of these with `nil`/`''` either raises (via downstream `to_s`/hashing) or, worse, proceeds to make a real `/flags` HTTP request and can emit `$feature_flag_called`, contradicting the spec's `MUST NOT make a feature-flag request or emit $feature_flag_called events` requirement. Only the newer canonical `evaluate_flags` (`client.rb:614-740`) has any guard at all — a nil/empty `distinct_id` short-circuits to an empty snapshot (`client.rb:625-627`) — but even `evaluate_flags` does not fall back to `Internal::Context`'s ambient distinct_id when the explicit argument is absent; it only no-ops rather than resolving context first. Only Rails has this middleware; there is no Sinatra/Grape/plain-Rack-specific middleware, though `Internal::Context` and `TracingHeaders` are framework-agnostic enough to be wired up manually.
- **Backwards compatibility:** Backward-compatible — making `distinct_id` fall back to `Internal::Context.current&.distinct_id` when omitted/nil (with a no-op/empty-result guard when neither is present) on the legacy flag APIs, and adding the same context-fallback to `evaluate_flags`, are both purely additive; existing explicit-`distinct_id` call sites are unaffected.
- **Remediation:** Add `Internal::Context` fallback resolution to all flag-evaluation methods (`is_feature_enabled`, `get_feature_flag`, `get_feature_flag_result`, `get_all_flags`, `get_feature_flag_payload`, `get_all_flags_and_payloads`, `evaluate_flags`) so that when no explicit `distinct_id` is passed, the ambient request-context id is used if present; when neither is present, no-op (empty/nil result, no HTTP request, no `$feature_flag_called`) rather than raising or proceeding with a blank identity.
