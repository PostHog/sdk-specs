# Shared RPC contract selections

The [catalog](public-rpc-catalog.md) defines the selected target. This file records its evidence and the canonical-spec alignment work, not alternative behavior that adapters may accept.

## Selection method

Use the most common observed behavior among SDKs exposing the relevant operation. Count an SDK once, not each overload, facade, or platform bridge. React/Rails forwarding does not create additional evidence beyond browser/Ruby; an absent API is not a vote for an alternative shape. This is implementation prevalence, not download volume or customer usage.

The pinned [source inventory](public-rpc-source-inventory.md) covers the canonical SDK inventory and the separately selected experimental browser package. Experimental-only APIs remain source evidence, not extra votes on established API families. Clear existing canonical requirements remain the baseline where the audit found an omission rather than a competing choice. When there is no established plurality, select a concrete existing pattern or explicit initial policy rather than leave an implementation-conditioned contract.

No SDK code, adapter, acceptance feature, or canonical OpenSpec file was changed by these selections. OpenSpec changes must use the repository's proposal/archive workflow. The compatibility work is downstream: a target default or result does not authorize an adapter to insert values, drop results, or compose SDK calls.

## Selected outcomes

| Topic | Selection | Evidence / basis |
|---|---|---|
| Identity and group keys | Strings | The ordinary signatures across browser/RN, iOS, Android, Flutter, KMP, Unity and the server SDKs use strings. Numeric/subject overloads are not a second canonical identity type. Runtime subject references remain separate for session-transfer APIs. |
| Register cardinality | One key/value per `/register` | Android, KMP, Flutter, Unity, Roblox are singular; browser, RN, iOS are bulk. **5 singular versus 3 bulk** among these eight exposed client surfaces. A single-entry map is a shape translation, not a loop. register_once and register_for_session retain their actual bulk operation shape. |
| Group flag overrides | One group type plus properties; no group key; reload=true | iOS, Android, Flutter, Unity, Roblox take type/properties; browser/RN use a type-map. Native iOS and Android declarations and Flutter wrappers distinguish this from membership. KMP does not expose this setter in the inspected common surface. The one-type shape has the plurality. |
| Missing enablement | false; explicit caller fallback wins only when missing | iOS, Android, KMP, Flutter mobile, Unity resolve missing to false; browser/RN permit nullish. Most enabled methods return booleans, not raw variants. Nonempty variants map to true, empty strings to false. |
| Value and payload results | Scalar flag values, decoded JSON payloads, null for unavailable data | Common mobile/server getter pattern. Structured flag results have one separate record with key/enabled/variant/payload. Null instead of language-specific undefined is a transport/API baseline selection, not evidence that every existing SDK already returns null. |
| Fresh flag reads | Gate on remote-loaded results since setup/reset; no force-fetch or waiting | Browser is the inspected public fresh option. Its readiness gate returns unavailable before remote flags load. The combined fresh/local-only case returns fallback by selected policy. Normal expiry/refresh behavior remains separate. |
| Payload match selector | Select local payload by supplied bool/variant; normal remote fallback returns its evaluated payload | Node and Ruby use a supplied match value instead of local value evaluation; Python uses it for local payload selection. All have an ordinary remote fallback. A selector is not a forced remote variant assignment or permission to overwrite the evaluated cache value. |
| Payload/bulk tracking | Payload reads silent by default; bulk reads silent | iOS/Android/Flutter payload getters and bulk result getters are silent; Python payload tracking defaults false. Preserve an explicit payload tracking option, but do not invent a mandatory per-call bulk tracking argument. |
| Snapshot filtering | Silent creation/payloads; tracked value/enablement reads; empty only_accessed before access | Already prescribed by evaluate-flags. The all-flags-before-access outlier is a gap, not a reason to weaken the target. |
| Person-property input | Explicit `set` and `set_once` maps, no competing open identify-property envelope | iOS/Android/Flutter support the two maps directly; browser supports their positional equivalents. Existing single-map-only implementations need a gap entry, not two adapter calls. |
| Omitted identify | Invalid/no-op, no identity transition or event | Explicit IDs are required by iOS, Android, Flutter, KMP, Unity and server identify/profile APIs. Browser/core omission overloads do not define the shared requiredness. |
| Alias | Ambient source for stateful calls, explicit/resolved source for request calls; source=`distinct_id`, target=`alias` | Shared identity model across public alias APIs. An optional properties map carries ordinary alias-event data; authoritative source/target fields win. Emitting `properties.distinct_id` is the existing canonical scenario and a selected envelope convention; it is not claimed as a measured majority across mobile implementations. |
| Group profile envelope | `$group_set` contains profile properties | Canonical builder shape in browser/core, iOS, Android, Flutter, Unity and server group-identify DTOs. Scenario assertions should use `$group_set.plan`, not duplicate `plan` at the root. |
| Property precedence | Per-event properties override registered properties | Explicit register specification; core `commonProperties` places event properties after persisted properties. Unity capture likewise merges caller properties after super properties. SDK-owned identity/session/envelope fields keep their authority. |
| Screen context | Update runtime screen context; do not persist it as user identity | iOS, Android, Flutter and Unity maintain screen/replay context in their public screen paths. This resolves the screen scenario without adapter state. |
| Opt-out clearing | Per-call `clear_persistence=false`; true clears identity/super properties while retaining denial | Retaining identity by default matches the ordinary native/mobile consent APIs. The clearing requirement exists in opt-in scenarios but has no agreed input placement; **the per-call field is a selected policy**, not a claim that most SDKs already expose it. |
| Opt-in event | No event by default; explicit capture_event_name requests one | Native/mobile and core consent operations do not emit the browser consent event by default. A supplied nonempty name uses the SDK's consent-event path, not an adapter capture. |
| Reset | New anonymous identity by default, stable device ID, clear resettable context, restore configured consent | ReuseAnonymousId=false and stable device IDs are common native defaults. Browser reset resets consent; iOS storage reset removes persisted opt-out; core reset clears resettable opt-out state. Android has an in-memory/persistence nuance, so **uniform post-reset consent is the selected canonical policy**, not an assertion of universal behavior. Reset can therefore change effective consent; applications and SDK migrations must account for that. |
| Flag notifications | No-argument readiness signal; runtime registration notifies immediately if already loaded; actual unsubscribe | No-argument notifications are used by native/mobile callback surfaces (iOS notifications, Android, Flutter, Unity), versus value-bearing browser/RN callbacks. For late registration the two direct browser/RN methods differ: browser notifies immediately, core/RN only on the next update. **Immediate notification is the canonical-scenario tie-breaker.** No payload is manufactured through hidden getters. |
| Configuration updates | One shared live-config patch record; initialization-only fields excluded | Only browser provides the inspected general set_config operation. There is no majority to infer: use its partial-update concept as the target, with one explicit mutability boundary and top-level replacement policy. Other SDKs do not select their own subset. |
| Queue defaults | Threshold 20, interval 30s, capacity 1000, batch 50 | These values are explicit together in iOS, Android, Flutter, KMP and Unity configuration. Other SDKs have different queues, but this is the dominant common client tuple, selected as the shared baseline rather than per-SDK defaults. |
| Flush/shutdown | Void completion after bounded native drain/attempt; unified applicable queues; timeout 30s | Awaitable server/core flush and common void mutation results provide the pattern. Unified logs/traces coverage is already canonical. **A common 30s flush deadline and exact bounded completion are policy selections**, not measured universal native behavior. They do not promise successful server ingestion. |
| Ordinary capture/mutation result | void; AI capture returns admitted UUID/null | Void is the common native/mobile and Node/Java mutation surface. UUID/result-returning operations remain observable gaps; do not discard their results. AI's UUID result is already explicit in capture-ai. |
| Bootstrap | Explicit identity/flag/payload/session fields; enabled bootstrap snapshot replaces persisted flags | Current canonical bootstrap and iOS implementation prescribe replacement of persisted flags, followed by complete-response replacement and partial/computation-error merging; core/RN currently layers persisted flag values over bootstrap. Preserve identified local identity against conflicting identified seeds. This is an existing canonical winner, not a reopened native choice. |
| Full AI and tracing headers | enable_full_ai_capture=false; hostname allow-list empty/disabled | Explicit capture-ai and tracing-headers requirements. AI wrapper integration and application request fixtures remain separate from SDK capture calls. |
| Logs/metrics/traces | Distinct trigger/capacity/batch knobs; shared numeric defaults | Logs use the native/mobile 30s/20/1000/50/500-per-10s tuple. Metrics use existing core 10s/1000 limits. OTLP spans have one inspected public implementation: retain its 5s/512/2048, 128 attributes/events, 8192-character value limit, 10000 live spans and 1h age limit. A single implementation is not a cross-SDK majority. |
| Exceptional numeric/config defaults | One explicit table, including zero/invalid distinctions | Remaining cross-family choices (for example evaluated-result TTL, generic retry ceiling, automatic-capture selection, and default attribution) are **initial policies**, not audited vote totals. They are deliberately revisable without reopening the common-schema decision. |
| Batch result access | Retained BatchSummary plus four explicit accessor RPCs | Rust CaptureSummary stores private fields and exposes submitted/not_persisted/all_persisted/event_results methods. Serializing those by secretly calling all four would violate the invocation rule. These are four explicit additions to the original 174 operations. |
| Facade getters | Explicit get_logger/get_metrics operations before facade methods | Browser, RN, Flutter and iOS expose product logger access; Node/Python expose metrics access. A property getter must not be hidden inside a logger/metrics method RPC. A no-op facade before initialization is the selected common pattern, rather than a nullable product handle. Configuration's diagnostic logger uses a separate reference kind. Together with summary accessors, the catalog has **180 operations**. |
| Rare product helpers | Use the existing public result/data pattern | SurveyRenderReason keeps visible/reason semantics rather than inventing a boolean projection. Session transfer retains its reserved `__posthog` payload and seconds-based startTime. Source-only helpers are not evidence of universal availability. |
| Runtime reference transport | Typed references, separate argument-reference paths, explicit callback/receiver lifetime | Shared harness policy selection. Reference objects, context continuations and callbacks do not gain SDK-conditioned schemas. Fixture construction and negative-input representability remain separate from a successful SDK result. |

## Canonical specification alignment

The pinned spec head is `4f2f48f48e2e6dfafb8383fb679af4e69ffdceb0`. The local checkout is older; it was not rewritten. The selected contract resolves, rather than defers, the following alignment work:

1. **register / set-group-properties-for-flags:** express single-key registration and one-type overrides; align group-key wording and client applicability. Multi-key registration scenarios need explicit calls, not an adapter loop.
2. **is-feature-enabled / flag results:** standardize missing-without-default to false, decoded payload/null results, and the common structured record. Keep snapshot no-I/O/tracking/filtering guarantees.
3. **on-feature-flags:** replace value-bearing callback assertions with readiness observations and explicit subsequent reads; retain immediate late registration and real removal.
4. **opt-in / reset:** define the clearing argument, default silent opt-in, and consistent reset consent/lifetime behavior.
5. **identify / alias:** require identify ID; distinguish implicit client alias source from missing request source; align alias properties.
6. **capture / register / group / group-identify:** settle merge precedence and precise `$group_set` property paths; retain context/personless/immediate provisions already present in current specs.
7. **screen / capture-exception:** align runtime screen context and handled-exception applicability for both identity models.
8. **setup / flush / shutdown / logs / traces:** record shared configuration defaults, mutability, completion boundaries, unified flush and keep-alive integration. Preserve AI/header options and existing security/privacy gates.
9. **bootstrap:** retain canonical identified-user reconciliation and bootstrap-over-persisted flag precedence; standardize the session/reset seed input shape.

These are downstream spec/feature changes, not permission to vary an SDK binding. The next step is the per-SDK binding/gap assessment against the selected catalog. SDK API/default migrations, implementation tests, and releases remain separate work.
