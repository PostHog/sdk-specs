## Context

An SDK-generated `$exception` event carries several kinds of metadata with different owners:

- event-level capture metadata such as `$exception_level` and `$exception_source`;
- per-entry mechanism metadata such as `type`, `handled`, `synthetic`, and `source`;
- optional native symbolication metadata in `$debug_images` and frame addresses;
- explicit producer inputs such as `$exception_fingerprint` and release/build context;
- denormalized fields derived by Cymbal, including `$exception_sources` and `$exception_handled`.

These concepts are currently documented separately or not at all. In particular, three source-like fields are easy to confuse: `$exception_source` identifies the capture integration, `$exception_sources` lists source files derived by Cymbal, and `mechanism.source` identifies a nested-exception relationship.

This contract applies to SDK-owned manual and automatic capture paths in client and server SDKs. It defines internal wire behavior without expanding the client-only public `capture-exception` API.

## Goals / Non-Goals

**Goals:**

- Define the canonical producer envelope for `$exception` events.
- Assign one meaning and owner to each capture, mechanism, relationship, and symbolication field.
- Preserve known metadata and represent unknown metadata through omission.
- Define trustworthy capture-boundary defaults and precedence.
- Document the boundary between SDK-produced and Cymbal-derived properties.
- Allow SDKs to converge independently without coordinated releases.

**Non-Goals:**

- Define exception grouping or issue-severity policy.
- Define stack parsing, frame ordering, source context, or symbol-upload algorithms.
- Define product presentation, suppression, assignment, or notification behavior.
- Replace the `exception-steps` capability.
- Replace the flat `$exception_list` envelope with recursively nested exception objects.
- Backfill historical events.

## Decisions

### 1. Widen the capability to exception event metadata

The capability owns the exception-specific producer envelope and metadata ownership, not only the nested mechanism object. This reflects that severity, integration source, mechanism fields, native images, and processor-derived denormalizations form one wire contract.

Alternative: keep a mechanism-only capability. Rejected because it leaves `$exception_level`, `$exception_source`, `$debug_images`, and similarly named processor fields without a coherent ownership model.

### 2. Separate capture category, integration, relationship, and source files

- `mechanism.type` is the semantic capture category, such as `middleware`, `task`, `panic`, or `onconsole`.
- `$exception_source` is the concrete technology and hook, such as `django.middleware` or `python.sys_excepthook`.
- `mechanism.source` is the relationship through which a nested exception was reached, such as `cause` or `unwrap`.
- `$exception_sources` is generated by Cymbal from in-app stack-frame source paths.

This keeps equivalent boundaries queryable across technologies while retaining concrete integration context.

Alternative: put Django, FastAPI, or Rails in `mechanism.type`. Rejected because it fragments semantic categories and duplicates integration identity.

### 3. Define handled relative to the application boundary

Handled state says whether the exception escaped the relevant application boundary. Deliberate manual, logger, console, or response-producing handler captures are handled. An exception that escapes application code is unhandled even though SDK or framework infrastructure eventually catches it to report it.

Alternative: define every observed/caught exception as handled. Rejected because global handlers and crash reporters necessarily catch failures that remain unhandled by the application.

### 4. Make synthetic provenance explicit

Synthetic state describes the represented exception or stack, not severity or handled state. Generated current stacks and normalized non-exception inputs are synthetic. A runtime exception remains non-synthetic when its original stack is preserved or when no replacement stack is generated. Unknown provenance is omitted.

### 5. Treat exception lists as flattened conceptual trees

Nested relationships are not always causes. Runtimes expose implicit contexts, aggregate members, suppressed exceptions, inner exceptions, and scalar or multi-error unwrap relationships. `mechanism.source` preserves that relationship when known.

The list is a deterministic depth-first, parent-before-child flattening. Every entry carries `mechanism.exception_id`; every nested entry carries `mechanism.parent_id`, `type: chained`, and its relationship source. This adjacency-list representation supports linear and branched trees while preserving the existing flat `$exception_list` envelope.

### 6. Derive boundary defaults at the owner

The capture path supplies defaults:

| Capture boundary | Level | Type | Handled | Source |
| --- | --- | --- | --- | --- |
| Public/manual caught exception | `error` | `generic` | `true` | omitted |
| Logger/console | normalized level | `logger`/`onconsole` | `true` | concrete integration |
| Consuming framework handler | `error` | `middleware` | `true` | concrete framework hook |
| Escaping request/task boundary | `error` | `middleware`/`task` | `false` | concrete framework hook |
| Non-terminating uncaught boundary | `error` | stable category | `false` | concrete runtime hook |
| Terminating crash/panic/signal | `fatal` | stable terminating category | `false` | concrete runtime hook |
| Context-free builder | omitted | omitted | omitted | omitted |

Typed integration metadata wins over recognized native metadata, which wins over the boundary default. An invalid override is ignored before precedence continues; a context-free builder omits an invalid value when no lower-precedence source exists. Generic application property bags cannot override SDK-owned canonical exception metadata. Internal integration channels and documented typed public overrides are distinct from generic property bags and participate in typed precedence.

### 7. Include native debug images as optional symbolication metadata

Native SDKs know loaded binary addresses and authoritative build identifiers; Cymbal cannot reconstruct them after the process exits. `$debug_images` therefore belongs to the producer envelope and links to native `instruction_addr` and `image_addr` frame fields.

The contract defines the accepted object shape and linkage invariants but leaves Mach-O, ELF, and PDB identifier algorithms to native symbolication implementations. Deferred crash reporters preserve the original crash-boundary metadata when reconstructing and enqueueing an event on the next launch.

### 8. Record grouping and release inputs without owning their policies

`$exception_fingerprint` is an optional explicit producer override. SDKs preserve it when supplied and do not invent it. Release/build properties pass through the normal capture enrichment pipeline. Grouping selection, release resolution, and symbol upload remain processor or product concerns.

### 9. Make Cymbal ownership explicit

Cymbal derives query and processing outputs from canonical producer input. SDKs do not independently synthesize `$exception_sources`, `$exception_functions`, `$exception_types`, `$exception_values`, fingerprint records/versions, issue IDs, resolved releases, or processing diagnostics. Nested `mechanism.handled` is authoritative over legacy top-level handled input.

### 10. Preserve compatibility during convergence

The wire changes are additive. Existing `$exception_source` producers continue to work, but future values follow a stable namespaced convention. Legacy SDKs may continue to omit optional fields. Consumers handle absence without requiring coordinated releases.

## Risks / Trade-offs

- [The capability becomes broad] → Limit it to exception-specific envelope fields and ownership; reference separate stack, steps, grouping, and release capabilities.
- [Existing source names are not namespaced] → Preserve existing values while requiring stable namespaced values for new integrations and converging old integrations incrementally.
- [Generic properties can conflict with canonical metadata] → Reserve SDK-owned and processor-owned exception keys; allow overrides only through documented typed inputs.
- [Existing SDKs place linkage fields inconsistently] → Standardize `exception_id` and `parent_id` inside `mechanism`, matching maintained SDK evidence and preserving the flat exception list.
- [Native schemas vary] → Require only the fields Cymbal needs and allow optional format-specific metadata.
- [Processor ownership differs from legacy SDK output] → Treat nested mechanism metadata as canonical while accepting legacy denormalizations during migration.

## Migration Plan

1. Publish the canonical `exception-event-metadata` capability and private acceptance scenarios.
2. Update shared builders to preserve valid supplied metadata, omit unknown optional fields, and emit required tree linkage on final events.
3. Update capture boundaries with semantic types, concrete `$exception_source` values, handled state, level, and synthetic provenance.
4. Update cause and aggregate builders to preserve relationship-specific `mechanism.source` values.
5. Add native debug-image conformance where SDKs capture address-based native frames.
6. Keep Cymbal authoritative for derived query, grouping, issue, and release properties.
7. Converge linear and aggregate builders on deterministic `exception_id`/`parent_id` tree linkage.

Rollback consists of reverting an SDK release. Older SDKs continue to omit optional fields, so no coordinated consumer rollback or data migration is required.

## Open Questions

SDK-specific API spelling, extensible outermost mechanism categories, native identifier algorithms, and release sequencing remain implementation details within this contract.
